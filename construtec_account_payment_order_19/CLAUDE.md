# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

`account.payment.order` — a header model with a `tipo` field (`anticipo` / `anticipo_viaticos` / `pago_directo`) representing flavors of a real Construtec accounting flow: money moves through an intermediary (an advance to a contact, or an employee reimbursement) and later has to be reconciled against vendor bills that belong to a **different partner** than the payment. Native Odoo reconciliation works per-partner/account and can't do this on its own. Migrated from the Odoo 16 module `bolson` (`..\Odoo16\bolson\`, "Manejo de cajas chicas y liquidaciones").

**`tipo='liquidacion'` existió como un cuarto valor/registro separado hasta que se fusionó dentro de Anticipo** (ver "Fusión: Liquidación deja de ser un tipo/registro aparte" más abajo, al final de la narrativa histórica) — de aquí en adelante, "liquidar" un Anticipo/Pago Directo significa que ese MISMO registro alcanza `state='liquidado'`, no que se crea un registro distinto. Buena parte de la narrativa histórica que sigue en este archivo describe el diseño de dos registros tal como existió durante gran parte de esta sesión - se deja como contexto de cómo se llegó al diseño actual, no como descripción de algo que siga funcionando así.

## What each `tipo` means, and the real workflow between them

**`anticipo_viaticos`** (ver la sección "FUSIÓN" y la de UX más abajo): comparte EXACTAMENTE el mismo ciclo enviar/aprobar/rechazar/aplicar que `anticipo` (constante `ANTICIPO_TIPOS = ('anticipo', 'anticipo_viaticos')` en `account_payment_order.py`, usada en todos los guards) - la única diferencia real es que trae `viaticos_line_ids`/captura de empleado y es el único que Community ve. Todo lo escrito abajo sobre "Anticipo" aplica igual a los dos, salvo donde se diga lo contrario.

- **Anticipo**: hand a contact money up front. `action_aplicar()` creates a normal `account.payment` (outbound, `partner_type='supplier'`) to `partner_id`, posted with `destination_account_id` forced to `cuenta_anticipo_id` (an "anticipos por liquidar" account) instead of the contact's normal payable. **`cuenta_anticipo_id` must be `account_type in ('asset_receivable', 'liability_payable')`** (enforced via the field's `domain=`) — anything else (e.g. a plain expense account) makes it invisible to `action_conciliar()`'s netting logic later and it will falsely report a mismatch when it's time to liquidar. `factura_ids` is **optional** at Aplicar time (attach one only if you already know which invoice it'll cover) — see the auto-detection note below. **`payment_method_line_id`** (domain `journal_id.outbound_payment_method_line_ids`, reset on journal change via `_onchange_journal_id_payment_method`) lets the user pick the payment method (Manual, Cheque, etc.) before applying; if left empty, `action_aplicar()` omits the key entirely from the `create()` vals so `account.payment`'s own `_compute_payment_method_line_id` picks a sensible default from the journal — passing `False` explicitly would instead pin it to "no method" and break `action_post()`.
- **Liquidar un Anticipo/Anticipo Viáticos ya Aplicado**: sobre el MISMO registro, se siguen agregando facturas a `factura_ids` (y opcionalmente más pagos vía `action_crear_pago()`) hasta que el botón "Liquidar" (`action_conciliar()`) puede correr: neta `factura_ids` contra `pago_ids` (N:M, no necesariamente 1:1) y postea un `account.move` regularizador que concilia todo — tolerando un desfase vía `cuenta_ajuste_id` si los totales no cuadran exacto. Termina en `state='liquidado'`. Ver "Fusión: Liquidación deja de ser un tipo/registro aparte" para el detalle completo.
- **Pago Directo**: the 1:1-ish case — someone (e.g. an employee) already paid a vendor bill out of pocket, in the company's name. Odoo ends up with a vendor bill (in the *vendor's* name) and needs a reimbursement payment (in the *employee's* name); it's reconciled with `action_conciliar()`/`action_cancelar()` **exactly like un Anticipo liquidándose** — same methods, same engine (guard: `if self.tipo not in ANTICIPO_TIPOS + ('pago_directo',): raise ...`). Va directo de `borrador` a `liquidado` (nunca pasa por `action_aplicar()`). Typically 1 factura + 1 pago, but nothing enforces that — it's the identical N:M mechanism. A diferencia de Anticipo, **no admite `cuenta_ajuste_id`** — debe cuadrar exacto.

**Anticipo vs. Pago Directo auto-detection** (`_aviso_posible_pago_directo()`, called at the end of `action_aplicar()`): if an Anticipo has factura(s) attached whose total exactly matches `monto`, and none of those facturas already have a reconciled payable/receivable line, that's not really a pending-liquidation Anticipo — it's a same-day full payment, i.e. a Pago Directo. The user chose **warn, don't auto-switch**: this returns an `ir.actions.client` / `display_notification` (sticky, type `warning`) instead of silently changing `tipo` or force-reconciling anything.

## Comprobante de Pago (printable voucher)

`report/account_payment_order_report.xml` is bound (`binding_type='report'`) to `account.payment.order` directly, so **Imprimir → Comprobante de Pago** is available on any record regardless of `tipo` — no per-tipo report needed. It shows `tipo`/fecha/contacto/diario, the Facturas table (skipped entirely if `factura_ids` is empty), and a "Pago(s)" table built from `o.pago_ids`. The "Diferencia" row is only rendered when there are facturas to compare against.

## Permissions

**Anyone in `account.group_account_invoice`** (the base "Facturación" group, already granted in `ir.model.access.csv`) **can create/edit an order and leave it in `borrador`**. **Only `account.group_account_manager`** ("Administrador") can advance state — `action_aplicar()` (→ aplicado), `action_conciliar()`/`action_cancelar()`/`action_crear_pago()`/`action_cancelar_anticipo_aplicado()` all call `_check_es_administrador_contable()` first, which raises `AccessError` if `self.env.user.has_group('account.group_account_manager')` is false. This is enforced in **Python, not just hidden buttons** — the buttons also carry `groups="account.group_account_manager"` for UX, but the real gate is server-side since a user could otherwise call the method directly (RPC, automation, etc). No separate access-control-list entry was needed for the manager group: `account.group_account_manager`'s `implied_ids` already includes `account.group_account_invoice` (`..\odoo\addons\account\security\account_security.xml:78`), so it inherits the same CRUD grant.

## Architecture

- **`action_conciliar()`/`action_cancelar()`** (`models/account_payment_order.py`) are the ported `bolson.bolson.conciliar()`/`cancelar()`, guarded with `if self.tipo not in ANTICIPO_TIPOS + ('pago_directo',): raise UserError(...)` plus the manager-only permission check above. Aplica igual a Anticipo/Anticipo Viáticos liquidándose sobre sí mismos y a Pago Directo.
- **`factura_ids`/`pago_ids`** are `One2many` via the `payment_order_id` field added to `account.move`/`account.payment` (`models/account_move.py`, `models/account_payment.py`) — same pattern as the original's `bolson_id`. The form uses `widget="many2many"` on these One2many fields (a deliberate Odoo trick, kept from the original) so users can search/attach *existing* posted bills/payments instead of creating new ones inline.
- **Domain fix vs. the original**: `bolson`'s `facturas` field filtered `[('payment_id', '=', False)]` — that field never existed on `account.move` (checked against `..\odoo\addons\account\models\account_move.py`; only `account.move.line.payment_id` and `account.move.origin_payment_id` exist). Replaced with `[('move_type', 'in', ('in_invoice', 'in_refund')), ('state', '=', 'posted')]`, which also fixes the original never actually restricting to vendor bills.

## Odoo 16 → 19 API deltas that mattered (checked against `..\odoo\addons\account\models\`)

| v16 (`bolson`) | v19 |
|---|---|
| `made_sequence_hole` | renamed **`made_sequence_gap`** |
| `communication` (account.payment) | renamed **`memo`** |
| `payment_state` selection (account.move) | gained a **`blocked`** value — don't hardcode a 6-item list |
| **`account.payment.state`** | **completely different lifecycle**: no longer `draft`/`posted`/`cancel`. Now `draft` / **`in_process`** / **`paid`** / `canceled` / `rejected` (`account_payment.py:36-43`). `action_post()` on a payment lands it in `in_process`, not `posted` — it only reaches `paid` once its "Outstanding Payments/Receipts" bridge account nets to zero (`_compute_state`, `account_payment.py:454-467`). **This bit us**: `pago_ids`'s domain and `action_conciliar()`'s loop originally filtered `state == 'posted'` (copied from the v16 pattern) and silently matched *zero* payments — `orden.pago_ids` came back empty with no error, because a One2many field's `domain=` is enforced on *read*, not just in the UI. Fixed to `state in ('in_process', 'paid')`. If you see a payment mysteriously missing from `factura_ids`/`pago_ids`, check its actual `state` value first, not just whether it "looks posted" in the UI. |
| `account.payment` no longer delegates to `account.move` for `line_ids` | `payment.line_ids` **raises `AttributeError`** — use **`payment.move_id.line_ids`**. The v16 module's `for l in c.line_ids:` relied on old-style `_inherits` delegation that no longer applies. |
| Payments post through an **"Outstanding Payments"/"Outstanding Receipts" bridge account** (`account_type='asset_current'` in this DB, not `asset_cash`) before ever touching the bank | `bolson`'s netting filter (`account_type not in ['asset_cash']`) is **not enough** in v19 — that bridge account passes the same filter, and since it's always a balanced in/out pair *within the payment itself*, including it silently cancels out and produces a totals mismatch that has nothing to do with the real invoice/payment imbalance. Fixed by filtering explicitly to `account_type in ('asset_receivable', 'liability_payable')` — the only two account types that represent an actual amount owed to/from a partner, regardless of what the "other leg" of any given line turns out to be (cash, bridge account, whatever). This is more robust than the original's approach for any Odoo version, not just a v19 patch. |
| `account.payment.reconciled_invoice_ids`/`reconciled_bill_ids` are **computed fields with a custom `_search`** (`_search_reconciled_invoice_ids`, `account_payment.py:783`) that only implements `'in'`/`'='` against a **concrete id** (`browse(value).reconciled_payment_ids.ids`) | Putting `('reconciled_invoice_ids', '=', False)` in a domain silently becomes `browse(False)` → empty recordset → `[('id', 'in', [])]`, i.e. **matches nothing, ever** — not an error, just an empty result. This made `pago_ids` come back empty exactly like the `state` bug above, for a different reason. Fixed by **dropping both from the field's `domain=`** and keeping the check only as a plain Python attribute read inside `action_conciliar()` (`if pago.reconciled_invoice_ids or pago.reconciled_bill_ids: raise UserError(...)`), which goes through the normal compute and works fine. **Lesson for this module**: any computed field with a non-trivial custom `_search` is suspect as a domain filter for `=False`/`!=False` — verify empirically (as done here, via `odoo-bin shell`) rather than assuming `=False` means "is empty" the way it does for a plain stored field. |
| `reconciled_invoice_ids`, `reconciled_bill_ids`, `destination_account_id`, `amount_total_signed`, `amount_untaxed_signed`, `account_type`, `account.account.reconcile`, `account.move.line.reconcile()`/`.remove_move_reconcile()` | unchanged |

## FUSIÓN: Solicitud de Pago + Anticipo son el mismo registro (`account.payment.order`, `tipo='anticipo'`)

**Esto reemplaza el diseño de dos modelos descrito en el resto de esta sección** (que existió durante buena parte de esta sesión: `account.payment.order.request` + un Wizard "Crear Anticipo" que convertía la Solicitud aprobada en un `account.payment.order` real, un segundo registro aparte). El usuario, probando el flujo real de punta a punta, concluyó que la separación era innecesaria y confusa ("creo que la estamos regando") y pidió fusionarlos en un solo registro.

**Qué cambió, en concreto**:
- `account.payment.order.request`/`.line` y el Wizard "Crear Anticipo" **se eliminaron por completo** del módulo (tablas huérfanas en la base de datos tras el `-u` - aceptado, sin migración de datos: el usuario borró los datos reales de producción por su cuenta antes de este despliegue).
- Todos los campos que tenía la Solicitud (`employee_partner_id`, `viaticos_line_ids`, `justificacion_tipo_id`, `origin`/`sync_state`/etc., el mecanismo completo de sincronización RPC) se movieron **tal cual** a `account.payment.order` — ahora conviven ahí con `journal_id`/`cuenta_anticipo_id`/`payment_id`/`factura_ids`/`pago_ids`, que ya existían para Anticipo/Liquidación/Pago Directo. La función a nivel de módulo `_resolve_employee_for_partner()` también vive ahora en `account_payment_order.py` (antes en el archivo eliminado) — `res_partner.py` importa de ahí.
- **`state` es un único Selection en español** ahora: `borrador`/`enviado`/`aprobado`/`rechazado`/`aplicado`/`cancelado`. `enviado`/`aprobado`/`rechazado` solo aplican a `tipo='anticipo'` (el ciclo heredado de la Solicitud); Liquidación y Pago Directo siguen yendo directo de `borrador` a `aplicado` vía `action_conciliar()`, exactamente como antes de la fusión — **no se tocó nada de esa lógica**. Los métodos `action_submit()`/`action_approve()`/`action_reject()`/`action_reset_to_draft()`/`action_cancel()` (nuevo, ported de `.request`) ahora ganan un guard `if self.tipo != 'anticipo': raise UserError(...)` que antes no hacía falta (eran un modelo aparte).
- **`action_aplicar()` ahora exige `state == 'aprobado'`** para `tipo='anticipo'` - cambio de comportamiento confirmado explícitamente con el usuario: **ya no existe el atajo** de aplicar directo desde `borrador` un anticipo creado a mano en Enterprise. Todo anticipo, incluso uno que nunca pasó por Community, debe pasar por Enviar+Aprobar antes de poder Aplicarse (un solo camino auditable).
- **El Wizard desaparece** - los campos que llenaba (`partner_id`, `journal_id`, `cuenta_anticipo_id`, `payment_method_line_id`, `monto`) ya existían en `account.payment.order`; ahora son editables directamente en el formulario mientras `state in ('borrador', 'aprobado')` (antes solo `'borrador'`), para que el contable los llene justo después de Aprobar, sin ningún paso de "conversión" intermedio. El aviso de "Anticipos pendientes de liquidar" que vivía en el Wizard se movió dentro de `action_aplicar()`, encadenado con `_aviso_posible_pago_directo()` vía el mecanismo nativo `next` de `display_notification` si ambos aplican a la vez.
- **`journal_id` dejó de ser `required=True` a nivel de campo** — antes SIEMPRE era obligatorio (tenía sentido: solo existía para Anticipo-ya-con-wizard/Liquidación/Pago Directo, todos creados con diario conocido de entrada). Ahora un Anticipo se crea SIN diario (lo llena el contable después de Aprobar) — **bug real encontrado verificando esto**: quitar `required=True` sin más habría permitido crear una Liquidación/Pago Directo sin diario también (antes lo impedía la constraint de la BD). Fix: nueva `@api.constrains('tipo', 'journal_id')` (`_check_journal_id()`) que exige diario siempre para `tipo != 'anticipo'`, más un chequeo explícito dentro de `action_aplicar()` para `tipo='anticipo'` (mismo patrón que `monto`/`cuenta_anticipo_id`/`partner_id`, que tampoco son `required=True` a nivel de campo).
- **Nueva secuencia real para `name`**: antes, para `tipo in ('anticipo', 'pago_directo')`, `_compute_name()` dejaba un placeholder estático `"Nueva Orden de Pago"` (mismo bug para los dos tipos) — ahora un `create()` override asigna `OP/0001`, `OP/0002`... (secuencia `account.payment.order.sequence`, mismo xmlid reciclado de la vieja secuencia `SOL/` de la Solicitud - `data/account_payment_order_sequence.xml`) para ambos tipos. En ese momento Liquidación seguía con su propio "No. Liquidación" manual aparte (`'Liquidación %s' % no_liquidacion`) - eso se retiró después, ver "Se eliminó el número de Liquidación manual" más abajo: Liquidación ahora usa esta MISMA secuencia OP/XXXX, como los demás tipos.
- **`no_liquidacion` en `account.payment`/`account.move`**: era un `Integer` que buscaba la Orden de Pago por coincidencia de número (`_onchange_no_liquidacion()`/overrides de `create()`/`write()`) — ahora es un **Many2one real** a `account.payment.order` (`domain=[('tipo','=','liquidacion')]`), sin esos overrides. `payment_order_id` (el otro campo de trazabilidad) no cambió.
- **Seguridad**: las 3 `ir.rule` de la vieja Solicitud (propia/aprobador/compañía) se reemplazaron por versiones que filtran `('tipo', '=', 'anticipo')` explícitamente (`account_payment_order_own_rule`/`_approver_rule`, más una nueva `account_payment_order_global_company_rule`) — sin ese filtro, un `base.group_user` cualquiera habría ganado visibilidad sobre Liquidación/Pago Directo, que nunca tuvo antes. Verificado con un script real: un usuario base puede crear/ver sus propios `tipo='anticipo'`, y un `AccessError` real le impide crear `tipo='pago_directo'`.
- Menú único "Órdenes de Pago" (`action_account_payment_order`) en Community y Enterprise — el menú/acción separado de "Solicitudes de Pago" se retiró.

**Todo lo demás documentado en el resto de esta sección sigue siendo cierto en sustancia** (el mecanismo de sync RPC, la resolución de empleado vía `employee_enterprise_ref`, el respaldo de compañía, el bug de `work_contact_id`, el bug de `puesto`/`departamento` heredados en el Contacto, el bug de `InvalidDomainError`) — solo cambió DÓNDE vive ese código (`account_payment_order.py` en vez del archivo eliminado) y el vocabulario de `state` (español, no inglés). Las menciones a "la Solicitud"/`account.payment.order.request` de aquí en adelante son narrativa histórica de cómo se llegó a este diseño, no una descripción de un modelo separado que siga existiendo.

## Refinamiento de UX inmediatamente posterior: `anticipo_viaticos`, sin catálogo de Tipo de Gasto, un solo campo de contacto

Nada más terminar la fusión de arriba, revisándola, el usuario pidió simplificar más - la separación "Tipo de Gasto" (catálogo) + "Empleado Solicitante" + "Nombre" duplicaba información y no reflejaba bien la intención real. Cambios, todos aplicados sobre el `account.payment.order` ya fusionado (nada de esto vuelve a tocar Liquidación/Pago Directo salvo lo explícitamente indicado):

- **Nuevo valor de `tipo`: `anticipo_viaticos`**, reemplazando por completo al catálogo `account.payment.order.justification.type` (modelo, menú "Tipos de Gasto", seed "Viáticos" y sus filas de `ir.model.access.csv` - **eliminados los cuatro**, decisión explícita del usuario: "eliminar todo por completo"). `justificacion_tipo_id`/`es_viaticos` desaparecieron del modelo y de la línea. Confirmado con el usuario: **`anticipo` normal y `anticipo_viaticos` comparten EXACTAMENTE el mismo flujo** (enviar/aprobar/aplicar) - no hay dos caminos distintos, solo dos etiquetas para el mismo mecanismo (constante `ANTICIPO_TIPOS` en `account_payment_order.py`, usada en absolutamente todos los guards que antes decían `tipo != 'anticipo'`). La pestaña "Viáticos" ahora se muestra con `invisible="tipo != 'anticipo_viaticos'"` directo (ya no hace falta el compute `es_viaticos` intermedio).
- **`employee_partner_id` (encabezado) se fusionó dentro de `partner_id`** - eran dos campos de contacto para la misma persona ("que no esté dos veces la persona que está solicitando"). `partner_id` ahora hace las dos funciones: para Liquidación/Pago Directo/Anticipo normal sigue siendo el contacto/proveedor de siempre, sin restricción; para `anticipo_viaticos`, la vista le agrega `domain="[('employee', '=', True)] if tipo == 'anticipo_viaticos' else []"` y `readonly="tipo == 'anticipo_viaticos'"` (el anti-suplantación de `write()` también se acotó a ese `tipo` específicamente, para no restringir de más a Liquidación/Pago Directo, que nunca tuvieron esa restricción). La línea de viáticos (`account.payment.order.viatico.line`) **mantiene su propio `employee_partner_id`** sin cambios - es un concepto distinto (el técnico de ESE renglón, no quién solicita el encabezado).
- **`requested_by_name` ("Nombre") se sacó de la vista** (seguía siendo redundante con `partner_id.name` una vez fusionado el campo de arriba) - el campo sigue existiendo en el modelo solo por compatibilidad con `_prepare_sync_vals()`, ya no se le pide nada al usuario.
- **`request_date` se eliminó del modelo por completo** ("nos quedamos solo con fecha") - `fecha` (el campo que ya usan Liquidación/Pago Directo) es ahora también la única fecha para Anticipo/Anticipo Viáticos. `_prepare_sync_vals()` envía `'fecha'` en vez de `'request_date'`.
- **En Community, ocultos**: `cuenta_anticipo_id`, `payment_method_line_id` (y su auxiliar `available_payment_method_line_ids`), y toda la sección "Facturas" - los tres con `invisible="not es_procesador"` (el compute que ya existía para gatear Aprobar/Rechazar). Como Community y Enterprise son bases de datos **separadas**, en la práctica Community nunca crea ni recibe registros `tipo` distinto a `anticipo_viaticos` - por eso no hizo falta ningún filtro de lista/búsqueda adicional para que "solo se vea Anticipo Viáticos ahí", es una consecuencia natural de la separación de bases, no algo que haya que forzar en código.
- **La pestaña Viáticos** (única visible en Community, junto con Sincronización) muestra ahora solo `employee_partner_id`/`departamento`/`puesto`/`cantidad`/`costo_individual`/`total` - se quitó la columna `justificacion_tipo_id` de la línea.
- **`journal_id`**: el domain condicional a solo bancos (`[('type','=','bank')] if tipo == 'anticipo_viaticos' else []`) se acotó específicamente a `anticipo_viaticos` (un Anticipo normal, creado a mano en Enterprise, puede seguir usando cualquier diario, igual que siempre) - y también se oculta en Community (`invisible="not es_procesador"`), ya que ahí el diario lo define el contable en Enterprise después de Aprobar, no el técnico al capturar.
- Verificado con un script end-to-end nuevo (creación sin tipo de gasto, sync, recepción, aprobar, llenar campos y aplicar, más un Anticipo normal pasando por el mismo enviar/aprobar/aplicar, más confirmar que el modelo del catálogo viejo ya no existe en el registro).

## Fase 1 del proyecto: tipos configurables por compañía, `anticipo_id` sin liquidar, reglas de Pago Directo

Inmediatamente después del refinamiento de UX de arriba, el usuario pidió tres cosas más para esta "primera fase" (Community solo ve Viáticos; el resto vive en Enterprise, pero de forma configurable, no hardcoded a `payment_order_role`):

- **Qué `tipo` se puede CREAR a mano es configurable por compañía**, cuatro Boolean nuevos en `res.company` (`payment_order_habilitar_anticipo`/`_anticipo_viaticos`/`_liquidacion`/`_pago_directo`, todos `default=True` para no cambiar el comportamiento de una Enterprise ya instalada al actualizar el módulo — **hay que ir a Ajustes y desmarcar a mano** los tres que no sean Anticipo Viáticos en la compañía de Community después de este despliegue; no se migran datos automáticamente, mismo criterio que la fusión Solicitud+Anticipo). `res.company._get_payment_order_allowed_tipos()` calcula el subconjunto habilitado. **`AccountPaymentOrder.fields_get()` filtra las opciones del Selection `tipo`** con ese subconjunto — deliberadamente **solo afecta lo que el desplegable del formulario ofrece elegir**, nunca `create()`/`write()` (verificado con un script: con Community-like config, `create({'tipo': 'pago_directo', ...})` sigue funcionando perfectamente aunque esa opción no aparezca en el desplegable) — necesario porque la sincronización (crea `anticipo_viaticos` en Enterprise) y `action_registrar_liquidacion()` (crea `tipo='liquidacion'`) deben poder seguir funcionando sin importar esta configuración. Si se necesitara alguna vez una restricción real a nivel de datos, habría que resolver primero cómo distinguir esas dos rutas internas de una creación manual por un usuario (ver el propio docstring de `fields_get()`).
- **`anticipo_id` (en una Liquidación) ahora solo lista Anticipos sin liquidar**: nuevo campo auxiliar `anticipos_disponibles_ids` (Many2many compute, mismo patrón que `available_payment_method_line_ids` — un domain string no puede expresar una subquery "sin Liquidación registrada" directamente), referenciado como `domain="[('id', 'in', anticipos_disponibles_ids)]"`. Incluye siempre el propio `anticipo_id` actual del registro (para que no desaparezca del desplegable si deja de calificar después de haberlo elegido). **`anticipo_id` dejó de ser `readonly="1"` fijo** — ahora es `readonly="state != 'borrador'"`, editable a mano en borrador (sigue llenándose automático vía el botón "Registrar Liquidación", pero ya no es la única forma). **Trampa real al probar esto en `odoo-bin shell` con `.new()`**: Odoo envuelve los ids reales de un x2many en un registro sin guardar como `NewId(origin=<id real>)` — comparar con `in` directo contra el recordset real da un falso negativo aunque el cálculo interno sea correcto (confirmado con un log de traza dentro del propio compute). Hay que comparar por `origin`, no por `in`. Esto es un artefacto exclusivo de `.new()` — el cliente web real nunca ve el wrapper NewId (la respuesta de onchange serializa ids planos), así que no afecta el uso real.
- **Pago Directo: factura obligatoria, monto exacto sin escape** — `action_conciliar()` ahora exige `factura_ids` no vacío para `tipo == 'pago_directo'` (antes de netear nada), y si el neteo no da exactamente cero, **ya no acepta `cuenta_ajuste_id` como escape** (a diferencia de Liquidación, que sigue permitiéndolo sin cambios — la diferencia parcial ES el caso de uso de Liquidación). Refleja la regla de negocio explicada por el usuario en esta misma sesión: Pago Directo = el anticipo/pago cubre el 100% de la factura; si no cubre el 100%, es una Liquidación, no un Pago Directo.
- Verificado end-to-end con un script nuevo (`fields_get()` filtrado en modo Community-like y Enterprise-like + que `create()` interno sigue sin bloquearse; `anticipo_id` excluye uno ya liquidado e incluye uno aplicado sin liquidar; Pago Directo sin factura bloqueado, con factura pero monto distinto bloqueado aunque tenga `cuenta_ajuste_id`, con monto exacto concilia; regresión de Liquidación con diferencia + `cuenta_ajuste_id` sigue funcionando sin cambios) y con `-u` sobre la base de prueba ya instalada (upgrade limpio, sin errores).

### Bug real: `tipo` seguía por defecto en `anticipo` fijo, invisible en el propio desplegable filtrado de Community

Reportado por el usuario: en Community, un registro nuevo no mostraba Viáticos/Pagos/Facturas - el campo `tipo` se veía "vacío". Causa: `fields_get()` (arriba) filtra las OPCIONES del desplegable según la compañía, pero el `default=` del campo seguía hardcodeado a `'anticipo'` - en Community (solo `anticipo_viaticos` habilitado), un registro nuevo arrancaba con `tipo='anticipo'` internamente, un valor que ni siquiera aparece en su propio desplegable ya filtrado, así que el widget lo mostraba en blanco - y como el valor real NO era `'anticipo_viaticos'`, todas las condiciones `invisible="tipo != 'anticipo_viaticos'"` (la pestaña Viáticos) ocultaban todo, tal como se reportó.

**El fix**: `default=lambda self: (self.env.company._get_payment_order_allowed_tipos() or ['anticipo'])[0]` - el primer tipo habilitado para la compañía actual, no un valor fijo. En Community (`anticipo_viaticos` como único habilitado) el nuevo registro ahora arranca correctamente en `anticipo_viaticos`; en Enterprise (los 4 habilitados) sigue arrancando en `anticipo`, sin regresión. Verificado con `.new({})` y `create({})` sin especificar `tipo` en ambos escenarios de compañía.

**De paso, otro ajuste relacionado**: la sección "Pagos/Cheques" (ver `action_crear_pago()` más abajo) había quedado visible sin importar la compañía tras agregarle el botón "Crear Pago" - correcto para Enterprise, pero Community nunca debe ver esa sección (igual que Facturas). Se corrigió a `invisible="not es_procesador"` en el div/campo/botón, mismo criterio que ya usa Facturas.

### Solicitante vs. Procesador — one field, same module both places

`res.company.payment_order_role` (`solicitante`/`procesador`, **default `procesador`** — an already-installed Enterprise database keeps behaving exactly as before after upgrading this module) is the only thing that distinguishes the two roles, and it only affects **one thing**: whether `action_approve()` on a request actually pushes a copy to another instance (`_sync_to_enterprise()` is a no-op unless `payment_order_role == 'solicitante' and payment_order_sync_enabled`). Everything else — menus, buttons, security groups — is identical in both editions; visibility is controlled by security groups (`group_payment_order_approver`, `account.group_account_invoice`), not by conditionally hiding UI based on the company role field. Don't add role-based `invisible=` conditions to menus/views for this — it was a deliberate simplification (fragile and unnecessary: an instance simply won't have anyone in the accounting groups if it's meant to be Solicitante-only, and "Crear Anticipo" being technically reachable but pointless on a pure-Solicitante instance is harmless).

### Sync mechanism — same JSON-RPC pattern as `construtec_materials_19`/`construtec_materials_sync_19`, but self-contained

`tools/enterprise_sync_api.py` is a **deliberate small copy** (not a shared dependency) of the proven helper in `construtec_materials_19` (Odoo19C): push via Odoo's own built-in `/jsonrpc` (`common.authenticate` + `object.execute_kw(...).create(...)`), `requests` library, never blocks the action that triggers it (`EnterpriseSyncError` caught, `sync_state`/`sync_error` recorded, retry every 30 min via `ir_cron_payment_order_sync_retry` + manual `action_retry_sync()`). **Why a copy and not a shared library**: each integration keeps its own URL/credentials/log, so revoking one API Key can't affect the other; this module also needed to avoid depending on `construtec_materials_19` (a Community-only module in spirit, even though nothing stops it installing elsewhere) just to reuse ~90 lines.

Because **both sides are literally the same model** (`account.payment.order`, same module installed on both instances) — unlike materials' mirror-into-a-different-model design — `_prepare_sync_vals()` still sends **plain values only, no ids** (`origin`/`external_ref`/Char/Date/Float), because `res.company`/`res.users` ids from one database mean nothing in the other even though the schema is identical. The receiving `create()` lands the record with `origin='synced'`, `state='approved'` directly — it does **not** go through this instance's own `action_submit()`/`action_approve()` again (already approved where it came from).

**Provisioning the integration user** (Procesador side): create a dedicated user in **only** `group_payment_order_sync_integration` (create-only on `account.payment.order` — `perm_read=perm_write=perm_unlink=0`, see `security/ir.model.access.csv`) — do **not** also add `base.group_user` or any broader group to it, or it inherits whatever else those imply. Generate its API Key from Ajustes > Mi Perfil > Seguridad de la cuenta, put the URL/db/login/key in Ajustes > Facturación > Solicitudes de Pago on the **Solicitante** instance (that's where `payment_order_role='solicitante'` and the sync fields actually get used).

### Aprobación por monto: Nivel Medio / Nivel Alto (`group_payment_order_approver_medio`/`_alto`)

Pedido explícito del usuario, basado en el formulario en papel adjuntado (`Solicitud de Pago - Auner Calderon.pdf`): ese PDF trae 2 columnas de autorización - "Autorización 1 (montos menores a Q2500.00)" firmada por "Jefe de Área"/"Project Manager", y "Autorización 2 (montos mayores a Q2500.00)" firmada por "Gerente de Área"/"Gerencia Comercial". **No se agregaron estados nuevos al `state` field** (decisión explícita: "igual que ahora, solo cambia QUIEN aprueba") - el flujo `draft → submitted → approved/rejected/cancel` sigue idéntico; lo único nuevo es que `action_approve()` ahora exige un grupo distinto según el monto.

**Por qué NO se portó `construtec_roles_permisos_19`** (el módulo de roles de Odoo19C que el usuario recordaba y preguntó explícitamente si convenía traer a Enterprise): investigado a fondo antes de decidir - ese módulo depende directamente de `construtec_helpdesk_mgmt` (`"depends": ["base", "construtec_helpdesk_mgmt"]`, Community-only) y su `security/construtec_roles_security.xml` referencia 3 grupos de helpdesk (`group_helpdesk_user_own`/`_team`, `group_helpdesk_manager`) dentro de sus propios `implied_ids`. **No instala en Enterprise tal cual** - fallaría por dependencia faltante, y aunque se sorteara eso, tronaría por external ID no resuelto en esas 3 referencias. Como el usuario solo necesita esto para Solicitudes de Pago por ahora, se siguió el mismo criterio ya documentado arriba para `group_payment_order_approver` (self-contained, no depende de nada externo a este módulo) en vez de intentar portar/adaptar ese módulo de Community.

**Jerarquía de grupos** (`security/payment_order_request_security.xml`): `group_payment_order_approver_alto` implica `group_payment_order_approver_medio` implica `group_payment_order_approver` (el grupo genérico ya existente, que a su vez implica `base.group_user`) - así que un usuario Nivel Alto automáticamente tiene todo lo que Nivel Medio y el grupo base ya otorgan (visibilidad vía `account_payment_order_request_approver_rule`, acceso al campo `employee_id` sin bloqueo, etc.), sin tener que listarlo aparte en cada `ir.rule`/vista.

**El umbral es configurable, no fijo** (pedido explícito): `res.company.payment_order_approval_threshold` (`Monetary`, default `2500.0` - el valor del PDF), expuesto en Ajustes > Facturación > "Aprobación por Monto". `_check_is_approver_for_amount()` (llamado por registro dentro de `action_approve()`, ya que el monto varía por Solicitud) compara `self.total_acreditar` contra `self.company_id.payment_order_approval_threshold`:
- `total_acreditar >= threshold` → exige `group_payment_order_approver_alto` (Gerente de Área).
- `total_acreditar < threshold` → exige `group_payment_order_approver_medio` (que Alto también tiene, por la implicación de arriba) - Jefe de Área.

`action_reject()` sigue usando el `_check_is_approver()` genérico (sin distinción por monto) - el usuario no pidió que el rechazo también fuera escalonado por nivel, solo la aprobación.

**Que se vea como una app nativa en Ajustes > Usuarios** (pedido explícito: "quisiera que en la pantalla del usuario estos permisos salieran como las aplicaciones nativas de Odoo... así como Contabilidad, uno le da clic y tiene varios niveles"): en Odoo 19, `res.groups` **ya no tiene `category_id`** (se quitó del modelo) - el mecanismo correcto es `res.groups.privilege`, confirmado leyendo `..\odoo\addons\base\models\res_groups_privilege.py` y el ejemplo real ya existente en este workspace (`construtec_roles_permisos_19/security/construtec_roles_security.xml`, que ya usa exactamente este patrón para su escalera de 4 roles). Sin esto, los grupos se ven como casillas sueltas en "Otros permisos", no como el selector limpio de un renglón por app.

- `ir.module.category` nuevo (`module_construtec_payment_order_category`, "Solicitudes de Pago") - es el renglón que aparece en la grilla de Usuarios, igual que "Contabilidad"/"Ventas".
- `res.groups.privilege` nuevo (`payment_order_approval_privilege`, "Nivel de Aprobación") con `category_id` apuntando a esa categoría - es la "columna" dentro del renglón.
- **Solo** `group_payment_order_approver_medio`/`_alto` tienen `privilege_id` seteado a ese privilegio (por eso se les acortó el `name` a "Nivel Medio (Jefe de Área)"/"Nivel Alto (Gerente de Área)" - el nombre de la categoría ya da el contexto "Solicitudes de Pago", repetirlo en cada nivel sería redundante, igual que "Contabilidad" no dice "Contabilidad: Facturación"). `group_payment_order_approver` (el genérico/base) **deliberadamente no tiene `privilege_id`** - sigue existiendo solo como grupo implícito interno, no aparece como un tercer nivel seleccionable confuso.
- Odoo ordena los niveles dentro del privilegio por profundidad de `implied_ids` (cuántos otros grupos del mismo privilegio implica) - como Alto implica Medio, se renderiza como el nivel más alto automáticamente, sin necesidad de un campo de orden manual.

### Cambio de arquitectura: la aprobación ahora ocurre en Enterprise, no en Community

Decisión explícita del usuario tras probar el flujo real de punta a punta (viendo el botón "Crear Anticipo" aparecer en Community, donde no tiene ningún sentido, y notando que `employee_id` llegaba vacío a Enterprise): **"considero que, una vez que el técnico envíe [la solicitud], las etapas de aprobación estén en Enterprise, porque allá están los usuarios administrativos. Y que en Community solo se vea como enviado."** Esto invierte el diseño original de esta sesión (Community aprobaba localmente y sincronizaba ya aprobada) - ahora:

- **El sync se dispara en `action_submit()`, no en `action_approve()`** - `_prepare_sync_vals()` ahora envía `'state': 'submitted'` (antes `'approved'`). En una instalación Procesadora, `action_submit()` sigue llamando a `_sync_to_enterprise()` pero es un no-op inofensivo (el guard interno ya existente: `company.payment_order_role != 'solicitante'` → `continue`).
- **La Solicitud sincronizada llega a Enterprise en `state='submitted'`**, no `'approved'` - a partir de ahí sigue el flujo NORMAL de Enterprise (sus propios usuarios Nivel Medio/Alto le dan clic a "Aprobar" como si fuera una solicitud creada ahí mismo). No hizo falta ningún código especial para esto - el `create()` genérico solo pone el estado que le llega, y una vez creada en `submitted`, `action_approve()`/`action_reject()` funcionan exactamente igual que para cualquier registro local de Enterprise.
- **Los botones Aprobar/Rechazar/Crear Anticipo ahora se ocultan por completo en una instalación Solicitante** (`es_procesador`, campo compute nuevo que resuelve `company_id.payment_order_role == 'procesador'` - una vista NO puede navegar `company_id.payment_order_role` directo dentro de una expresión `invisible=`, hace falta este auxiliar, mismo patrón que `es_viaticos`). En Community, la Solicitud simplemente se queda visualmente en "Enviada" para siempre desde el punto de vista de esa base - lo que pase después (aprobación, rechazo, Anticipo) ocurre en la copia de Enterprise, y **no hay sincronización de vuelta** (Enterprise → Community) del estado final; no se pidió y queda fuera de alcance de esta pasada. Si se necesita a futuro, sería un mecanismo nuevo simétrico al que ya existe (Community → Enterprise), no algo que ya esté construido.
- El bloque "Aprobación por Monto" en Ajustes también se ocultó para instalaciones Solicitante (`payment_order_role != 'procesador'`) - el umbral solo importa donde realmente se aprueba.

### `employee_enterprise_ref`: resolver el empleado real en Enterprise al sincronizar

Bug real encontrado por el usuario probando el flujo: en la copia de Enterprise de una Solicitud sincronizada, el campo "Empleado Solicitante" y la columna "Empleado" de cada línea llegaban **vacíos** - solo los campos de texto (`puesto`/`departamento`/`tecnico_name`) llegaban bien. Esto era **el comportamiento esperado del diseño original** (`employee_id` es local a cada base, nunca viaja) pero resultó insuficiente en la práctica: el usuario quiere que la Solicitud, ya en Enterprise, quede vinculada al `hr.employee` **real** de allá, no solo a su nombre en texto.

**La solución reutiliza algo que ya existía**: cuando Community sincroniza su directorio de empleados (`res.company._sync_employees_from_enterprise()`), cada `hr.employee` mirror ya guarda `enterprise_employee_ref` = el id **original** de ese empleado en Enterprise. Este es el único id en todo este módulo que es genuinamente válido en ambas bases (viene literalmente de allá) - así que ahora viaja también, tanto en el encabezado como en cada línea:

- `_prepare_sync_vals()` agrega `employee_enterprise_ref: self.employee_id.enterprise_employee_ref` (encabezado) y lo mismo por línea.
- `AccountPaymentOrderRequest._resolve_employee_enterprise_ref()`/la lógica equivalente en `.line.create()` hacen `self.env['hr.employee'].browse(int(ref)).exists()` - una búsqueda directa por id, no por nombre (a diferencia de `justificacion_tipo_name`/`analytic_account`, que sí se resuelven por nombre porque no hay ninguna referencia cruzada previa para esos catálogos). Desde el rediseño "Contacto como fachada" (ver sección siguiente), esto resuelve hacia `employee_partner_id` (`employee.work_contact_id.id`), no directo a `employee_id` - `employee_id` es ahora un campo calculado.
- Si el empleado se resuelve, **también** se usa `employee.company_id` para `company_id` del encabezado - más preciso que cualquier respaldo manual, porque es la compañía real de esa persona.

### Multi-compañía: `payment_order_default_company_id` como respaldo cuando no hay empleado resoluble

Consideración nueva del usuario: Enterprise puede tener varias compañías, con empleados contratados en cada una - si `employee_enterprise_ref` no resuelve (empleado todavía no sincronizado, por ejemplo), la Solicitud no debe caer en cualquier compañía por accidente (rompería reglas multi-compañía en otros lados de Enterprise).

- **Nuevo modelo espejo** `account.payment.order.enterprise.company` (`name`, `enterprise_company_ref`) - mismo patrón que empleados/cuentas analíticas: `tools/enterprise_sync_api.fetch_companies()` (`search_read` sobre `res.company`, solo `name` - nada sensible) + `res.company._sync_enterprise_companies()`, sumado al mismo cron/botón "Sincronizar ahora" que ya jala empleados y cuentas analíticas.
- **`res.company.payment_order_default_company_id`** (Many2one a ese espejo, expuesto en Ajustes > Facturación > Sincronización de Empleados como un desplegable poblado por el propio sync - nunca se escribe a mano el nombre de la compañía, precisamente para evitar errores de tipeo). Pedido explícito: "que me liste qué empresas están" en vez de escribir el nombre a mano.
- `_prepare_sync_vals()` también envía `company_enterprise_ref` (el `enterprise_company_ref` de esta compañía por defecto) - se usa en el receptor **solo si** `employee_enterprise_ref` no resolvió nada (`_resolve_company_enterprise_ref()`, después de `_resolve_employee_enterprise_ref()` en el orden de `create()`). Si ninguno de los dos resuelve, `company_id` cae al default normal de Odoo (`self.env.company`, la compañía del usuario de integración) - sin cambios ahí.

### "Empleado" como Contacto (`employee_partner_id`), no hr.employee directo

Observación del usuario probando el flujo completo (con `employee_enterprise_ref`/multi-compañía ya construidos): **"considero que es mejor que [el campo de empleado] esté relacionado al campo de contactos... esto para no pelear con la regla de multiempresa de empleados, tanto en community como en enterprise."** El problema real: `hr.employee` trae su propia regla de multi-compañía (un usuario normalmente solo ve empleados de las compañías que tiene permitidas) - un picker Many2one directo a `hr.employee` en el formulario de la Solicitud puede quedar vacío/restringido para un usuario que sí debería poder elegir un empleado de otra compañía. `res.partner` (Contactos) no tiene esa restricción.

**Diseño acordado ("Contacto como fachada, empleado por debajo")**: el campo que el usuario ve y elige sigue llamándose "Empleado" en la UI, pero es un Many2one a `res.partner`, no a `hr.employee`. El `hr.employee` real se resuelve por debajo, automáticamente, sin que el usuario tenga que saberlo:

- **`employee_partner_id`** (Many2one `res.partner`, en encabezado y línea) - el campo que el usuario ve/elige. Dominio `[('employee', '=', True)]`, usando el campo **nativo** de Odoo `res.partner.employee` (`Boolean`, `compute` + `store=True`, definido en `..\odoo\addons\hr\models\res_partner.py`) - no hizo falta inventar un campo propio: Odoo ya calcula y guarda si un contacto tiene al menos un `hr.employee` vinculado, y al ser un campo plano guardado en `res.partner`, filtrarlo NO dispara la regla de multi-compañía de `hr.employee` (esa regla solo aplica al leer/buscar `hr.employee` directamente).
- **`employee_id`** (Many2one `hr.employee`, en encabezado y línea) - pasó de ser el campo que el usuario llenaba a ser un campo **calculado** (`compute='_compute_employee_id', store=True, readonly=True`), resuelto por `_resolve_employee_for_partner(partner, company)` (función a nivel de módulo, compartida entre encabezado y línea). Todo lo que ya existía y leía de `employee_id` (banco/teléfono/correo en el onchange y en `create()`, `employee_enterprise_ref` en `_prepare_sync_vals()`, el gate de `action_submit()` que exige empleado en cada línea) **sigue funcionando sin cambios** - solo cambió de dónde sale el valor.
- **Desempate cuando un contacto tiene `hr.employee` en más de una compañía** (contratado en varias empresas - el mismo escenario de multi-compañía ya cubierto por `payment_order_default_company_id`): se usa `partner.sudo().employee_ids` (también nativo, `One2many('hr.employee', 'work_contact_id')`) y se prefiere el que coincide con la compañía de la Solicitud/línea (`company_id` del encabezado, `request_id.company_id` en la línea); si ninguno coincide, cae al primero activo. Decisión explícita del usuario, confirmada antes de implementar.
- **`_resolve_employee_enterprise_ref()`** (recepción sincronizada) ahora resuelve hacia `employee_partner_id = employee.work_contact_id.id` (no hacia `employee_id` directo, que ya no acepta escritura útil por ser calculado) - y como también fija `company_id = employee.company_id.id`, el compute de `employee_id` vuelve a resolver exactamente al mismo `hr.employee` de origen (el desempate por compañía coincide con la compañía real de ese empleado).
- **`write()`**: el candado antisuplantación ahora protege `employee_partner_id` (el campo que el usuario real controla) y, por defensa en profundidad, también `employee_id` directo - ningún usuario sin el grupo aprobador puede cambiar el empleado de una Solicitud ya creada, sea cual sea el campo que intente escribir.
- **Trampa real encontrada verificando esto**: vincular `user_id` a un `hr.employee` dispara el mismo mecanismo núcleo de Odoo ya documentado arriba (`_sync_user()`/`_remove_work_contact_id()`) que **reemplaza `work_contact_id`** por el partner propio del usuario recién vinculado - es decir, el "Contacto" detrás de un empleado puede cambiar de identidad (no solo perder campos) en cuanto se le crea login. Esto no rompe nada porque `employee_ids` (la relación inversa) se recalcula junto con el swap - el contacto nuevo pasa a resolver correctamente hacia ese mismo empleado - pero si se arma una prueba con dos empleados compartiendo un contacto a propósito, hay que vincular `user_id` **antes** de fijar ese contacto compartido, no después (ver `verify_partner_facade.py` - un primer intento de esa prueba falló exactamente por este orden).

### `puesto`/`departamento`: heredados en el Contacto, no resueltos en vivo por Solicitud

Bug reportado por el usuario probando el rediseño "Contacto como fachada" de arriba: al elegir un Contacto en una Solicitud, `puesto`/`departamento` quedaban vacíos. Causa real (confirmada con `debug_puesto_depto.py` antes de tocar nada): la lógica SÍ resolvía bien cuando el `hr.employee` de la compañía de la Solicitud tenía `job_title`/`department_id` cargados - el vacío ocurría cuando el desempate por compañía (`_resolve_employee_for_partner`) no encontraba ningún `hr.employee` en la compañía específica de esa Solicitud (Enterprise real: varias compañías, el mismo contacto empleado en una de ellas nada más).

Decisión del usuario tras plantear la disyuntiva (¿un valor por contacto, o seguir resolviendo en vivo por compañía?): **un solo valor por Contacto** - la mayoría de contactos solo tiene un empleo, y quiere que "se hereden automático cuando se cree el empleado y se vincule el contacto", pensando ya en una relación empresa-a-empresa (varias compañías en Enterprise), no solo Community-Enterprise.

- **`res_partner.py`** (nuevo): `employee_department_id` (Many2one `hr.department`) y `employee_job_title` (Char), ambos `compute` + `store=True` + `compute_sudo=True` en `res.partner`, `@api.depends('employee_ids.department_id', 'employee_ids.job_title', 'employee_ids.company_id')` - se recalculan solos en cuanto se crea/edita/vincula el `hr.employee`, sin ningún cron ni acción manual. Reutilizan `_resolve_employee_for_partner()` (la misma función de `account_payment_order_request.py`) con `self.env.company` como criterio de compañía (no hay una Solicitud de por medio a este nivel) - incluidos ahí porque es lógica de dominio de este módulo, no algo que deba vivir en el core de `hr`.
- **Encabezado y línea** (`_onchange_employee_partner_id`, `_fill_derived_vals_from_employee`, `Line.create()`): `puesto`/`departamento` ahora se leen directo de `employee_partner_id.employee_job_title`/`.employee_department_id.name` - **ya no** dependen de que `_resolve_employee_for_partner` encuentre un `hr.employee` en la compañía exacta de esa Solicitud. El resto (banco/teléfono/correo/`employee_enterprise_ref`/`tecnico_name`) sigue exactamente igual, resuelto en vivo vía `_resolve_employee_for_partner` - esos sí varían legítimamente por compañía (o solo importan para la compañía de esa Solicitud puntual), a diferencia de puesto/departamento.
- **No hace falta ningún script ni sincronización nueva** (pregunta real del usuario después de implementar esto) - confirmado con `verify_partner_job_sync.py`:
  - **Empleados ya existentes en Enterprise antes de esta migración**: Odoo recalcula solo, para TODOS los registros existentes, cualquier campo `compute` + `store=True` recién agregado - es el comportamiento estándar del ORM al correr `-u`, no algo que haya que programar aparte.
  - **La sincronización Community↔Enterprise no necesitó ningún cambio**: `department_id`/`job_title` ya viajaban de Enterprise a Community desde antes, como parte del pull periódico de empleados que ya existía (`_sync_employees_from_enterprise`/`fetch_employees`). El `write()` que ese pull hace sobre el `hr.employee` espejo de Community dispara el `_compute_employee_job_info` de `res_partner.py` **localmente en la base de Community** (mismo código, mismo módulo instalado en ambos lados) - el dato no necesita viajar dos veces, solo se recalcula donde ya llegó.
- **Vista** (`views/res_partner_views.xml`, nuevo): `employee_department_id` se agregó a la ficha del Contacto (`base.view_partner_form`, junto al campo nativo `function`), `readonly="1"` e `invisible="not employee"` - pedido explícito del usuario: "¿Dónde veo el departamento y puesto? En la ficha del contacto que pertenece el empleado."
- **Corrección posterior del usuario - `function` no es un campo nuevo, es el nativo "Job Position"**: la primera versión de esto creó `employee_job_title` (Char) en vez de reusar `res.partner.function` (`base`, ya existente, disponible en Community y Enterprise por igual - lo usa cualquier contacto para su puesto, sea empleado o no). Se corrigió: `function` se **redeclara** en `res_partner.py` con `compute='_compute_employee_job_info', compute_sudo=True, store=True, readonly=False` - mismo patrón exacto que usa el propio Odoo en `crm.lead.function` (`..\odoo\addons\crm\models\crm_lead.py`, `_compute_function()`): `if not partner.function or employee.job_title: partner.function = employee.job_title or partner.function`. Esto es **deliberadamente autoreferencial** (lee y escribe el mismo campo dentro de su propio compute) - no es un error, es el idioma sancionado por Odoo para "compute que cede a un valor manual cuando no tiene nada nuevo que aportar". Como resultado: **nunca pisa el `function` de un contacto que no es empleado** (su `employee_ids` nunca cambia, el compute jamás se dispara para él), y si un contacto luego SÍ se vincula a un `hr.employee` real, `function` pasa a reflejar el puesto de RR.HH. desde ese momento (verificado con `verify_partner_job_info.py`, casos 7 y 8 - un contacto no-empleado con `function='CEO'` puesto a mano conserva su valor; el mismo contacto, tras vincularse a un `hr.employee`, actualiza `function` al puesto real).

### Directorio de Empleados: pull automático desde Enterprise (Solicitante-only)

**Dirección invertida respecto a los demás syncs de este módulo**: aquí Community *jala* (pull) datos de Enterprise, en vez de empujar (push) hacia allá. Motivo explícito del usuario: los empleados **solo se crean en Enterprise** (via `construtec_hr_employee_19`/`construtec_hr_payroll_19`), nunca en Community — este mecanismo únicamente le da a Community una copia de referencia (nombre/departamento/puesto) para poder crear manualmente cuentas `res.users` de esos empleados ahí.

- **`tools/enterprise_sync_api.fetch_employees()`**: `search_read` sobre `hr.employee` en Enterprise pidiendo `name`, `department_id`, `job_title`, `bank_account_ids`, `work_phone`, `private_phone` — nunca el registro completo, aunque las credenciales usadas puedan técnicamente leer más. `department_id`/`job_title` son campos de **`hr.version`** en Odoo 19 (no de `hr.employee` directamente — ver `construtec_hr_employee_19/CLAUDE.md`), pero se leen igual como `employee.department_id`/`employee.job_title` gracias a la delegación de `hr.version` sobre `hr.employee`; verificado leyendo `..\odoo\addons\hr\models\hr_version.py` directamente, no asumido. **Ese mismo `version_id` requiere el grupo "Employees Officer" (`hr.group_hr_user`) para leerse** — un `base.group_user` normal en Community, sin ese grupo, obtiene `AccessError` al leer `job_title`/`department_id` directo; todo el código de este módulo que los lee para un solicitante cualquiera usa `.sudo()` explícitamente (ver `_onchange_employee_id()`/`_fill_derived_vals_from_employee()` en `account_payment_order_request.py`) — confirmado con un test real, no asumido.
- **Decisión explícita del usuario: sin cambios en Enterprise para esto.** Lo correcto en seguridad hubiera sido un modelo/vista de solo-lectura dedicado en Enterprise para no exponer el `hr.employee` completo (salario, banco, DPI, etc.) ante una fuga de credenciales — el usuario reconoció el riesgo y decidió aceptarlo por ahora, reusando las **mismas credenciales de administrador** ya configuradas para el push de Solicitudes de Pago (`payment_order_sync_url/db/login/api_key`). Si esto cambia más adelante, ese modelo de solo-lectura en Enterprise es el primer paso a re-proponer.
- **`hr.employee.enterprise_employee_ref`** (`models/hr_employee.py`, campo nuevo vía `_inherit`): guarda el id del empleado en Enterprise, usado *solo* para no duplicar en cada sincronización — no editable, sin significado fuera de este mecanismo.
- **`res.company._sync_employees_from_enterprise()`**: no-op si `payment_order_role != 'solicitante'` o la sincronización no está habilitada (mismo patrón que el resto). Busca-o-crea `hr.department` por nombre (nunca por id — bases independientes), y hace upsert de `hr.employee` por `enterprise_employee_ref`.
- **Intervalo configurable** (`employee_sync_interval_number`/`_type` en `res.company`, expuesto en Ajustes): al guardar, se escribe directo sobre el único registro `ir.cron` (`ir_cron_employee_sync`) — **el cron es global, no por compañía**; si algún día hay más de una compañía Solicitante con intervalos distintos, la última que se guarde gana. Aceptable hoy porque la instancia Community es de una sola compañía; documentado aquí como limitación conocida, no resuelta.
- **`hr` se agregó a `depends`** — antes este módulo solo dependía de `account`/`mail`. `hr` ya estaba instalado en ambas ediciones antes de este cambio, así que no debería disparar ningún `to_install` en cascada al actualizar.

**Lección de despliegue de esta misma sesión, aplica igual aquí**: cualquier cambio de esquema en este módulo (campos nuevos en `res.company`/`hr.employee`, tablas nuevas) **debe aplicarse en Enterprise vía terminal** (`odoo-bin -u construtec_account_payment_order_19 --stop-after-init`), **nunca dando clic en Actualizar desde Ajustes > Aplicaciones** — ese botón dispara `ir_module.button_install()` internamente, que hace una lectura amplia de `res.company` (`company_countries = self.env['res.company'].search([]).country_id`) *antes* de que corra la migración de esquema del propio módulo, y truena con `UndefinedColumn` de forma 100% reproducible mientras el código ya está desplegado pero el esquema no. Esto causó dos incidentes reales en producción (`construtecasesores.odoo.com`) el 2026-08-18 al agregar `payment_order_role`; se resolvió cada vez revirtiendo el commit (`git revert`, nunca `reset --hard`, ver [[dos_repositorios_odoo19e_enterprise]]) y luego re-desplegando + migrando por terminal.

**Nota sobre despliegue en Docker** (`erp.construtecasesores.com`, VPS propio): `docker exec -it <contenedor> odoo -u <modulo> --stop-after-init -d <db> --no-http` (el ejecutable dentro de la imagen oficial se llama `odoo`, no `odoo-bin`; falta `--no-http` truena con `OSError: Address already in use` porque el proceso principal ya tiene el puerto 8069 ocupado dentro del mismo contenedor). Ese `docker exec` migra la base correctamente, pero es un proceso aparte del que sirve las páginas web — **el proceso principal sigue con el código/registro viejo en memoria hasta que se reinicia** (`docker restart <contenedor>`), o si no vas a ver errores tipo `"res.config.settings"."campo_nuevo" field is undefined` en el navegador aunque la migración ya haya corrido bien.

### Empleado vinculado en la Solicitud (encabezado y cada línea de Viáticos)

`employee_id` (Many2one a `hr.employee`, **local a Community**, nunca se envía como id a Enterprise) tanto en el encabezado (default: el empleado cuyo `user_id` coincide con `self.env.user`, vía el directorio ya sincronizado — ver sección anterior) como en cada `account.payment.order.line` (el empleado destino de ese renglón de viáticos — decisión explícita del usuario: la línea ya no tiene un campo de texto libre "Técnico" en la vista, `employee_id` es la única forma de indicar a quién corresponde el renglón). En ambos casos, un `@api.onchange('employee_id')` **autocompleta** campos de texto plano (`puesto`/`departamento` en el encabezado; `tecnico_name`/`puesto`/`departamento` en la línea) — esos campos de texto, no el id, son lo que viaja en `_prepare_sync_vals()` hacia Enterprise, exactamente igual que el resto de este módulo (ver "Sync mechanism" arriba: nunca ids entre bases independientes). `tecnico_name` sigue existiendo en el modelo de la línea (no required, se llena solo) pero **no está en la vista** - el usuario solo ve/elige `employee_id`; `tecnico_name` es puramente la representación en texto que viaja por RPC.

**`employee_id` de la línea NO es `required=True` a nivel de campo** (solo `required="1"` en la vista, cosmético) - a propósito: una línea sincronizada llega SOLO con `tecnico_name` en texto (Enterprise no tiene forma de mapear un `tecnico_name` de Community a uno de SUS propios `hr.employee`), así que un `required=True` real en el modelo rompería la recepción de toda solicitud sincronizada con líneas. Se exige en cambio en `action_submit()` (`rec.viaticos_line_ids.filtered(lambda l: not l.employee_id)` → `UserError`), que las líneas creadas localmente siempre atraviesan y las sincronizadas (que llegan ya `state='approved'`) nunca pasan.

**Por qué ahora mismo**: motivado por una necesidad futura en Enterprise 19 (definir qué cuentas contables afecta cada viático según departamento/puesto del empleado destino) - explícitamente **no construida todavía**, el alcance de esta pasada es solo capturar y sincronizar departamento/puesto como texto, en encabezado y en cada línea.

### Anti-suplantación: `employee_id` de solo lectura, `cuenta_acreditar`/`banco` autocompletados y bloqueados

Decisión explícita del usuario: una vez creada la Solicitud, **nadie (salvo un Aprobador) puede cambiar `employee_id`** — `write()` lo bloquea (`UserError`) si el nuevo valor difiere del ya guardado, salvo `self.env.user.has_group(APPROVER_GROUP_XMLID)`. El campo también es `readonly=True` a nivel de vista. Motivo: `cuenta_acreditar`/`banco` ahora se autocompletan desde la cuenta bancaria **real** del empleado vinculado — permitir cambiar `employee_id` después de creada la solicitud sería una forma de redirigir el pago a la cuenta de otra persona.

`cuenta_acreditar`/`banco` son `readonly=True` (a nivel de campo, es decir aplica en toda vista de formulario salvo que se sobre-escriba explícitamente) y se llenan solo vía `_onchange_employee_id()` (formulario) o `_fill_derived_vals_from_employee()` (creación por API/script, ya que el onchange no corre fuera del formulario web) desde `employee_id.cuenta_bancaria`/`employee_id.banco_nombre` — nunca editables a mano.

### Cuenta bancaria del empleado: sincronizada en lote, pero self-scoped (`hr_employee.py`)

Decisión explícita del usuario: la cuenta bancaria de **todos** los empleados se trae en el mismo pull periódico que nombre/departamento/puesto (`fetch_employees()` ahora también solicita `bank_account_ids` a `hr.employee` y hace una segunda llamada a `res.partner.bank` para `acc_number`/`bank_id`) - el usuario explícitamente prefirió esto sobre una alternativa más segura (traer en vivo, solo la cuenta propia, nunca guardar la de otros) por simplicidad de mantenimiento.

Para que esto no signifique "cualquier usuario de Community puede leer la cuenta bancaria de cualquier empleado", `hr.employee` gana 4 campos nuevos:
- `cuenta_bancaria_raw`/`banco_nombre_raw`: el dato real, `groups='hr.group_hr_manager'` - invisible a un usuario normal por **cualquier** camino (vista, `read()`/`search_read()` vía RPC), no solo oculto en pantalla.
- `cuenta_bancaria`/`banco_nombre`: campos **compute** (`compute_sudo=True`) sin restricción de grupo, pero que solo resuelven a un valor real cuando `employee.user_id == self.env.user` - para cualquier otro empleado, devuelven `False` sin importar qué permisos tenga quien pregunta. Esta es la comprobación de "self-only" real; `groups=` por sí solo no puede expresar "solo su propio registro", así que se combinan ambos mecanismos (grupo + auto-chequeo en el compute).

**Esto solo funciona de punta a punta porque `account.payment.order.employee_id` siempre es el empleado vinculado al usuario actual** (default automático + bloqueado contra cambios, ver arriba) — nunca se expone un selector que permita a un usuario elegir "ver la cuenta de fulano".

**Bug real encontrado y corregido en esta misma sesión, antes de desplegar**: sin `@api.depends_context('uid')` en el `@api.depends(...)` del compute, el caché de Odoo puede **reutilizar el valor calculado para un usuario cuando OTRO usuario distinto consulta el MISMO registro dentro de la misma transacción** (`self.env.user` no es una ruta de campo, así que `@api.depends()` normal no lo detecta como dependencia — el caché no sabe que debe invalidarse al cambiar de usuario). Se confirmó el fallo con un test real (mismo `hr.employee`, `with_user(A)` seguido de `with_user(B)` en el mismo script) antes de tener el fix, y se confirmó la corrección después - **cualquier compute self-scoped por `self.env.user` en este módulo debe llevar `@api.depends_context('uid')` además de `@api.depends(...)`**, o el mecanismo de privacidad completo queda roto de forma silenciosa (sin error, solo filtrando datos de otro empleado). Ambos computes (`_compute_mi_info_bancaria`, `_compute_mi_telefono_personal`) ya lo tienen.

### Cuentas Analíticas (Proyecto): mismo patrón pull que empleados

`account.analytic.account` gana `enterprise_analytic_ref` (igual patrón que `hr.employee.enterprise_employee_ref`). `res.company._sync_analytic_accounts_from_enterprise()` corre en el mismo cron/intervalo que el sync de empleados (`ir_cron_employee_sync`, cuyo nombre ya no describe del todo su alcance pero se dejó así para no forzar una migración de datos solo por el nombre). `plan_id` es **obligatorio** en `account.analytic.account` (Odoo 19) - se busca-o-crea un `account.analytic.plan` por nombre igual que `hr.department`; si Enterprise no manda `plan_id`, cae en un plan genérico `"Proyectos (sin plan de origen)"` en vez de fallar toda la sincronización.

El encabezado gana `analytic_account_id` (Many2one local, nunca enviado como id) que autocompleta el `proyecto` (Char) ya existente vía `_onchange_analytic_account_id()` - mismo patrón que `employee_id`→`puesto`/`departamento`. `proyecto` sigue siendo lo que viaja a Enterprise en `_prepare_sync_vals()`, sin cambios ahí.

### Teléfono: campos NATIVOS de hr.employee (work_phone -> mobile_phone -> private_phone)

Decisión final y explícita del usuario, tras dos vueltas en esta misma sesión: el teléfono debe viajar por los campos **nativos** de `hr.employee` (`work_phone`, `mobile_phone`, `private_phone`), no por campos propios - "que se traslade de ficha a ficha entre Community y Enterprise usando el modelo estándar". `res.company._sync_employees_from_enterprise()` escribe directo a esos tres campos nativos; `account_payment_order_request` los lee directo (`employee.work_phone or employee.mobile_phone or employee.private_phone`, en ese orden) para autocompletar `telefono` - a diferencia de `cuenta_acreditar`/`banco`, este campo **no** quedó de solo lectura (el usuario no lo pidió), sigue editable a mano.

Enterprise tiene **tres** campos de teléfono, no dos - descubierto cuando el usuario probó esto la primera vez y su propio número no llegó a Community (lo tenía cargado en "Celular de Trabajo" = `mobile_phone`, no en "Teléfono de Trabajo" = `work_phone`).

**Bug real de Odoo core, encontrado y corregido en esta sesión - el motivo de `hr_employee.py`'s `write()` override**: `work_phone`/`mobile_phone` son campos `compute` + `store` + `inverse`, resueltos desde `work_contact_id.phone` (un `res.partner`). En cuanto se asigna `employee.user_id` a un empleado - **exactamente lo que hace el flujo real de este módulo**, cuando el administrador de Community vincula el empleado ya sincronizado a un usuario - el propio núcleo de `hr.employee` (`_sync_user()`/`_remove_work_contact_id()`, `..\odoo\addons\hr\models\hr_employee.py:1314-1334`) **reemplaza `work_contact_id` por el partner del usuario recién vinculado**, que no tiene teléfono, borrando en silencio el dato ya sincronizado. Confirmado reproduciendo el bug exacto (`emp.user_id = u.id` seguido de `emp.work_phone` → `False`) antes del fix.

**El fix**: `hr.employee.write()` (override en este módulo) toma una foto de `work_phone`/`mobile_phone` de los empleados sincronizados (`enterprise_employee_ref` truthy) **antes** de llamar a `super().write(vals)` cuando `'user_id'` está en `vals`, y si después del write del núcleo esos campos quedaron vacíos, los vuelve a escribir. Acotado a empleados sincronizados únicamente (nunca debería haber empleados "nativos" de Community de todas formas, pero por si acaso). `private_phone` es un `Char` simple sin `compute`/`inverse` - no le afecta este problema, se escribe y lee directo sin envoltura especial.

**Trade-off de privacidad asumido conscientemente** (el usuario no lo pidió explícitamente para teléfono, a diferencia de la cuenta bancaria donde sí fue un requisito explícito - ver más abajo): al escribir `private_phone` directo al campo nativo, cualquier usuario de Community con `hr.group_hr_user` ("Employees Officer") puede ver el teléfono personal de **cualquier** empleado - el mismo comportamiento de serie de Odoo, ni más ni menos restrictivo. Un intento anterior en esta sesión había construido un mecanismo self-scoped (solo el propio empleado ve su teléfono personal, ni siquiera un Oficial de RR.HH.) - se descartó a pedido explícito del usuario junto con los campos propios de teléfono. Si esto cambia, ese mecanismo self-scoped (idéntico al de `cuenta_bancaria` de abajo) es el patrón a reusar.

**Importante para el usuario al probar esto**: los datos de un empleado ya sincronizado antes de este cambio (o antes de agregar `mobile_phone`) no se actualizan solos - hay que correr "Sincronizar ahora" (Ajustes > Facturación > Sincronización de Empleados) o esperar al cron, para que el pull vuelva a correr y traiga los campos nuevos.

### Correo: mismo patrón que teléfono (`work_email` -> `private_email`)

Pedido explícito del usuario, calcado 1:1 del diseño de teléfono: `work_email`/`private_email` son los campos nativos equivalentes de correo (`email` en cambio es `related="user_id.email"` - el login de Community, no tiene nada que ver con Enterprise, **no se sincroniza**). `work_email` tiene **exactamente el mismo bug** que `work_phone` (mismo `_compute_work_contact_details`, mismo `work_contact_id`) - por eso `hr_employee.py`'s `write()` override ahora recorre `_WORK_CONTACT_FIELDS = ('work_phone', 'mobile_phone', 'work_email')` como una sola lista, no cada campo por separado. `private_email` es un `Char` simple igual que `private_phone` - mismo trade-off de privacidad (visible a cualquier `hr.group_hr_user`, no self-scoped).

El campo `correo` del encabezado de la Solicitud (antes con `default=lambda self: self.env.user.email`, el login de Community) ahora se autocompleta también vía `_onchange_employee_id()`/`_fill_derived_vals_from_employee()` con `employee.work_email or employee.private_email`, mismo criterio de prioridad que `telefono` - sigue editable a mano, no quedó de solo lectura.

### `justificacion_tipo_id`: catálogo (`account.payment.order.justification.type`), etiquetado "Tipo de Gasto"

### Bug real: `InvalidDomainError` en `payment_method_line_id` con un diario sin métodos de pago

Reportado por el usuario en producción, al elegir un diario de banco en el Wizard "Crear Anticipo": `Invalid domain representation: id,in,`. Causa: tanto el Wizard como `account.payment.order` (`payment_method_line_id`) tenían `domain="[('id', 'in', journal_id.outbound_payment_method_line_ids)]"` - navegar un Many2many **directo por punto dentro de un `domain=` en string** revienta en el cliente en cuanto esa lista queda **vacía** (diario de banco sin métodos de pago outbound configurados) - el propio parser JS de dominios no sabe serializar `id,in,<lista vacía>` correctamente. **El fix - mismo patrón que usa el propio Odoo** (`account.payment.available_payment_method_line_ids`, `..\odoo\addons\account\models\account_payment.py`): nunca naveges un Many2many por punto dentro de un domain string - materializa un campo `Many2many` calculado intermedio (`available_payment_method_line_ids`, `@api.depends('journal_id')`) y apunta el domain a ESE campo top-level en su lugar. Aplicado en **ambos** lugares (`account_payment_order.py` y el Wizard) - el campo auxiliar se agregó a ambas vistas con `invisible="1"` (necesario: un domain string solo puede referenciar campos que el formulario efectivamente tiene cargados).

### `action_crear_pago()`: el contable ya no tiene que crear el `account.payment` a mano antes de Conciliar

Pedido del usuario: puede haber varios pagos para una sola factura (ej. el pago del propio Anticipo cubre una parte, falta un pago adicional para el resto) o varias facturas cubiertas por un solo pago - `action_conciliar()` ya sabía netear cualquier combinación de `factura_ids`/`pago_ids`, pero **alguien tenía que crear y contabilizar el `account.payment` a mano en Contabilidad > Pagos primero**, y vincularlo aquí. `action_crear_pago()` (nuevo, `tipo in ('liquidacion', 'pago_directo')`, gateado a `account.group_account_manager` igual que `action_conciliar()`/`action_cancelar()`) calcula `total_facturas - ya_pagado` (solo facturas `posted`, solo pagos `in_process`/`paid`) y crea+contabiliza **un solo pago** por esa diferencia - decisión explícita del usuario ("un solo pago por el monto total"), no una lista de montos capturados de antemano. Si hiciera falta más de un pago adicional, se puede llamar varias veces (cada uno cubre lo que quede pendiente en ESE momento) o seguir agregando pagos ya existentes a mano en `pago_ids`, como ya se podía. Lanza `UserError` si no queda nada pendiente (evita crear un pago de Q0 o duplicar cobertura).

**Anticipo/Anticipo Viáticos NO tienen este botón** - ya tienen su propio equivalente (`action_aplicar()`, que también crea y contabiliza el pago automáticamente) y agregar un segundo botón redundante ahí sería confuso. La vista ya no oculta la sección "Pagos/Cheques" para Anticipo (antes estaba envuelta en `invisible="tipo in ('anticipo', 'anticipo_viaticos')"` junto con `cuenta_ajuste_id`/`move_id`, que SÍ siguen ocultos para Anticipo - esos dos son exclusivos de Liquidación/Pago Directo).

Sobre "un campo de cancelado/borrador solo para gerente" (parte de este mismo pedido): inicialmente asumí que `action_cancelar()` (Liquidación/Pago Directo, ya gateado a Gerente) cubría esto por completo - **incompleto**: al usuario le faltaba el botón "Cancelar" en un **Anticipo ya Aplicado** específicamente. `action_cancel()` (el Cancelar original de Anticipo, sin restricción de grupo) se oculta a propósito una vez `state == 'aplicado'` porque solo cambia el estado, sin revertir nada - no servía para ese caso. Se agregó `action_cancelar_anticipo_aplicado()` (nuevo botón "Cancelar", mismo label, visible solo cuando `tipo in ANTICIPO_TIPOS and state == 'aplicado'`, gateado igual que `action_cancelar()`): cancela **todos** los pagos en `pago_ids` con estado `in_process`/`paid` (`remove_move_reconcile()` en sus líneas + `payment.action_cancel()`, mismo patrón que `action_cancelar()` usa con `move_id`) y regresa el estado a `cancelado`. Bloquea con `UserError` si ya existe una Liquidación registrada para este Anticipo (`search_count([('anticipo_id', '=', self.id)])`) - cancelar el pago por debajo rompería esa Liquidación (ya sea porque todavía lo referencia en `pago_ids` sin conciliar, o porque ya se conciliaron sus líneas). Verificado: bloqueado sin permiso de Gerente, Gerente sí puede cancelar (el `account.payment` real queda en estado `canceled`), y bloqueado si ya hay una Liquidación registrada.

### `diferencia_conciliacion`: saldo en vivo en Liquidación/Pago Directo, "lo más cercano a la conciliación nativa de Odoo"

Pedido del usuario: al elegir el Anticipo de Origen en una Liquidación, necesitaba saber de inmediato si le faltaban facturas o pagos para que todo quedara equilibrado - hoy solo se enteraba del desbalance con un `UserError` al intentar Conciliar. Dos piezas:

- **`diferencia_conciliacion`** (Monetary, compute no-stored, `tipo in ('liquidacion', 'pago_directo')`): `total facturas posted - total pagos in_process/paid` - **misma fórmula ya usada por `action_crear_pago()`**, una aproximación con los totales de cada documento (`amount_total`/`amount`), no con las líneas contables reales que sí usa `action_conciliar()` (que sigue siendo la autoridad final - este campo es solo un indicador en vivo, coincide con el caso normal). Positivo = faltan pagos, negativo = faltan facturas (o pagos de más), cero = listo para Conciliar. Visible en el formulario justo debajo de Pagos/Cheques, con un texto de ayuda explicando el signo.

Solo agrega, nunca quita (si se cambia a otro Anticipo, no borra pagos ya cargados de otra fuente).
- Verificado: al registrar vía el botón, la diferencia arranca negativa (falta cargar facturas por el monto del Anticipo); al cargar la factura correspondiente, llega a cero y Conciliar funciona sin pedir Cuenta de Ajuste; elegir `anticipo_id` a mano (sin el botón) también carga los pagos del Anticipo, igual que el flujo del botón.

### Sincronización de vuelta: el estado real (Enviado/Aprobado/Rechazado/Aplicado) ya regresa a Community

**Hallazgo del usuario, no un pedido de feature nueva sobre algo que ya funcionaba**: hasta este cambio, `_sync_to_enterprise()` era de un SOLO sentido - al Enviar una Orden en Community, se crea un registro NUEVO en Enterprise (`origin='synced'`), pero el registro ORIGINAL en Community nunca se enteraba de nada de lo que pasara después ahí (aprobación, rechazo, aplicación) - se quedaba congelado en `state='enviado'` para siempre. - **`fetch_order_status()`** (nuevo en `tools/enterprise_sync_api.py`): `search_read` sobre `account.payment.order` en Enterprise, filtrando por `external_ref in [...]` (el propio `name` de cada Orden local pendiente - NUNCA por id, son bases de datos distintas), trayendo `state`/`reject_reason`/`approve_date`/`reject_date`.
- **Descubrimiento de seguridad, no un permiso nuevo**: el usuario de integración (`group_payment_order_sync_integration`) YA tenía `perm_read=1` sobre este modelo en `ir.model.access.csv` (lo necesitan sus propios `@api.constrains` al validar un `create()`, ej. `_check_anticipo_id`) - el comentario del grupo decía "nunca leer", desactualizado; se corrigió el texto para reflejar la realidad, sin tocar el permiso real ni crear un usuario/grupo aparte.
- **`res.company._pull_payment_order_status()`**: busca las propias Órdenes `tipo in ANTICIPO_TIPOS`, `origin='local'`, `sync_state='synced'`, `state not in ('aplicado', 'rechazado', 'cancelado')` (los 3 estados terminales - `'aprobado'` SIGUE pendiente de revisar en la próxima corrida, todavía puede llegar a `'aplicado'`); por cada una que cambió de estado en Enterprise, hace un `write()` PLANO de `state`/`reject_reason`/`approve_date`/`reject_date` - **nunca llama `action_approve()`/`action_reject()`/`action_aplicar()`** (esos son para EJECUTAR la transición aquí mismo; esto solo refleja una transición que YA ocurrió allá, sin repetir ningún efecto secundario como crear un pago local o disparar otra sincronización).
- Botón manual "Sincronizar ahora" (`action_pull_payment_order_status_now()`) en Ajustes, junto al intervalo - mismo patrón que el de empleados.
- Verificado con un mock de `fetch_order_status()` (sin depender de dos instancias reales corriendo): el pull actualiza solo las Órdenes pendientes reales, respeta los 3 estados terminales (no las vuelve a tocar ni a consultar), y una corrida sin nada pendiente no intenta conectarse a la Procesadora. También verificado que cambiar el intervalo en Ajustes actualiza el cron real, y que el cron viene activo por defecto en 1 hora.

### Elegir el Anticipo de Origen hereda diario, método de pago, pagos y facturas (no solo pagos)

### Se eliminó el número de Liquidación manual - Liquidación ahora usa la misma secuencia OP/XXXX

Razonamiento del usuario: no hace falta una numeración de Liquidación aparte - la propia Orden de Pago (`tipo`) ya distingue si es Anticipo/Liquidación/Pago Directo, así que un solo número de Orden de Pago (secuencia `OP/0001`, `OP/0002`...) alcanza para cualquier tipo, incluida Liquidación.

**IMPORTANTE - no confundir con el campo homónimo en `account.payment`/`account.move`**: esto es sobre `account.payment.order.no_liquidacion` (un `Integer` manual, con su propia numeración en papel, que generaba el nombre `"Liquidación N"` vía `_compute_name()`) - **eliminado por completo** (campo, `_sql_constraints` de unicidad, `@api.onchange('no_liquidacion')`). El OTRO `no_liquidacion` (Many2one en `account.payment`/`account.move`, domain `tipo='liquidacion'`, agregado en la fusión Solicitud+Anticipo - ver arriba) **no se tocó** - sigue funcionando igual, es un campo completamente distinto que ya no tiene ninguna relación con el número manual retirado aquí.

**Qué cambió**: `create()` ahora asigna la secuencia `OP/XXXX` también para `tipo='liquidacion'` (antes solo `anticipo`/`anticipo_viaticos`/`pago_directo`) - una Liquidación creada sin `name` explícito ya no depende de que alguien escriba un número a mano; simplemente es la siguiente Orden de Pago de la secuencia, igual que cualquier otro tipo. `_compute_name()` se simplificó a solo el placeholder de un `.new()` sin guardar (`'Nueva Orden de Pago'` si `name` sigue vacío) - ya no depende de `no_liquidacion` para nada.

**Sin migración de datos** (mismo criterio ya usado en esta sesión): las Liquidaciones reales ya existentes en producción, con su "Liquidación N" ya asignado, se quedan con ese nombre tal cual está en la base de datos - `name` es un campo `store=True` normal, no se recalcula solo. Ninguna Liquidación NUEVA a partir de este despliegue volverá a usar ese esquema; el usuario decide qué hacer con los registros viejos.

Tres pedidos relacionados del usuario, todos sobre el mismo formulario de Anticipo:

- **`payment_id` (Many2one "Pago del Anticipo") se eliminó del modelo por completo** - ya existía `pago_ids` (One2many) cubriendo el mismo caso genéricamente (y mejor, ya que admite más de un pago). `action_aplicar()` ya no le escribe nada (solo `state`); el pago que crea sigue llevando `payment_order_id` (por eso aparece en `pago_ids`, sin cambios de esa parte). El reporte impreso (`o.pago_ids | o.payment_id` → `o.pago_ids`) y la vista (el campo ya no aparece) se ajustaron igual. **Consecuencia real, documentada aquí para que no sorprenda**: `action_registrar_liquidacion()` usaba `payment_id` como una referencia INDEPENDIENTE que sobrevivía aunque el pago se "reasignara" (comando `(4, id)` sobre un One2many reescribe el `payment_order_id` del pago hacia el nuevo padre) hacia la Liquidación - sin ese campo aparte, ahora se copian **todos** los pagos de `self.pago_ids` hacia la Liquidación (`[(4, p.id) for p in self.pago_ids]`, antes solo uno), y el Anticipo de origen se queda con `pago_ids` **vacío** después de Registrar Liquidación (el/los pago(s) pasan a pertenecerle a la Liquidación, que es donde tiene sentido verlos para la conciliación). Antes esto no se notaba porque `payment_id` seguía mostrando el pago en el Anticipo aunque ya perteneciera a la Liquidación.
- **`monto` hereda `total_acreditar` para Anticipo Viáticos** - ya no se captura a mano para ese tipo, sigue la suma de las pestañas de detalle (hoy solo Viáticos; si se agrega una pestaña de Materiales en el futuro, bastaría con sumarla también dentro de `_compute_totales()`, sin tocar nada de este mecanismo). Implementado con `_sync_monto_desde_total_acreditar()`, llamado desde: `@api.onchange('viaticos_line_ids.total', 'anticipo_previo')` (formulario web), después de `super().create()` (altas por API/script), y desde `write()` cuando cambian `viaticos_line_ids`/`anticipo_previo`/`tipo` (ediciones por API/script) - **no es un `compute=` del campo** (se evaluó y se descartó: un compute `store=True` con un `if` que a veces no asigna valor para un tipo distinto revienta con "compute method did not assign a value" - más seguro seguir el patrón ya usado en el módulo para "valor derivado pero técnicamente editable", como `proyecto`/`_onchange_analytic_account_id`). Vista: `monto` pasó a `readonly="tipo == 'anticipo_viaticos' or state not in ('borrador','aprobado')"` (antes solo el segundo criterio) - visualmente ya no se puede tocar a mano para ese tipo, aunque el campo en la BD sigue siendo un `Monetary` normal, no un compute. **Anticipo normal (sin pestañas) no se toca** - sigue siendo 100% manual, como siempre; el mecanismo de sync literalmente no hace nada para ese tipo.
- Verificado con un script nuevo: `payment_id` ya no existe como campo; `monto` se sincroniza al crear con líneas, al agregar una línea vía `write()`, y se autocorrige aunque se haya escrito un valor manual desalineado (en cuanto cualquier escritura de líneas/`anticipo_previo` dispara el re-sync); un Anticipo normal sin líneas mantiene su monto manual intacto; `action_aplicar()`/`action_registrar_liquidacion()`/`action_cancelar_anticipo_aplicado()` funcionan correctamente solo con `pago_ids` (incluyendo que Registrar Liquidación mueve todos los pagos, dejando el Anticipo de origen sin pagos propios).

### Bug real: "Volver a Borrador" desde Enviada no tenía ningún gate de permiso

Reportado por el usuario: cualquiera con acceso de Facturación (incluido el Jefe de técnicos, quien solo debería poder crear/enviar) podía retirar en silencio una Orden ya Enviada de vuelta a Borrador - `action_reset_to_draft()` no llamaba a ningún chequeo de permiso, y el botón en la vista no tenía `groups=` (a diferencia de `action_approve()`/`action_reject()`, justo arriba en el mismo `<header>`).

**Matiz importante, no una restricción uniforme**: el mismo botón/método también cubre Rechazada → Borrador, que SÍ debe seguir abierto para el solicitante original - es el camino normal para corregir y reenviar algo que ya fue rechazado, no una acción que amerite permiso especial. Gatear las dos transiciones por igual habría roto ese flujo legítimo.

**El fix**: `action_reset_to_draft()` ahora llama `rec._check_is_approver()` (el mismo chequeo que ya usa `action_reject()`) **solo cuando `rec.state == 'enviado'`** - Rechazada → Borrador queda sin cambios. La vista se dividió en **dos** `<button name="action_reset_to_draft">` con el mismo `name` (llaman al mismo método) pero `invisible=`/`groups=` distintos: uno para `state == 'enviado'` con `groups="...group_payment_order_approver"`, otro para `state == 'rechazado'` sin `groups=` - un solo `groups=` en un botón que cubre ambos estados no puede expresar "requerido para este estado, no para aquel". Verificado con un script real en `construtec_test`: un usuario sin el grupo aprobador queda bloqueado en `enviado` (`AccessError`), el mismo usuario CON el grupo sí puede resetear un `enviado`, y sin el grupo igual puede resetear un `rechazado`.

### Un Anticipo solo puede tener una Liquidación: constraint dura (SQL + Python)

Requisito explícito del usuario, endureciendo una regla que hasta este cambio solo se cumplía a medias: "una liquidación si o si debe tener un anticipo, solo es un anticipo por liquidación y solo es una liquidación por anticipo". La primera mitad (`toda Liquidación necesita anticipo_id`) ya estaba forzada por `_check_anticipo_id()` desde antes - la segunda mitad ("solo una Liquidación por Anticipo") **solo era un filtro de UI** (`anticipos_disponibles_ids`, que excluye del desplegable un Anticipo ya liquidado) - nada impedía crear una segunda Liquidación apuntando al mismo `anticipo_id` a mano o por API/script.

**El fix, dos capas** (defensa en profundidad, mismo patrón que ya usa el resto del módulo):
- `_sql_constraints = [('anticipo_id_uniq', 'unique(anticipo_id)', ...)]` - a nivel de base de datos, a prueba de carrera (dos usuarios guardando "al mismo tiempo"). Funciona porque en Postgres `NULL` nunca es igual a `NULL` en un `UNIQUE` - un Anticipo/Pago Directo (`anticipo_id` siempre `NULL`) nunca choca contra otro; solo protege entre Liquidaciones (las únicas que llevan `anticipo_id` real).
- `_check_anticipo_id()` (`@api.constrains`) ahora también busca una Liquidación duplicada apuntando al mismo Anticipo y, si existe, lanza un `ValidationError` con el nombre de la Liquidación ya registrada - mensaje más útil que el genérico de Postgres, para el caso normal (sin carrera de por medio).

Verificado end-to-end en `construtec_test` (ver script de la sección siguiente, que cubre esto en el mismo flujo): una segunda Liquidación contra un Anticipo ya liquidado queda bloqueada con el mensaje esperado.

### Nuevo estado `liquidado`: separa "Aplicado" (Anticipo) de "completamente conciliado" (Liquidación/Pago Directo)

Pedido del usuario, pensando en voz alta sobre el modelo de negocio real: un Anticipo Viáticos es pura salida de dinero (un pago, sin facturas todavía); la Liquidación es donde llegan las facturas que lo justifican; cuando las salidas de dinero y el total de facturas **cuadran**, tanto el Anticipo como la Liquidación deberían quedar en un estado que se lea como "liquidado", no confundirse con el "aplicado" genérico que ya usa Anticipo para "el pago ya se ejecutó".

Dos decisiones de diseño confirmadas explícitamente con el usuario antes de tocar código:

1. **¿Un ajuste (`cuenta_ajuste_id`) sigue contando como "liquidado"?** Sí - `liquidado` es el resultado de que `action_conciliar()` termine con éxito, use o no una Cuenta de Ajuste para absorber una diferencia. No se introdujo un tercer estado intermedio ("conciliado con ajuste" vs. "liquidado exacto") - se consideró innecesario para lo que el usuario pidió.
2. **¿El `state` del Anticipo cambia también a `liquidado`?** No, deliberadamente - el Anticipo se queda en `state='aplicado'` para siempre (no hay una transición `aplicado -> liquidado` en el propio Anticipo). Cambiar su `state` habría obligado a revisar/ajustar cada guard y dominio que hoy compara contra `state == 'aplicado'` para `ANTICIPO_TIPOS` (`_compute_anticipos_disponibles_ids`, `action_registrar_liquidacion`, `action_cancelar_anticipo_aplicado`, `_find_anticipos_sin_liquidar`, el pull de estado Community↔Enterprise en `res_company.py`) - riesgo real e innecesario en un módulo ya en producción. En vez de eso, el Anticipo gana un indicador **aparte**.

**Qué cambió, en concreto**:
- `state` (Selection compartido por los 4 tipos) gana un valor nuevo, `('liquidado', 'Liquidado')`, entre `aplicado` y `cancelado`. Solo lo usan Liquidación/Pago Directo - `action_conciliar()` ahora termina con `self.write({'move_id': move.id, 'state': 'liquidado'})` (antes `'aplicado'`). Anticipo/Anticipo Viáticos siguen terminando en `'aplicado'`, sin cambios.
- **`liquidacion_ids`** (One2many nuevo, `account.payment.order`/`anticipo_id`) - la relación inversa de `anticipo_id`; en la práctica nunca trae más de un registro (forzado por la constraint de la sección anterior). Existe solo como respaldo del compute de abajo.
- **`esta_liquidado`** (Boolean, `compute='_compute_esta_liquidado', store=True`, `@api.depends('liquidacion_ids.state')`) - `True` cuando el Anticipo tiene una Liquidación vinculada y esa Liquidación ya está en `state='liquidado'`. Se recalcula solo en ambas direcciones (al conciliar, al cancelar una Liquidación de vuelta a `borrador` vía `action_cancelar()` - que no tiene ningún cambio propio, simplemente ya no dispara si el estado previo era `aplicado` o `liquidado`, no comprueba precondición de estado).
- **Vista**: un `<widget name="web_ribbon" title="Liquidado" .../>` en la esquina del formulario, visible solo si `tipo in ANTICIPO_TIPOS and esta_liquidado`; columna opcional `esta_liquidado` en la lista; dos filtros nuevos en la búsqueda ("Anticipos Liquidados"/"Anticipos sin Liquidar"). Los botones/statusbar/badge de Liquidación/Pago Directo que comparaban contra `state == 'aplicado'` (`action_conciliar`/`action_cancelar` `invisible=`, el `statusbar_visible`, la decoración `success` de la lista general) se actualizaron a `'liquidado'` - **ningún** lugar que compara el `state` del Anticipo (no de la Liquidación) contra `'aplicado'` se tocó.

**No afecta la sincronización Community↔Enterprise**: tanto `_prepare_sync_vals()` (siempre manda `state: 'enviado'` al crear del lado Solicitante) como `_pull_payment_order_status()`/`_find_anticipos_sin_liquidar()` en `res_company.py` solo leen/escriben el `state` del **Anticipo** (que sigue siendo `aplicado`/`rechazado`/`cancelado`/etc., sin cambios) - nunca el de una Liquidación, que es puramente local a la instalación Procesadora (Liquidación no se sincroniza ni se crea del lado Solicitante).

Verificado end-to-end en `construtec_test` (`-u construtec_account_payment_order_19 --stop-after-init --no-http`, luego un script por `odoo-bin shell`): Anticipo creado y aplicado (`state=aplicado`); Liquidación registrada y vinculada (`anticipo_id` correcto); factura posteada por el monto exacto (`diferencia_conciliacion=0.00`); `action_conciliar()` deja la Liquidación en `state=liquidado`; el Anticipo recalcula `esta_liquidado=True` sin ninguna acción adicional; una segunda Liquidación contra el mismo Anticipo sigue bloqueada (constraint de la sección anterior); `action_cancelar()` regresa la Liquidación a `borrador` y el Anticipo recalcula `esta_liquidado=False` automáticamente.

### Indicador "Sin Liquidar" por técnico en la línea de Viáticos + reporte "Viáticos sin Liquidar" (por empleado, solo Enterprise)

Pedido explícito del usuario, apoyado en el `esta_liquidado` recién agregado: al capturar una solicitud de Anticipo Viáticos con varios técnicos (cada uno una línea de `viaticos_line_ids`), quiere ver de inmediato, por técnico, cuántas OTRAS solicitudes de viáticos de ese mismo técnico ya están Aplicadas pero todavía sin Liquidación conciliada - y además un reporte aparte, agrupado por empleado, con el mismo criterio.

- **`viaticos_sin_liquidar_count`** (Integer, `compute`, **no stored** - mismo criterio que `diferencia_conciliacion`/`anticipos_disponibles_ids`: es un indicador en vivo sobre datos de OTROS registros, no algo que tenga sentido cachear) en `account.payment.order.viatico.line` (`models/account_payment_order_viatico_line.py`). Cuenta, para el `employee_partner_id` de esa línea, cuántas OTRAS líneas de viáticos (de OTRAS Órdenes, nunca de la propia) cumplen `order_id.tipo='anticipo_viaticos'`, `order_id.state='aplicado'`, `order_id.esta_liquidado=False`. Se agregó como columna nueva ("Sin Liquidar") en la lista editable de la pestaña Viáticos, con `decoration-warning` cuando es mayor a cero.
  - **Trampa evitada**: `order_id.id` puede ser un `NewId` mientras se captura una solicitud nueva sin guardar todavía - comparar eso directo dentro de un domain de `search_count()` rompería (Postgres no entiende un `NewId`). Se excluye la propia Orden del conteo (`('order_id', '!=', ...)`) solo cuando `isinstance(line.order_id.id, int)` - en la práctica ni hace falta para una Orden nueva (nunca está en `state='aplicado'` todavía, así que el propio filtro de estado ya la excluye), pero se dejó por si se consulta el conteo en una Orden ya Aplicada existente (de solo lectura en ese estado).
- **Reporte "Viáticos sin Liquidar"** (`views/account_payment_order_viaticos_report_views.xml`) - una lista (+ pivot) sobre `account.payment.order` (el ENCABEZADO, no la línea), agrupada por defecto por `partner_id` - el jefe de técnicos/empleado que capturó la solicitud, **no** los técnicos individuales de `viaticos_line_ids` (corrección explícita del usuario tras una primera versión que agrupaba por línea/técnico: "debe estar agrupado... por el empleo que el jefe de técnicos... en el encabezado... no los técnicos que van en el detalle"). Domain: `tipo='anticipo_viaticos'`, `state='aplicado'`, `esta_liquidado=False`. Menú nuevo bajo Contabilidad/Facturación (`account.menu_finance_payables`), gateado a `account.group_account_invoice`.
  - **"Visto desde Enterprise"** (pedido explícito del usuario): una Liquidación nunca se crea ni se sincroniza hacia Community (es puramente local a la instalación Procesadora - ver la sección "Nuevo estado `liquidado`" arriba) - si este reporte se mostrara igual en Community, TODO se vería "sin liquidar" para siempre, información engañosa, no real. En vez de ocultar el menú por completo (no hay un mecanismo limpio de `groups=` basado en configuración de compañía - los `menuitem` solo aceptan grupos de seguridad, no un campo calculado como `es_procesador`), el domain de la propia acción filtra `company_id.payment_order_role = 'procesador'` - mismo criterio que ya usa `es_procesador` en el formulario, aplicado aquí directo en el domain. En Community, la compañía propia siempre tiene `payment_order_role='solicitante'`, así que el reporte simplemente no devuelve nada ahí (mensaje de "sin resultados" explicando por qué, en vez de datos incorrectos).
  - **No confundir con `viaticos_sin_liquidar_count`** (el indicador de la sección anterior, a nivel de LÍNEA/técnico dentro de una solicitud) - son dos vistas distintas del mismo problema, a propósito: la columna ayuda a detectar en el momento de capturar si UN técnico ya tiene algo pendiente; el reporte da la vista gerencial agrupada por quién solicitó cada Anticipo Viáticos.

Verificado en `construtec_test` (`-u ... --stop-after-init --no-http`, luego un script por `odoo-bin shell`): dos Anticipos Viáticos Aplicados sin liquidar para el mismo técnico (Orden A y B) → la línea de B ve `viaticos_sin_liquidar_count=1` (cuenta a A, no a sí misma); un tercer Anticipo (Orden C) se registra, se liquida completo (factura exacta + `action_conciliar()`) → el conteo en la línea de B sigue en 1 (A sigue pendiente, C ya no cuenta); el reporte (a nivel de encabezado, agrupado por `partner_id`) incluye A y B pero excluye C.

### `liquidacion_id`: ver desde el Anticipo hacia su Liquidación (antes solo se veía al revés)

Reportado por el usuario: la Liquidación siempre mostró `anticipo_id` ("Anticipo de Origen"), pero el Anticipo no tenía ningún campo simétrico para ver hacia qué Liquidación quedó vinculado - había que ir a buscarla a mano (o confiar en `esta_liquidado`, que solo dice sí/no, sin decir cuál).

`liquidacion_id` (Many2one, `compute='_compute_liquidacion_id'`, `@api.depends('liquidacion_ids')` - toma el primero de `liquidacion_ids`, el One2many agregado junto con `esta_liquidado`) - de solo lectura, visible en el mismo grupo que `anticipo_id`, justo debajo, con `invisible="tipo not in ('anticipo', 'anticipo_viaticos') or not liquidacion_id"` (no ocupa espacio en un Anticipo que todavía no tiene Liquidación registrada). Verificado: vacío antes de `action_registrar_liquidacion()`, apunta a la Liquidación correcta después.

### Investigado: `community_url` "no se ve" en Enterprise - no es un bug de código, es cobertura de datos

Reportado por el usuario: en Enterprise, un Anticipo Viáticos no muestra el link "Ver Orden en Community" (`community_url`), mientras que en Community el link "Ver Orden en Enterprise" (`enterprise_url`) sí se ve correctamente. Investigado con un script que simula exactamente lo que `create_sync_record()` hace en Enterprise al recibir una sincronización (`Order.create({'origin_record_id': ..., 'origin_base_url': ..., ...})`, el mismo payload real que arma `_prepare_sync_vals()`): tanto el compute (`_compute_community_url`) como el `arch` de la vista de formulario (confirmado con `get_view()`) resuelven y muestran el campo correctamente cuando `origin_record_id`/`origin_base_url` están presentes - **no hay ningún bug de código aquí**.

La causa real, casi seguro: `origin_record_id`/`origin_base_url` solo se llenan en un registro que llegó por sincronización (`origin='synced'`) - un Anticipo creado directamente a mano en Enterprise (no sincronizado desde Community) nunca los tiene, y por diseño su `community_url` se queda vacío correctamente (no hay ninguna "Orden en Community" que enlazar, porque no existe). También es posible que sea un Anticipo sincronizado ANTES de que este campo existiera en el módulo (sin migración de datos retroactiva, mismo criterio ya documentado varias veces en este archivo). **Para confirmar**: revisar en un Anticipo Viáticos sincronizado nuevo (creado en Community después de este despliegue, con la sincronización habilitada) si el link aparece - si sigue sin verse en un registro genuinamente nuevo y sincronizado, ahí sí habría un bug real que investigar más a fondo con ese caso concreto.

### Bug real: `viaticos_sin_liquidar_count` solo contaba Anticipos ya `aplicado`, dejando fuera Borrador/Enviada/Aprobada

Reportado por el usuario con un caso real de producción (`erp.construtecasesores.com`): dos técnicos con solicitudes de viáticos pendientes en otro lado no mostraban ningún conteo ("debería aparecer uno para cada uno"). Causa: la primera versión de `_compute_viaticos_sin_liquidar_count()` filtraba `order_id.state == 'aplicado'` - un criterio que interpreté (sin confirmarlo con el usuario) como "solo cuenta dinero ya desembolsado". El pedido original del usuario, sin embargo, fue más amplio: "la cantidad de veces que aparece ese técnico... en otras solicitudes de viáticos que **aún no se hayan liquidado**" - una solicitud todavía en Borrador/Enviada/Aprobada (esperando revisión/pago) también "aún no se ha liquidado", y es exactamente el caso real que el usuario reportó (dos técnicos con solicitudes en curso en otro estado, no necesariamente ya Aplicadas).

**El fix**: el domain cambió de `('order_id.state', '=', 'aplicado')` a `('order_id.state', 'not in', ('rechazado', 'cancelado'))` - ahora Borrador/Enviada/Aprobada/Aplicada cuentan todas como "aún no liquidada" (coherente: `esta_liquidado` de todas formas solo puede ser `True` para una Orden Aplicada con Liquidación conciliada, así que el filtro de `esta_liquidado = False` ya deja pasar naturalmente los estados previos a Aplicado); solo Rechazada/Cancelada quedan excluidas, por representar dinero que nunca se va a entregar o que ya se revirtió.

**Nota para si el fix no resuelve el caso real reportado**: este módulo tiene un bug de Odoo core ya documentado (ver "Bug real de Odoo core" sobre `work_phone`/`work_email`, arriba) donde `hr.employee.work_contact_id` puede reemplazarse por un contacto distinto al vincular un `user_id` - si el conteo sigue en 0 para un técnico que el usuario sabe que tiene una solicitud pendiente, vale la pena verificar que el `employee_partner_id` de la solicitud vieja sea EXACTAMENTE el mismo `res.partner` que el de la solicitud nueva (pudo haber cambiado de identidad si a ese empleado se le vinculó un usuario entre una solicitud y otra).

Verificado en `construtec_test`: una Orden en Borrador (nunca enviada/aprobada/aplicada) para un técnico SÍ se cuenta en `viaticos_sin_liquidar_count` de una segunda Orden nueva para el mismo técnico (antes del fix, no contaba); al Rechazar esa primera Orden, el conteo baja a 0.

## Fusión: Liquidación deja de ser un tipo/registro aparte

**Esto reemplaza el diseño de dos registros descrito en el resto de este archivo** (que existió durante buena parte de esta sesión: `tipo='liquidacion'` era un CUARTO valor con su propio registro `account.payment.order`, vinculado 1:1 al Anticipo de origen vía `anticipo_id`, creado por el botón "Registrar Liquidación"). El usuario, describiendo el flujo real, señaló el problema: "el anticipo queda vacío [al mover sus pagos hacia la Liquidación] y hace la vinculación... veo que es muy enredado". Su propuesta, confirmada e implementada tal cual: **que no haya otra orden de pago, sino que la misma orden de pago esté en un estado liquidado, y el liquidado ya presente facturas y pagos** - exactamente como ya funcionaba Pago Directo (que nunca tuvo un registro "padre" separado).

**Dos decisiones explícitas del usuario antes de tocar código**:
1. **Sin migración de datos** - "no hay información por guardar hasta este momento, se puede eliminar sin problema". No existían Liquidaciones reales en producción con datos que preservar, así que no se construyó ningún script de migración (fusionar facturas/pagos/asiento de una Liquidación existente hacia su Anticipo) - si esto se retoma alguna vez con datos reales de por medio, hay que escribirlo antes de desplegar, no asumir que se puede simplemente borrar (el `ondelete='restrict'` de `payment_order_id` en `account.move`/`account.payment` de todas formas impediría un `unlink()` directo mientras la Liquidación tenga facturas/pagos vinculados).
2. **`tipo='liquidacion'` se elimina por completo**, no se deja como opción residual - ya no tenía ningún caso de uso real distinto a Pago Directo desde que (en un cambio anterior de esta misma sesión) una Liquidación pasó a ser obligatoriamente 1:1 con un Anticipo.

**Qué cambió, en concreto**:

- **`tipo`** (Selection) pierde el valor `'liquidacion'` - ahora solo `anticipo` / `anticipo_viaticos` / `pago_directo`.
- **Campos eliminados por completo** (existían solo para el vínculo entre los dos registros): `anticipo_id`, `anticipos_disponibles_ids` + su compute, `liquidacion_ids`, `liquidacion_id` + su compute, `esta_liquidado` + su compute, la `_sql_constraints` `anticipo_id_uniq`, `_check_anticipo_id()`, `_onchange_anticipo_id_heredar_datos()`. También se eliminó `no_liquidacion` (Many2one) de `account.move`/`account.payment` - era un campo con dominio `tipo='liquidacion'` que ya duplicaba a `payment_order_id` sin aportar nada distinto (y ese `tipo` ya no existe); `payment_order_id` sigue siendo el campo de trazabilidad, sin cambios.
- **`action_registrar_liquidacion()` se eliminó** - ya no crea ningún registro nuevo. En su lugar, un Anticipo/Anticipo Viáticos ya `aplicado` sigue usando sus propios `factura_ids`/`pago_ids` (campos que YA existían en el registro, antes ocultos/opcionales para ese tipo - ver la sección de auto-detección de Pago Directo, más arriba) y llama al mismo `action_conciliar()` que ya usaba Pago Directo.
- **`action_conciliar()`/`action_cancelar()`/`action_crear_pago()`** ahora aceptan `tipo in ANTICIPO_TIPOS + ('pago_directo',)` (antes `('liquidacion', 'pago_directo')`). Para Anticipo/Anticipo Viáticos, `action_conciliar()`/`action_crear_pago()` exigen `state == 'aplicado'` primero (Pago Directo sigue sin precondición de estado, arranca desde `borrador` como siempre).
- **`action_conciliar()` sigue terminando en `state='liquidado'`** (sin cambios desde la sesión anterior) - la diferencia es que ahora ese `write()` ocurre sobre el MISMO registro que ya estaba en `aplicado`, no sobre un registro nuevo.
- **`action_cancelar()` (deshacer la conciliación) ahora es tipo-consciente al decidir a qué estado regresar**: para Pago Directo, `borrador` (sin cambios); para Anticipo/Anticipo Viáticos, **`aplicado`**, NO `borrador` - el desembolso original (`action_aplicar()`) ya ocurrió y sigue siendo válido, solo se deshace la conciliación. Antes esto no aplicaba porque Liquidación (el único tipo que usaba `action_cancelar()` además de Pago Directo) siempre volvía a `borrador` sin ambigüedad.
- **`action_cancelar_anticipo_aplicado()`** perdió el chequeo `search_count([('anticipo_id', '=', self.id)])` (bloqueaba si "ya existe una Liquidación registrada") - ya no hace falta: como exige `state == 'aplicado'` específicamente, un Anticipo ya liquidado (que ahora está en `state='liquidado'`, no `'aplicado'`) queda excluido por esa misma precondición, sin necesitar una búsqueda aparte. Para revertir un Anticipo ya Liquidado hay que usar primero `action_cancelar()` (vuelve a `aplicado`) y LUEGO `action_cancelar_anticipo_aplicado()` (vuelve a `cancelado`) - una reversión en dos pasos, cada uno deshaciendo su propio efecto contable (primero la conciliación, luego el desembolso).
- **Bug real encontrado y corregido de paso**: `action_cancel()` (el "Cancelar" sin restricción de grupo, para un Anticipo que TODAVÍA no tiene ningún efecto contable) no tenía NINGÚN chequeo de estado en Python - solo el botón estaba oculto en la vista para `state in ('aplicado', ...)`. Cualquiera con acceso de Facturación podía, vía RPC, poner `state='cancelado'` a un Anticipo ya Aplicado o Liquidado sin revertir el pago/asiento real, dejando el registro en un estado contable inconsistente (marcado "cancelado" pero con dinero real ya movido). Corregido: `action_cancel()` ahora exige `state in ('borrador', 'enviado', 'aprobado', 'rechazado')` explícitamente en Python, no solo en la vista.
- **`puede_conciliar`** (Boolean, `compute`, no stored) nuevo - centraliza en un solo campo la condición "esta Orden puede pasar por `action_conciliar()` ahora mismo" (Anticipo/Anticipo Viáticos en `aplicado`, o Pago Directo en `borrador`), reemplazando varias condiciones `tipo not in (...) or state != ...` repetidas en la vista (botón Conciliar/Liquidar, botón Crear Pago, grupo de Diferencia a Conciliar).
- **Vista**: el botón antes llamado "Registrar Liquidación" desaparece; el botón que ya existía como "Conciliar" (antes solo visible para Liquidación/Pago Directo) ahora se llama **"Liquidar"** y es visible para los 3 tipos restantes vía `invisible="not puede_conciliar"` - mismo método (`action_conciliar()`) para todos. La sección "Facturas"/"Pagos/Cheques" (`invisible="not es_procesador"`) ya era genérica para cualquier tipo desde antes, así que no necesitó cambios - simplemente ahora un Anticipo Aplicado también la aprovecha. El div de "Diferencial"/`cuenta_ajuste_id`/`move_id` (antes oculto para `tipo in ANTICIPO_TIPOS`) ahora se muestra para los 3 tipos, gateado a `invisible="not es_procesador"` (nuevo - antes no hacía falta porque Community nunca veía Liquidación/Pago Directo; ahora si Anticipo Viáticos puede llegar a `liquidado`, Community necesita seguir sin ver estos campos contables). Los filtros de búsqueda "Anticipos Liquidados"/"Anticipos sin Liquidar" pasaron de comparar `esta_liquidado` a comparar `state` directamente (`'liquidado'`/`'aplicado'`).
- **`_find_anticipos_sin_liquidar()`** se simplificó - ya no necesita el `.filtered(lambda a: not self.search_count([('anticipo_id', '=', a.id)]))` posterior: `state == 'aplicado'` ya significa "sin liquidar" por sí solo (antes hacía falta ese filtro extra porque un Anticipo podía seguir en `aplicado` con una Liquidación ya registrada en otro lado).
- **Reporte "Viáticos sin Liquidar" y `viaticos_sin_liquidar_count`** (ver secciones anteriores) se simplificaron igual - el domain que antes decía `('order_id.esta_liquidado', '=', False)` ya no hace falta: excluir `state='liquidado'` (columna) o filtrar `state='aplicado'` (reporte) alcanza por sí solo.

**`_prepare_sync_vals()` no cambió** (siempre mandó `state: 'enviado'` al crear del lado Solicitante) - pero **`_pull_payment_order_status()` SÍ necesitó un ajuste**, ver la sección siguiente ("Bug real: `_pull_payment_order_status()` trataba `aplicado` como terminal"). El Comprobante de Pago (`report/account_payment_order_report.xml`) no cambió - ya trabajaba genéricamente con `factura_ids`/`pago_ids`/`move_id`/`cuenta_ajuste_id` del registro que sea.

Verificado en `construtec_test` (`-u construtec_account_payment_order_19 --stop-after-init --no-http`, luego dos scripts por `odoo-bin shell`): un Anticipo normal se crea, se aplica, se le adjunta una factura por el monto exacto y se concilia SOBRE SÍ MISMO (mismo id antes y después, `state='liquidado'`, `move_id` seteado, cero registros nuevos creados); `action_cancelar()` lo regresa a `state='aplicado'` (no borrador); `action_cancel()` queda bloqueado en `aplicado` (`UserError`, antes no había ningún chequeo); `action_cancelar_anticipo_aplicado()` funciona normalmente sobre un Anticipo `aplicado` sin liquidar; Pago Directo sigue funcionando exactamente igual (`borrador`→`liquidado` vía Conciliar→`borrador` vía Cancelar); `tipo` ya no ofrece `'liquidacion'` en su Selection. Por separado, se verificó que `viaticos_sin_liquidar_count` y el reporte "Viáticos sin Liquidar" siguen funcionando correctamente con el nuevo modelo de un solo registro (una Orden que se liquida deja de contar/aparecer, una que sigue pendiente sigue contando/apareciendo).

### Bug real: `_pull_payment_order_status()` trataba `aplicado` como terminal - Community nunca se enteraba de la Liquidación

Detectado por el usuario razonando en voz alta sobre el modelo: "eso se comunica con community para decir que la solicitud de viáticos ya está liquidada" - correcto, y **no estaba pasando**. `_pull_payment_order_status()` (`res_company.py`, el mecanismo que ya existía para reflejar en Community el Enviado/Aprobado/Rechazado/Aplicado real de Enterprise) consideraba `'aplicado'` un estado TERMINAL - una vez que la copia local de Community llegaba a `aplicado`, dejaba de consultarlo para siempre. Desde la fusión de Liquidación dentro de Anticipo (sección anterior), `'aplicado'` **ya no es terminal** - el mismo registro en Enterprise puede seguir avanzando hasta `'liquidado'` - así que Community se quedaba congelada en "Aplicado" sin enterarse jamás de que ya se liquidó.

**El fix**: el domain de `pendientes` cambió de `('state', 'not in', ('aplicado', 'rechazado', 'cancelado'))` a `('state', 'not in', ('liquidado', 'rechazado', 'cancelado'))` - ahora una Orden en `aplicado` sigue consultándose en cada corrida del cron hasta que Enterprise la liquide (o la cancele/rechace). `fetch_order_status()` (`tools/enterprise_sync_api.py`) no necesitó ningún cambio - ya traía `state` genéricamente, sin asumir ningún valor final en particular.

**Corregido**: los botones "Liquidar" (`action_conciliar`), "Cancelar" (`action_cancelar`), "Cancelar" de Anticipo Aplicado (`action_cancelar_anticipo_aplicado`), "Aplicar" (`action_aplicar`) y la variante "Volver a Borrador" de `state='enviado'` ganaron `or not es_procesador` en su `invisible=` (mismo patrón que ya usan "Aprobar"/"Rechazar") - pedido explícito del usuario tras la nota de seguridad anterior: "en community... el botón... borrador o cancelar debe estar oculto para todos". Deliberadamente **NO** se tocó `action_cancel()` (el "Cancelar" sin restricción de grupo, antes de Aplicar) ni la variante "Volver a Borrador" de `state='rechazado'` - ninguno de los dos mueve dinero real ni depende de Enterprise; son la forma normal en que el propio solicitante retira/corrige su solicitud en Community antes de que se procese, y deben seguir abiertos ahí. Solo view-level (`invisible=`) - no se agregó un chequeo nuevo en Python (el riesgo real ya era acotado, ver el razonamiento que sigue); si se quiere reforzar también server-side, sería agregar un chequeo de `company.payment_order_role == 'procesador'` similar a `_check_es_administrador_contable()`.

Razonamiento original del gap (contexto, ya no aplica tal cual): la copia LOCAL de Community de una Orden sincronizada nunca tiene `move_id`/`factura_ids`/`pago_ids` reales (esos campos son puramente locales a Enterprise, nunca viajan) - si un usuario de Community con `account.group_account_manager` clickeara "Cancelar" sobre una copia ya `liquidado`, solo cambiaría el `state` local de vuelta a `aplicado` sin revertir nada real, y el siguiente pull lo volvería a poner en `liquidado` (Enterprise sigue siendo la fuente de verdad) - impacto bajo, pero confuso para quien lo viera, y ahora ya ni siquiera se ve.

Verificado con un mock de `fetch_order_status()` (sin depender de dos instancias reales corriendo): una Orden local en `state='aplicado'` sigue apareciendo en el domain de `pendientes` (antes de este fix, quedaba excluida); al simular que Enterprise ya la tiene en `'liquidado'`, el pull la actualiza correctamente; una Orden ya `liquidado` localmente queda excluida del domain (terminal real).

### Bug real: una factura/pago conciliado que se resetea a Borrador desaparecía de la Orden, y la Liquidación se quedaba "fantasma"

Reportado por el usuario probando una Orden ya Liquidada de punta a punta: factura con asiento, pago con asiento, Orden liquidada con su propio asiento regularizador. Al resetear el **pago** a Borrador desde Contabilidad > Pagos (`action_draft()`, fuera de esta Orden por completo), pasaron dos cosas mal: (1) la Orden **no cambió de estado** - se quedó "Liquidado" aunque la conciliación ya no era válida (una de sus líneas ya no estaba posteada); (2) el pago **desapareció** de `pago_ids` en la Orden, aunque `payment_order_id` seguía apuntando ahí.

**Causa de la desaparición**: `factura_ids`/`pago_ids` tenían un `domain=` filtrando por estado (`state='posted'`/`state in ('in_process','paid')`). Un `domain=` en un campo `One2many` se aplica también **al leer**, no solo al buscar candidatos para adjuntar (mismo mecanismo ya documentado arriba para el bug de `pago_ids` con `state='posted'` en la tabla de deltas v16→v19) - en cuanto el pago pasó a `draft`, dejó de calificar y el campo simplemente dejó de "verlo", aunque el registro siguiera existiendo y apuntando aquí. **El fix**: se quitó el filtro de estado de AMBOS domains - todo el código que necesita solo los posted/conciliables ya filtra explícitamente por `state` en Python (`_compute_diferencia_conciliacion`, `action_conciliar`, `action_crear_pago`), así que el domain del campo nunca aportaba nada más que esta desaparición.

**Causa de que la Orden no reaccionara**: nada en el core de Odoo avisa a un modelo custom cuando una factura/pago que tenía vinculado cambia de estado - `account.move.button_draft()`/`account.payment.action_draft()` no saben que `payment_order_id` existe. Había que detectarlo activamente.

**El fix, propuesto explícitamente así por el usuario** ("cambie el estado de la orden de pago de liquidado a aplicado... y que todo quede plasmado en el chatter"):
- `account_move.py`/`account_payment.py` ganan un `write()` override: si `state` cambia a algo distinto de posted/in_process/paid para un documento cuya Orden está en `state='liquidado'`, se llama a `orden._reaccionar_a_documento_desconciliado(documentos, nuevo_estado)` **después** de que el `super().write()` ya aplicó el cambio.
- `_reaccionar_a_documento_desconciliado()` (en `account_payment_order.py`) llama a `_deshacer_conciliacion()` - un método nuevo, extraído del cuerpo de `action_cancelar()` (unreconciliar+cancelar+eliminar `move_id`, regresar `state` a `aplicado`/`borrador` según el tipo, exactamente igual que el botón "Cancelar" manual) - y deja un mensaje en el chatter de la Orden nombrando qué documento cambió y a qué estado.
- **Deliberadamente sin `_check_es_administrador_contable()`** en la cascada automática (a diferencia de `action_cancelar()`, que sí lo exige) - quien reseteó la factura/pago ya tenía el permiso de Contabilidad correspondiente para hacer ESO; esto es solo una consecuencia automática sobre la Orden, no una acción nueva que alguien esté ejecutando directamente sobre ella.
- Reversión en dos pasos si el Anticipo ya estaba Liquidado y se quiere revertir del todo: `action_cancelar()` (Liquidado → Aplicado) y LUEGO `action_cancelar_anticipo_aplicado()` (Aplicado → Cancelado) - cada uno deshace su propio efecto contable por separado, mismo patrón ya usado en la fusión de arriba.

**También hacía falta para Community** ("esto también debe ser sincronizado a community... para poder controlar bien qué pagos van a estar en qué órdenes"): con el fix anterior de esta misma sesión, `_pull_payment_order_status()` ya no trataba `'liquidado'` como terminal para poder AVANZAR de `aplicado` a `liquidado` - pero seguía tratándolo como terminal para dejar de consultar una vez llegado ahí, lo cual bloquearía enterarse de que **retrocedió** de `liquidado` a `aplicado` por este mismo bug. Se quitó `'liquidado'` del todo de los estados terminales - ahora solo `'rechazado'`/`'cancelado'` lo son; cualquier Orden en cualquier otro estado se sigue consultando indefinidamente, precisamente porque ya no se puede asumir que el estado solo avanza.

Verificado en `construtec_test` con 4 escenarios: (1) Anticipo Liquidado, resetear el PAGO a Borrador → Orden regresa a Aplicado, el pago SIGUE visible en `pago_ids` (ya en estado Borrador), chatter actualizado; (2) mismo Anticipo, resetear la FACTURA a Borrador → mismo resultado, la factura sigue visible; (3) Pago Directo Liquidado, resetear su pago → regresa a Borrador (no Aplicado, tipo-consciente); (4) resetear un pago de una Orden que NO estaba Liquidada → no pasa nada raro, sin mensaje espurio en el chatter. Por separado, se verificó con un mock de `fetch_order_status()` que una Orden en `liquidado` localmente sigue en la lista de pendientes a consultar, y que una reversión real (Enterprise reporta `aplicado` donde Community tenía `liquidado`) se refleja correctamente.

### Reporte "Viáticos sin Liquidar": clic en una fila abre el form (función normal de Odoo)

Pedido explícito del usuario sobre esta lista (`views/account_payment_order_viaticos_report_views.xml`): un clic en cualquier fila debe abrir esa Orden en su vista de formulario - "una función normal de Odoo".

- **`view_mode` de la acción** pasó de `list,pivot` a `list,form,pivot` - sin `form` en la lista de vistas, la acción no tiene a dónde navegar al abrir un registro (no hacía nada al hacer clic). No se registró un `view_id` propio para el form - Odoo usa el form por defecto del modelo (`view_account_payment_order_form`, el mismo formulario real con los botones Liquidar/Cancelar/etc.), que es justo lo que se quería.
- **Intento revertido en el camino**: se probó primero `editable="bottom"` + `open_form_view="1"` (para sumar edición masiva - un pedido inicial del usuario sobre esta misma lista) - pero una lista `editable` intercepta el clic en CUALQUIER celda para entrar en edición inline (`onCellClicked` en `list_renderer.js`), y solo abre el form desde un ícono dedicado aparte, no desde un clic normal en la fila. El usuario aclaró que lo que quería era el comportamiento simple y estándar (clic en la fila = abrir form, "actualmente solo está a la vista lista y no hay más datos") - **`editable`/`open_form_view` se quitaron**, la lista volvió a ser de solo navegación (`create="0" delete="0"`, sin más). Si más adelante se retoma la edición masiva, hay que aceptar el trade-off: con una lista `editable`, un clic normal en la fila deja de abrir el form directamente - sería edición inline + un ícono aparte para abrir el form, no ambos con el mismo clic.

Verificado con `get_view()`: la acción incluye `form` en `view_mode`; el arch de la lista ya NO trae `editable` ni `open_form_view`.

## Anticipo Materiales: `tipo` nuevo, líneas de producto, Pagar a Jefe/Proveedor

Fase 2 del proyecto (ver más arriba) - migrar la vieja "Solicitud de Materiales" de `construtec_materials_19` (Community, retirado el 2026-08-18) hacia este mismo modelo, siguiendo exactamente el patrón ya usado por Viáticos: mismo modelo/módulo instalado en ambos lados, mismo ciclo enviar/aprobar/aplicar/liquidar, mismo mecanismo de sync. Diseñado y aprobado con el usuario en sesión de planeación antes de construir (plan guardado, dos correcciones reales del usuario incorporadas antes de empezar - ver abajo). **Pass 1 de 4 ya construido y verificado**; Pass 2 (Orden de Compra), Pass 3 (compra directa vs. bodega propia) y Pass 4 (conciliación, debería ser gratis) siguen pendientes, cada uno en su propia pasada verificable.

**Dos correcciones reales del usuario sobre el diseño inicial, antes de tocar código**:

Por eso `account.payment.order.material.line` **no tiene** un campo `requisition_type`/interno-compra: esa determinación queda implícita en si Enterprise le resuelve o no un `product_id` a la línea (ver más abajo).

El diseño final para esto (Pass 3, no construido todavía) no necesita código de inventario en absoluto - se resuelve 100% con el tipo de producto que Enterprise elija por línea (almacenable = reposición de bodega propia, flujo nativo sin cambios; Servicio/no almacenable = sin picking, factura directa contra cuenta de gasto) - ver el plan completo si se retoma.

### Pass 1 (construido): `tipo='anticipo_materiales'`, líneas, Pagar a

### Pass 3 y Pass 4: confirmados sin código nuevo, verificados de punta a punta en un servidor real

Verificado en `construtec_test` con un servidor real (`odoo-bin server`, no solo `shell`) y el navegador, no solo scripts - ciclo completo: crear Orden `anticipo_materiales` con una línea de materiales → Enviar → Aprobar → llenar Diario/Cuenta de Anticipos/`pagar_a='proveedor_directo'`/`proveedor_materiales_id` → Aplicar (pago real creado) → asignar `product_id` (producto nuevo tipo **Servicio**, a propósito, para probar el caso "compra directa a obra") → Generar Orden de Compra (agrupó bien, `partner_id`/monto/origin correctos) → Confirmar la OC → **confirmado: sin ningún botón/smart-button de recepción, sin `stock.picking`** (exactamente el comportamiento pedido, cero código de inventario) → crear la factura del proveedor desde la propia OC (`action_create_invoice()` nativo) → postearla (trajo impuesto, `$575` vs. el pago original de `$500` - diferencia real) → vincularla a `factura_ids` → `action_crear_pago()` para cubrir la diferencia del impuesto (`$75`) → `action_conciliar()` ("Liquidar") → **`state='liquidado'`, asiento generado, chatter completo Borrador→Enviado→Aprobado→Aplicado→Liquidado**. Ningún código nuevo hizo falta para Pass 3/Pass 4 - se confirma la hipótesis del diseño.

**Bug real encontrado en esta verificación (no se habría visto con `odoo-bin shell`/rollback - solo probando la vista real)**: `material_line_ids` tenía `readonly="state != 'borrador'"` a nivel de todo el campo (heredado del mismo patrón que `viaticos_line_ids`) - eso deja la lista ENTERA de solo lectura en cuanto la Orden pasa a `aplicado`, incluyendo `product_id`, justo el único momento en que hace falta editarlo (después de Aplicar, antes de Generar Orden de Compra). El botón "Generar Orden de Compra" aparecía, pero no había forma de asignar productos desde el formulario.

**El fix**: se quitó el `readonly` a nivel del campo `material_line_ids` (ahora `readonly="state not in ('borrador', 'aplicado')"`, para seguir bloqueando la lista completa en cualquier otro estado) y se movió un `readonly="parent.state != 'borrador'"` a cada columna EXCEPTO `product_id` (que queda editable mientras la lista en general no esté bloqueada) - así el jefe de técnicos no puede tocar `product_name`/`qty`/etc. una vez enviada la Orden, pero Enterprise sí puede resolver `product_id` después de Aplicar. `product_id` también pasó de `optional="hide"` a `optional="show"` (se necesita ver/usar en cada Orden real, no tiene sentido esconderlo por defecto).

**Segundo bug de vista, mismo patrón que el de Pass 1**: al escribir el primer intento de este fix se usó `readonly="state != 'borrador'"` (sin `parent.`) en las columnas - mismo `ParseError` de "Access Rights Inconsistency" que ya se documentó arriba (`state` no existe en el modelo de la línea). **Lección para cualquier columna dentro de una lista anidada de un One2many en este módulo**: cualquier condición que necesite un campo del ENCABEZADO (`state`, `es_procesador`, `tipo`, etc.) debe usar `parent.<campo>`, nunca el nombre del campo a secas - Odoo 19 valida esto al cargar la vista y tumba el registro del módulo entero (`-u` falla) si se referencia un campo que no existe en el modelo de la línea.

## Catálogo SAT en la Solicitud de Materiales

Pedido explícito del usuario: al capturar líneas de materiales, poder elegir de un catálogo real de productos por proveedor (derivado de los Documentos SAT) en vez de escribir todo a mano - con dos condiciones explícitas: (1) que el catálogo **prefiera** mostrar lo del proveedor ya indicado en la línea, sin restringir a solo eso; (2) que no se llene de basura (el catálogo SAT trae de todo - combustible, servicios, etc. - no solo materiales).

- **Nueva dependencia**: `construtec_sat_catalog_sync_19` (antes solo-Community, ahora también desplegado en este árbol de Enterprise - ver el CLAUDE.md de ese módulo). `account.payment.order.material.line` gana `catalogo_id` (Many2one `construtec.materials.catalog.mirror`), **opcional, nunca obligatorio** - `product_name` sigue siendo texto libre, elegir del catálogo es pura conveniencia.
- **Autocompletado** (`_onchange_catalogo_id()`, `account_payment_order_material_line.py`): elegir una entrada llena `product_name`/`vendor_name`/`estimated_price` desde el catálogo - todo editable después, mismo patrón que el resto de autocompletados del módulo (`_onchange_partner_id`, etc.).
- **Preferencia por proveedor sin restringir**: el campo en la vista (`views/account_payment_order_views.xml`, pestaña Materiales) pasa `context="{'vendor_hint': vendor_name}"` - el `name_search()` con preferencia por proveedor vive en `construtec_sat_catalog_sync_19` (no aquí), reordena resultados sin nunca ocultar ninguno. Ver el CLAUDE.md de ese módulo para el mecanismo completo.
- **Filtro por `bien_o_servicio`, aquí y no en el origen** (segunda corrección del usuario: primero se descartó curar proveedores a mano; después, se descartó también filtrar en Enterprise al sincronizar - "se van a sincronizar todos los productos... en un futuro voy a necesitar los productos de tipo servicio también" para otra sección aún no construida). El catálogo (`construtec.materials.catalog.mirror`) sincroniza bienes Y servicios sin ningún filtro propio - el filtro real vive en `catalogo_id` (`domain="[('bien_o_servicio', '=', 'B')]"`, `account_payment_order_material_line.py`), porque la Solicitud de Materiales específicamente solo necesita Bienes. Un futuro consumidor de Servicios agregaría su propio campo/domain con `'S'`, sin tocar el catálogo ni la sincronización.
- **Verificado de punta a punta con un servidor real y el navegador** (2026-09-01): proveedor curado con una entrada de catálogo → aparece en el picker de la línea → seleccionarla llena Material/Proveedor Sugerido/Precio Estimado y recalcula Subtotal/Total a Acreditar en vivo, confirmado visualmente en `construtec_test`.

### Ajustes del pull del Catálogo de Materiales, alojados aquí (no en `construtec_sat_catalog_sync_19`)

`construtec_sat_catalog_sync_19` ahora jala directo desde Enterprise (ver su CLAUDE.md, "Sincronización Community↔Enterprise: PULL, no push") - los campos de conexión/intervalo (`materials_catalog_sync_*`) viven en `res.company`, definidos en ESE módulo (`depends: ['base']` solamente). Visible solo cuando `payment_order_role == 'solicitante'` (mismo criterio que "Sincronización de Empleados" - el pull solo tiene sentido en Community).

**Reutiliza las MISMAS credenciales de `payment_order_sync_*`, sin pedirlas dos veces** (segunda corrección, misma pasada - pedido explícito del usuario: "utiliza las mismas credenciales que ya están para sincronizar solicitudes de pago, es al mismo Odoo"): el bloque "Catálogo de Materiales" ya **no** tiene sus propios campos de URL/Base de Datos/Usuario/API Key - solo el toggle "Sincronización Habilitada" + intervalo + botón "Sincronizar ahora". `res_company.py` gana `_sync_materials_catalog_credentials()`, llamado desde `create()`/`write()` cada vez que cambia cualquiera de los 4 `payment_order_sync_*` - copia esos mismos 4 valores hacia `materials_catalog_sync_url`/`_db`/`_login`/`_api_key` (los campos que `construtec_sat_catalog_sync_19` sigue usando internamente para el pull, sin cambios ahí). Usa `super(ResCompany, company).write(...)` para el espejo (evita recursión innecesaria - el nuevo `vals` no contiene ninguna clave `payment_order_sync_*`, así que el guard `any(f in vals for f in ...)` de todas formas no volvería a dispararse aunque se llamara `write()` normal). Verificado con `odoo-bin shell`: escribir cualquiera de los 4 campos de Solicitudes de Pago actualiza los 4 del Catálogo de Materiales; cambiar solo uno de los 4 vuelve a espejar los 4 correctamente (no solo el que cambió); escribir un campo no relacionado (`materials_catalog_sync_enabled`) no dispara el espejo ni entra en loop.

**Bug real reportado en producción, encontrado el mismo día**: en `erp.construtecasesores.com`, con `payment_order_sync_*` ya configurado desde antes (Solicitudes de Pago funcionando), el botón "Sincronizar ahora" del Catálogo de Materiales fallaba con *"incompleta (falta URL, base de datos, usuario o API Key)"* pese a que las credenciales de Solicitudes de Pago sí estaban completas. Causa: el espejo (`_sync_materials_catalog_credentials()`) solo se dispara dentro de `write()`/`create()` cuando esos 4 campos **cambian de valor** - una compañía cuyas credenciales ya estaban guardadas ANTES de que este mecanismo existiera nunca los volvió a escribir, así que el espejo nunca corrió para ella. `post_init_hook` no sirve aquí (confirmado leyendo `odoo/modules/loading.py`: solo corre en instalación fresca, `update_operation == 'install'`, nunca en `-u` de un módulo ya instalado) y un script de migración habría sido más trabajo del necesario. **El fix**: `action_sync_materials_catalog_now()` (override, `res_company.py`) llama a `_sync_materials_catalog_credentials()` justo antes de delegar a `super()` - cada clic en "Sincronizar ahora" se auto-repara solo, sin depender de que alguien vuelva a guardar las credenciales de Solicitudes de Pago. También se agregó la misma llamada dentro de `_cron_sync_employees_from_enterprise()` (respaldo periódico, ya recorre las compañías Solicitante correctas). Verificado con `odoo-bin shell`: compañía con `payment_order_sync_*` completo pero `materials_catalog_sync_*` en blanco (forzado a nivel SQL, con `env.flush_all()`/`env.invalidate_all()` en los puntos correctos para que la prueba sea representativa) - el botón corrige el espejo y sincroniza en el mismo clic, sin necesitar re-guardar nada.

## Cargar Cotización de Proveedor con IA (Community, `tipo='anticipo_materiales'`)

Pedido explícito del usuario: el jefe de técnicos sube un archivo (PDF, imagen/captura de pantalla, o Word) con una cotización real de un proveedor, y Odoo la transcribe automáticamente hacia `material_line_ids` - **siempre como sugerencia revisable, nunca aplicada a ciegas**. Diseñado en sesión de planeación (`AskUserQuestion` para 3 decisiones antes de construir: proveedor de IA, soporte de Word, y aceptación de que el archivo sale hacia un servicio externo) - ver el plan guardado de esta sesión para el razonamiento completo.

- **`tools/quote_extraction_api.py`** (nuevo) - cliente delgado para la API de Mensajes de Anthropic (Claude), mismo estilo que `tools/enterprise_sync_api.py` (requests puro, `QuoteExtractionError` propia, sin el SDK oficial `anthropic` - deliberado, este módulo mantiene cada integración externa como su propio cliente HTTP pequeño). Tres funciones públicas (`extract_quote_from_image`/`_pdf`/`_text`) arman un `content` block distinto (`image`/`document`/`text`) y comparten `_call_messages_api()`, que fuerza **tool use** (`tool_choice: {'type': 'tool', 'name': 'registrar_cotizacion'}`) con un JSON Schema (`proveedor`, `lineas: [{descripcion, cantidad, unidad, precio_unitario}]`) - salida estructurada garantizada, nunca se parsea texto libre de la IA. Modelo `claude-sonnet-5`. Fotos grandes de celular se reducen con Pillow (ya disponible en este entorno) antes de codificar a base64, para bajar costo de tokens.
- **`models/account_payment_order_quote_import_wizard.py`** (nuevo) - un solo wizard (`TransientModel`) con `state` interno (`upload`/`review`), no dos wizards encadenados (la lista de líneas extraídas tendría que viajar por `context` entre dos modelos distintos, más frágil que un solo `state` - mismo idioma que ya usa el resto de este módulo para `action_*` que regresan un `act_window` apuntando al mismo registro).
  - **`action_extraer()`**: valida archivo + `company.anthropic_api_key` presentes (nada se gasta si falta cualquiera de los dos), detecta el tipo por extensión, llama a la función correspondiente. **Todo en una sola transacción, decisión explícita del usuario** ("aceptable que el archivo se pierda, reintentar es simple") - si `QuoteExtractionError`, se relanza como `UserError` y **nada se guarda** (ni el `ir.attachment` ni ninguna línea del wizard sobreviven, porque el `ir.attachment` real se crea DESPUÉS de que la llamada a la IA ya tuvo éxito, nunca antes). Si tiene éxito: crea el `ir.attachment` sobre la Orden (trazabilidad), llena `line_ids`, dejachatter, pasa a `state='review'`.
  - **`action_aplicar()`**: exige al menos una línea con `incluir=True` (nunca aplica una lista vacía en silencio); crea líneas reales vía el `create()` normal de `account.payment.order.material.line` (reutiliza el respaldo `description → product_name` ya existente, sin lógica nueva ahí); llena `proveedor_materiales_name` en el encabezado **solo si está vacío** (nunca pisa lo que el jefe ya escribió a mano).
- **`.docx` (Word)**: `_extraer_texto_docx()` usa `python-docx` con **import perezoso** (misma técnica que `pdfminer.six` en `construtec_account_19/models/sat_retention_import.py` - el módulo sigue cargando en cualquier entorno sin la librería instalada; solo revienta, con un `UserError` claro en español, si alguien realmente sube un `.docx` sin tenerla). Extrae párrafos **y tablas** (una cotización casi siempre viene en tabla) concatenados en un solo texto plano, enviado a `extract_quote_from_text()` (sin visión, más barato/confiable que convertir a imagen). Verificado con un `.docx` real generado con la propia librería (párrafo + tabla 2x3) - el texto extraído conserva el contenido de ambas partes correctamente.
- **`python-docx` no estaba instalado en ningún Python embebido de este workspace** - se instaló localmente (`Odoo19E\python\Scripts\pip.exe install python-docx`) para poder verificar el camino real. **Pendiente real, no resuelto todavía**: cómo está armado el contenedor Docker de Community en producción (imagen oficial vs. imagen propia) determina el comando exacto para instalarlo ahí de forma durable - un `pip install` manual dentro del contenedor se pierde en el próximo `docker recreate` si la imagen es la oficial sin modificar. Enterprise no lo necesita (el botón nunca aparece ahí, `es_procesador` lo oculta, y el import perezoso evita que el módulo necesite la librería para cargar).
- **Vista**: botón "Cargar Cotización" (`views/account_payment_order_views.xml`, pestaña Materiales, arriba de la lista), `invisible="state != 'borrador' or not id or es_procesador"` - `not id` evita abrirlo sobre un registro sin guardar (`NewId`), `es_procesador` lo oculta en Enterprise. `groups="account.group_account_invoice"` (el mismo nivel base de acceso a este módulo en Community - sin grupo nuevo, ver más abajo).
- **`res.company.anthropic_api_key`** (nuevo campo, Char) - bloque nuevo "IA para Cotizaciones (Anthropic)" en Ajustes > Facturación (`views/res_config_settings_views.xml`/`models/res_config_settings.py`), mismo patrón `password="True"` que `payment_order_sync_api_key`, gated a `payment_order_role == 'solicitante'` (solo se usa desde Community). Campo independiente de las demás credenciales de este módulo (proveedor distinto, Anthropic no es Enterprise).

### Catálogo de Proveedores + auto-vinculación de proveedor/material (2026-09-02)

Extensión pedida directamente por el usuario: además de fecha/proveedor/líneas, "Cargar Cotización" ahora resuelve el proveedor y cada material contra catálogos **conocidos** (`construtec.materials.vendor.mirror`/`construtec.materials.catalog.mirror`, ambos en `construtec_sat_catalog_sync_19` - ver su CLAUDE.md para el modelo/pull nuevos) - si ya existen, se vinculan; si no, se crean marcados `pendiente_verificar`. Tres decisiones confirmadas vía `AskUserQuestion`: los nuevos quedan marcados para revisión, el catálogo de proveedores sale de TODOS los Documentos SAT recibidos (no solo materiales ya catalogados), y la comparación es texto simple normalizado (nunca asistida por IA - un nombre distinto no calza, se crea uno nuevo).

- **`_normalizar(texto)`** (module-level, `account_payment_order_quote_import_wizard.py`) - mayúsculas + colapsar espacios, comparación EXACTA tras normalizar. Sin fuzzy matching, sin ayuda de la IA - decisión explícita, más predecible que "adivinar" cuál registro es "el mismo".
- **`_resolver_proveedor(nombre_extraido)`**: busca en `construtec.materials.vendor.mirror` por nombre normalizado (comparación en Python sobre `search([])`, no un domain SQL con `ilike` - tabla chica, evita problemas de espacios/mayúsculas que un `ilike` no resuelve solo). Si no hay nombre extraído (IA no detectó proveedor), no resuelve/crea nada - degrada limpio al comportamiento anterior (solo texto libre, sin catálogo). `sudo()` deliberado (llamador de confianza) - `base.group_user` solo tiene lectura sobre este catálogo.
- **`_resolver_material(proveedor, descripcion, precio_unitario)`**: busca en `construtec.materials.catalog.mirror` **acotado a `bien_o_servicio='B'` Y al proveedor ya resuelto** (`partner_name` exacto) - evita que "Cemento" de un proveedor se confunda con el de otro (verificado explícitamente: mismo texto, dos proveedores distintos, dos entradas de catálogo distintas, nunca se mezclan). Sin proveedor resuelto, tampoco intenta nada - vincular un material a un catálogo sin saber de qué proveedor es sería inventar un dato que no está.
- **Ambos resolvers devuelven `(record, created)`** - el wizard usa `created` solo para el resumen del chatter ("N conocidos, M nuevos"), no cambia el comportamiento.
- **Campos nuevos**: `proveedor_catalogo_id` (wizard) y `catalogo_id` (línea del wizard) - se copian a `account.payment.order.proveedor_materiales_catalogo_id` (encabezado, nuevo, solo informativo - `proveedor_materiales_name` sigue siendo lo único que viaja por sincronización) y a `account.payment.order.material.line.catalogo_id` (la línea real, ya existía como campo pero antes SIEMPRE quedaba vacía al venir de una cotización - ahora llega resuelta) en `action_aplicar()`, con el mismo criterio "solo si está vacío" que ya usa `proveedor_materiales_name`.

Verificado con `odoo-bin shell` en `construtec_test`, 3 escenarios reales: (1) proveedor y material YA conocidos (mismo proveedor) → vinculados, cero duplicados creados; (2) proveedor y material NUEVOS → ambos creados con `pendiente_verificar=True`, sin `origin_id`, la línea real y el encabezado quedan vinculados a ellos; (3) mismo texto de material que en (1) pero de un proveedor DISTINTO → correctamente NO vinculado al material de (1), se crea uno nuevo scoped a ese otro proveedor. También verificado que múltiples entradas locales sin `origin_id` (Integer vacío, no `0` real a nivel SQL) no chocan contra el `unique(origin_id)` ya existente - mismo comportamiento de Postgres con `NULL` ya usado/documentado en otras constraints de este proyecto. `-u` limpio de `construtec_sat_catalog_sync_19` + este módulo sobre `construtec_test`, sin `ERROR`/`CRITICAL` nuevos.

### Bug real en producción: el botón "Cargar Cotización" nunca aparecía para el jefe de técnicos (2026-09-02)
