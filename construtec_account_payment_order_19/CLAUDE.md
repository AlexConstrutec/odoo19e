# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

`account.payment.order` — a header model with a `tipo` field (`anticipo` / `liquidacion` / `pago_directo`) representing three flavors of a real Construtec accounting flow: money moves through an intermediary (an advance to a contact, or an employee reimbursement) and later has to be reconciled against vendor bills that belong to a **different partner** than the payment. Native Odoo reconciliation works per-partner/account and can't do this on its own. Migrated from the Odoo 16 module `bolson` (`..\Odoo16\bolson\`, "Manejo de cajas chicas y liquidaciones").

All three `tipo` values now have real logic — `pago_directo` was added in a later round of this session by **reusing** Liquidación's engine (see below), not by writing a separate implementation.

## What each `tipo` means, and the real workflow between them

**Cuarto valor, `anticipo_viaticos`** (ver la sección "FUSIÓN" y la de UX más abajo): comparte EXACTAMENTE el mismo ciclo enviar/aprobar/rechazar/aplicar que `anticipo` (constante `ANTICIPO_TIPOS = ('anticipo', 'anticipo_viaticos')` en `account_payment_order.py`, usada en todos los guards) - la única diferencia real es que trae `viaticos_line_ids`/captura de empleado y es el único que Community ve. Todo lo escrito abajo sobre "Anticipo" aplica igual a los dos, salvo donde se diga lo contrario.

- **Anticipo**: hand a contact money up front. `action_aplicar()` creates a normal `account.payment` (outbound, `partner_type='supplier'`) to `partner_id`, posted with `destination_account_id` forced to `cuenta_anticipo_id` (an "anticipos por liquidar" account) instead of the contact's normal payable. **`cuenta_anticipo_id` must be `account_type in ('asset_receivable', 'liability_payable')`** (enforced via the field's `domain=`) — anything else (e.g. a plain expense account) makes it invisible to `action_conciliar()`'s netting logic later and every subsequent Liquidación will falsely report a mismatch. `factura_ids` is **optional** on an Anticipo (attach one only if you already know which invoice it'll cover) — see the auto-detection note below. **`payment_method_line_id`** (domain `journal_id.outbound_payment_method_line_ids`, reset on journal change via `_onchange_journal_id_payment_method`) lets the user pick the payment method (Manual, Cheque, etc.) before applying; if left empty, `action_aplicar()` omits the key entirely from the `create()` vals so `account.payment`'s own `_compute_payment_method_line_id` picks a sensible default from the journal — passing `False` explicitly would instead pin it to "no method" and break `action_post()`.
- **Liquidación**: the one ported from `bolson`. Takes N vendor bills (`factura_ids`, possibly different suppliers) + N payments (`pago_ids`, typically the originating Anticipo's payment, pre-attached automatically), nets them, and posts one regularizing `account.move` that reconciles everything — tolerating a mismatch via `cuenta_ajuste_id` if the totals don't line up exactly. **Cannot be created directly** — see below.
- **Pago Directo**: the 1:1 case — someone (e.g. an employee) already paid a vendor bill out of pocket, in the company's name. Odoo ends up with a vendor bill (in the *vendor's* name) and needs a reimbursement payment (in the *employee's* name); it's reconciled with `action_conciliar()`/`action_cancelar()` **exactly like Liquidación** — same methods, same engine, the guard just accepts both tipos now (`if self.tipo not in ('liquidacion', 'pago_directo'): raise ...`). No `anticipo_id` requirement (that constraint only fires for `tipo == 'liquidacion'`). Typically 1 factura + 1 pago, but nothing enforces that — it's the identical N:M mechanism.

**Anticipo → Liquidación is a required, one-directional flow** (user's explicit instruction this session): a Liquidación can't be created standalone. `_check_anticipo_id()` (`@api.constrains('tipo', 'anticipo_id')`) raises `ValidationError` on any `tipo='liquidacion'` record without `anticipo_id` set. The only supported way to get a valid Liquidación is `action_registrar_liquidacion()` on an already-`aplicado` Anticipo, which creates the new order with `anticipo_id` set and `pago_ids` pre-loaded with the Anticipo's own `payment_id`. Pago Directo has **no** equivalent restriction — it's created directly like Liquidación used to be, just without the `anticipo_id` requirement.

**Anticipo vs. Pago Directo auto-detection** (`_aviso_posible_pago_directo()`, called at the end of `action_aplicar()`): if an Anticipo has factura(s) attached whose total exactly matches `monto`, and none of those facturas already have a reconciled payable/receivable line, that's not really a pending-liquidation Anticipo — it's a same-day full payment, i.e. a Pago Directo. The user chose **warn, don't auto-switch**: this returns an `ir.actions.client` / `display_notification` (sticky, type `warning`) instead of silently changing `tipo` or force-reconciling anything. The Anticipo still ends up `aplicado` with its `payment_id` set either way; nothing is blocked.

## Comprobante de Pago (printable voucher)

`report/account_payment_order_report.xml` is bound (`binding_type='report'`) to `account.payment.order` directly, so **Imprimir → Comprobante de Pago** is available on any record regardless of `tipo` — no per-tipo report needed. It shows `tipo`/fecha/contacto/diario, the Facturas table (skipped entirely if `factura_ids` is empty — true for a pure Anticipo with no invoice attached yet), and a "Pago(s)" table built from `o.pago_ids | o.payment_id` (a union, because Anticipo's own generated payment lives in the dedicated `payment_id` field, not in the generic `pago_ids` collection used by Liquidación/Pago Directo). The "Diferencia" row is only rendered when there are facturas to compare against.

## Permissions

Confirmed design this session: **anyone in `account.group_account_invoice`** (the base "Facturación" group, already granted in `ir.model.access.csv`) **can create/edit an order and leave it in `borrador`**. **Only `account.group_account_manager`** ("Administrador") can advance state — `action_aplicar()` (Anticipo → aplicado) and `action_conciliar()`/`action_cancelar()` (Liquidación ↔ aplicado) all call `_check_es_administrador_contable()` first, which raises `AccessError` if `self.env.user.has_group('account.group_account_manager')` is false. This is enforced in **Python, not just hidden buttons** — the buttons also carry `groups="account.group_account_manager"` for UX, but the real gate is server-side since a user could otherwise call the method directly (RPC, automation, etc). No separate access-control-list entry was needed for the manager group: `account.group_account_manager`'s `implied_ids` already includes `account.group_account_invoice` (`..\odoo\addons\account\security\account_security.xml:78`), so it inherits the same CRUD grant. `action_registrar_liquidacion()` has **no** manager gate — it only creates a new `borrador` record, which is already covered by the base create permission.

## Architecture

- **`action_conciliar()`/`action_cancelar()`** (`models/account_payment_order.py`) are the ported `bolson.bolson.conciliar()`/`cancelar()`, guarded with `if self.tipo != 'liquidacion': raise UserError(...)` plus the manager-only permission check above.
- **`factura_ids`/`pago_ids`** are `One2many` via the new `payment_order_id` field added to `account.move`/`account.payment` (`models/account_move.py`, `models/account_payment.py`) — same pattern as the original's `bolson_id`. The form uses `widget="many2many"` on these One2many fields (a deliberate Odoo trick, kept from the original) so users can search/attach *existing* posted bills/payments instead of creating new ones inline.
- **`no_liquidacion`** is a `related` field to itself (`payment_order_id.no_liquidacion`) on both `account.move` and `account.payment`, `store=True, readonly=False`, PLUS an `@api.onchange` + `create()`/`write()` override that looks up an order by that number and sets `payment_order_id` — this looks redundant but it's intentional and matches the original `bolson` pattern: typing a `no_liquidacion` value directly on an invoice/payment auto-attaches it to the matching order.
- **Domain fix vs. the original**: `bolson`'s `facturas` field filtered `[('payment_id', '=', False)]` — that field never existed on `account.move` (checked against `..\odoo\addons\account\models\account_move.py`; only `account.move.line.payment_id` and `account.move.origin_payment_id` exist). Replaced with `[('move_type', 'in', ('in_invoice', 'in_refund')), ('state', '=', 'posted')]`, which also fixes the original never actually restricting to vendor bills.

## Odoo 16 → 19 API deltas that mattered (checked against `..\odoo\addons\account\models\`)

| v16 (`bolson`) | v19 |
|---|---|
| `made_sequence_hole` | renamed **`made_sequence_gap`** |
| `communication` (account.payment) | renamed **`memo`** |
| `payment_state` selection (account.move) | gained a **`blocked`** value — don't hardcode a 6-item list |
| **`account.payment.state`** | **completely different lifecycle**: no longer `draft`/`posted`/`cancel`. Now `draft` / **`in_process`** / **`paid`** / `canceled` / `rejected` (`account_payment.py:36-43`). `action_post()` on a payment lands it in `in_process`, not `posted` — it only reaches `paid` once its "Outstanding Payments/Receipts" bridge account nets to zero (`_compute_state`, `account_payment.py:454-467`). **This bit us**: `pago_ids`'s domain and `action_conciliar()`'s loop originally filtered `state == 'posted'` (copied from the v16 pattern) and silently matched *zero* payments — `orden.pago_ids` came back empty with no error, because a One2many field's `domain=` is enforced on *read*, not just in the UI. Fixed to `state in ('in_process', 'paid')`. If you see a payment mysteriously missing from `factura_ids`/`pago_ids`, check its actual `state` value first, not just whether it "looks posted" in the UI. |
| `account.payment` no longer delegates to `account.move` for `line_ids` | `payment.line_ids` **raises `AttributeError`** — use **`payment.move_id.line_ids`**. The v16 module's `for l in c.line_ids:` relied on old-style `_inherits` delegation that no longer applies. |
| Payments post through an **"Outstanding Payments"/"Outstanding Receipts" bridge account** (`account_type='asset_current'` in this DB, not `asset_cash`) before ever touching the bank | `bolson`'s netting filter (`account_type not in ['asset_cash']`) is **not enough** in v19 — that bridge account passes the same filter, and since it's always a balanced in/out pair *within the payment itself*, including it silently cancels out and produces a totals mismatch that has nothing to do with the real invoice/payment imbalance. Fixed by filtering explicitly to `account_type in ('asset_receivable', 'liability_payable')` — the only two account types that represent an actual amount owed to/from a partner, regardless of what the "other leg" of any given line turns out to be (cash, bridge account, whatever). This is more robust than the original's approach for any Odoo version, not just a v19 patch. |
| `account.payment.reconciled_invoice_ids`/`reconciled_bill_ids` are **computed fields with a custom `_search`** (`_search_reconciled_invoice_ids`, `account_payment.py:783`) that only implements `'in'`/`'='` against a **concrete id** (`browse(value).reconciled_payment_ids.ids`) | Putting `('reconciled_invoice_ids', '=', False)` in a domain silently becomes `browse(False)` → empty recordset → `[('id', 'in', [])]`, i.e. **matches nothing, ever** — not an error, just an empty result. This made `pago_ids` come back empty exactly like the `state` bug above, for a different reason. Fixed by **dropping both from the field's `domain=`** and keeping the check only as a plain Python attribute read inside `action_conciliar()` (`if pago.reconciled_invoice_ids or pago.reconciled_bill_ids: raise UserError(...)`), which goes through the normal compute and works fine. **Lesson for this module**: any computed field with a non-trivial custom `_search` is suspect as a domain filter for `=False`/`!=False` — verify empirically (as done here, via `odoo-bin shell`) rather than assuming `=False` means "is empty" the way it does for a plain stored field. |
| `reconciled_invoice_ids`, `reconciled_bill_ids`, `destination_account_id`, `amount_total_signed`, `amount_untaxed_signed`, `account_type`, `account.account.reconcile`, `account.move.line.reconcile()`/`.remove_move_reconcile()` | unchanged |

## FUSIÓN: Solicitud de Pago + Anticipo son el mismo registro (`account.payment.order`, `tipo='anticipo'`)

**Esto reemplaza el diseño de dos modelos descrito en el resto de esta sección** (que existió durante buena parte de esta sesión: `account.payment.order.request` + un Wizard "Crear Anticipo" que convertía la Solicitud aprobada en un `account.payment.order` real, un segundo registro aparte). El usuario, probando el flujo real de punta a punta, concluyó que la separación era innecesaria y confusa ("creo que la estamos regando") y pidió fusionarlos en un solo registro.

**Qué cambió, en concreto**:
- `account.payment.order.request`/`.line` y el Wizard "Crear Anticipo" **se eliminaron por completo** del módulo (tablas huérfanas en la base de datos tras el `-u` - aceptado, sin migración de datos: el usuario borró los datos reales de producción por su cuenta antes de este despliegue).
- Todos los campos que tenía la Solicitud (`employee_partner_id`, `viaticos_line_ids`, `justificacion_tipo_id`, `origin`/`sync_state`/etc., el mecanismo completo de sincronización RPC) se movieron **tal cual** a `account.payment.order` — ahora conviven ahí con `journal_id`/`cuenta_anticipo_id`/`payment_id`/`factura_ids`/`pago_ids`, que ya existían para Anticipo/Liquidación/Pago Directo. La función a nivel de módulo `_resolve_employee_for_partner()` también vive ahora en `account_payment_order.py` (antes en el archivo eliminado) — `res_partner.py` importa de ahí.
- **`state` es un único Selection en español** ahora: `borrador`/`enviado`/`aprobado`/`rechazado`/`aplicado`/`cancelado`. `enviado`/`aprobado`/`rechazado` solo aplican a `tipo='anticipo'` (el ciclo heredado de la Solicitud); Liquidación y Pago Directo siguen yendo directo de `borrador` a `aplicado` vía `action_conciliar()`, exactamente como antes de la fusión — **no se tocó nada de esa lógica**. Los métodos `action_submit()`/`action_approve()`/`action_reject()`/`action_reset_to_draft()`/`action_cancel()` (nuevo, ported de `.request`) ahora ganan un guard `if self.tipo != 'anticipo': raise UserError(...)` que antes no hacía falta (eran un modelo aparte).
- **`action_aplicar()` ahora exige `state == 'aprobado'`** para `tipo='anticipo'` - cambio de comportamiento confirmado explícitamente con el usuario: **ya no existe el atajo** de aplicar directo desde `borrador` un anticipo creado a mano en Enterprise. Todo anticipo, incluso uno que nunca pasó por Community, debe pasar por Enviar+Aprobar antes de poder Aplicarse (un solo camino auditable).
- **El Wizard desaparece** - los campos que llenaba (`partner_id`, `journal_id`, `cuenta_anticipo_id`, `payment_method_line_id`, `monto`) ya existían en `account.payment.order`; ahora son editables directamente en el formulario mientras `state in ('borrador', 'aprobado')` (antes solo `'borrador'`), para que el contable los llene justo después de Aprobar, sin ningún paso de "conversión" intermedio. El aviso de "Anticipos pendientes de liquidar" que vivía en el Wizard se movió dentro de `action_aplicar()`, encadenado con `_aviso_posible_pago_directo()` vía el mecanismo nativo `next` de `display_notification` si ambos aplican a la vez.
- **`journal_id` dejó de ser `required=True` a nivel de campo** — antes SIEMPRE era obligatorio (tenía sentido: solo existía para Anticipo-ya-con-wizard/Liquidación/Pago Directo, todos creados con diario conocido de entrada). Ahora un Anticipo se crea SIN diario (lo llena el contable después de Aprobar) — **bug real encontrado verificando esto**: quitar `required=True` sin más habría permitido crear una Liquidación/Pago Directo sin diario también (antes lo impedía la constraint de la BD). Fix: nueva `@api.constrains('tipo', 'journal_id')` (`_check_journal_id()`) que exige diario siempre para `tipo != 'anticipo'`, más un chequeo explícito dentro de `action_aplicar()` para `tipo='anticipo'` (mismo patrón que `monto`/`cuenta_anticipo_id`/`partner_id`, que tampoco son `required=True` a nivel de campo).
- **Nueva secuencia real para `name`**: antes, para `tipo in ('anticipo', 'pago_directo')`, `_compute_name()` dejaba un placeholder estático `"Nueva Orden de Pago"` (mismo bug para los dos tipos) — ahora un `create()` override asigna `OP/0001`, `OP/0002`... (secuencia `account.payment.order.sequence`, mismo xmlid reciclado de la vieja secuencia `SOL/` de la Solicitud - `data/account_payment_order_sequence.xml`) para ambos tipos, sin tocar `_compute_name()` (que sigue resolviendo `'Liquidación %s' % no_liquidacion` para `tipo='liquidacion'` exactamente igual que siempre).
- **`no_liquidacion` en `account.payment`/`account.move`**: era un `Integer` que buscaba la Orden de Pago por coincidencia de número (`_onchange_no_liquidacion()`/overrides de `create()`/`write()`) — ahora es un **Many2one real** a `account.payment.order` (`domain=[('tipo','=','liquidacion')]`), sin esos overrides. `payment_order_id` (el otro campo de trazabilidad) no cambió.
- **Seguridad**: las 3 `ir.rule` de la vieja Solicitud (propia/aprobador/compañía) se reemplazaron por versiones que filtran `('tipo', '=', 'anticipo')` explícitamente (`account_payment_order_own_rule`/`_approver_rule`, más una nueva `account_payment_order_global_company_rule`) — sin ese filtro, un `base.group_user` cualquiera habría ganado visibilidad sobre Liquidación/Pago Directo, que nunca tuvo antes. Verificado con un script real: un usuario base puede crear/ver sus propios `tipo='anticipo'`, y un `AccessError` real le impide crear `tipo='pago_directo'`.
- Menú único "Órdenes de Pago" (`action_account_payment_order`) en Community y Enterprise — el menú/acción separado de "Solicitudes de Pago" se retiró.

**Todo lo demás documentado en el resto de esta sección sigue siendo cierto en sustancia** (el mecanismo de sync RPC, la resolución de empleado vía `employee_enterprise_ref`, el respaldo de compañía, el bug de `work_contact_id`, el bug de `puesto`/`departamento` heredados en el Contacto, el bug de `InvalidDomainError`) — solo cambió DÓNDE vive ese código (`account_payment_order.py` en vez del archivo eliminado) y el vocabulario de `state` (español, no inglés). Las menciones a "la Solicitud"/`account.payment.order.request` de aquí en adelante son narrativa histórica de cómo se llegó a este diseño, no una descripción de un modelo separado que siga existiendo.

## Refinamiento de UX inmediatamente posterior: `anticipo_viaticos`, sin catálogo de Tipo de Gasto, un solo campo de contacto

Nada más terminar la fusión de arriba, revisándola, el usuario pidió simplificar más - la separación "Tipo de Gasto" (catálogo) + "Empleado Solicitante" + "Nombre" duplicaba información y no reflejaba bien la intención real. Cambios, todos aplicados sobre el `account.payment.order` ya fusionado (nada de esto vuelve a tocar Liquidación/Pago Directo salvo lo explícitamente indicado):

- **Nuevo valor de `tipo`: `anticipo_viaticos`**, reemplazando por completo al catálogo `account.payment.order.justification.type` (modelo, menú "Tipos de Gasto", seed "Viáticos" y sus filas de `ir.model.access.csv` - **eliminados los cuatro**, decisión explícita del usuario: "eliminar todo por completo"). `justificacion_tipo_id`/`es_viaticos` desaparecieron del modelo y de la línea. Confirmado con el usuario: **`anticipo` normal y `anticipo_viaticos` comparten EXACTAMENTE el mismo flujo** (enviar/aprobar/aplicar) - no hay dos caminos distintos, solo dos etiquetas para el mismo mecanismo (constante `ANTICIPO_TIPOS` en `account_payment_order.py`, usada en absolutamente todos los guards que antes decían `tipo != 'anticipo'`). La pestaña "Viáticos" ahora se muestra con `invisible="tipo != 'anticipo_viaticos'"` directo (ya no hace falta el compute `es_viaticos` intermedio).
- **`employee_partner_id` (encabezado) se fusionó dentro de `partner_id`** - eran dos campos de contacto para la misma persona ("que no esté dos veces la persona que está solicitando"). `partner_id` ahora hace las dos funciones: para Liquidación/Pago Directo/Anticipo normal sigue siendo el contacto/proveedor de siempre, sin restricción; para `anticipo_viaticos`, la vista le agrega `domain="[('employee', '=', True)] if tipo == 'anticipo_viaticos' else []"` y `readonly="tipo == 'anticipo_viaticos'"` (el anti-suplantación de `write()` también se acotó a ese `tipo` específicamente, para no restringir de más a Liquidación/Pago Directo, que nunca tuvieron esa restricción). La línea de viáticos (`account.payment.order.viatico.line`) **mantiene su propio `employee_partner_id`** sin cambios - es un concepto distinto (el técnico de ESE renglón, no quién solicita el encabezado).
- **`requested_by_name` ("Nombre") se sacó de la vista** (seguía siendo redundante con `partner_id.name` una vez fusionado el campo de arriba) - el campo sigue existiendo en el modelo solo por compatibilidad con `_prepare_sync_vals()`, ya no se le pide nada al usuario.
- **`request_date` se eliminó del modelo por completo** ("nos quedamos solo con fecha") - `fecha` (el campo que ya usan Liquidación/Pago Directo) es ahora también la única fecha para Anticipo/Anticipo Viáticos. `_prepare_sync_vals()` envía `'fecha'` en vez de `'request_date'`.
- **En Community, ocultos**: `cuenta_anticipo_id`, `payment_method_line_id` (y su auxiliar `available_payment_method_line_ids`), y toda la sección "Facturas" - los tres con `invisible="not es_procesador"` (el compute que ya existía para gatear Aprobar/Rechazar). Como Community y Enterprise son bases de datos **separadas**, en la práctica Community nunca crea ni recibe registros `tipo` distinto a `anticipo_viaticos` - por eso no hizo falta ningún filtro de lista/búsqueda adicional para que "solo se vea Anticipo Viáticos ahí", es una consecuencia natural de la separación de bases, no algo que haya que forzar en código.
- **La pestaña Viáticos** (única visible en Community, junto con Sincronización) muestra ahora solo `employee_partner_id`/`departamento`/`puesto`/`cantidad`/`costo_individual`/`total` - se quitó la columna `justificacion_tipo_id` de la línea.
- **`journal_id`**: el domain condicional a solo bancos (`[('type','=','bank')] if tipo == 'anticipo_viaticos' else []`) se acotó específicamente a `anticipo_viaticos` (un Anticipo normal, creado a mano en Enterprise, puede seguir usando cualquier diario, igual que siempre) - y también se oculta en Community (`invisible="not es_procesador"`), ya que ahí el diario lo define el contable en Enterprise después de Aprobar, no el técnico al capturar.
- Verificado con un script end-to-end nuevo (creación sin tipo de gasto, sync, recepción, aprobar, llenar campos y aplicar, más un Anticipo normal pasando por el mismo enviar/aprobar/aplicar, más confirmar que el modelo del catálogo viejo ya no existe en el registro).

## Fase 1 del proyecto: tipos configurables por compañía, `anticipo_id` sin liquidar, reglas de Pago Directo

Inmediatamente después del refinamiento de UX de arriba, el usuario pidió tres cosas más para esta "primera fase" (Community solo ve Viáticos; el resto vive en Enterprise, pero de forma configurable, no hardcoded a `payment_order_role`):

- **Qué `tipo` se puede CREAR a mano es configurable por compañía**, cuatro Boolean nuevos en `res.company` (`payment_order_habilitar_anticipo`/`_anticipo_viaticos`/`_liquidacion`/`_pago_directo`, todos `default=True` para no cambiar el comportamiento de una Enterprise ya instalada al actualizar el módulo — **hay que ir a Ajustes y desmarcar a mano** los tres que no sean Anticipo Viáticos en la compañía de Community después de este despliegue; no se migran datos automáticamente, mismo criterio que la fusión Solicitud+Anticipo). `res.company._get_payment_order_allowed_tipos()` calcula el subconjunto habilitado. **`AccountPaymentOrder.fields_get()` filtra las opciones del Selection `tipo`** con ese subconjunto — deliberadamente **solo afecta lo que el desplegable del formulario ofrece elegir**, nunca `create()`/`write()` (verificado con un script: con Community-like config, `create({'tipo': 'pago_directo', ...})` sigue funcionando perfectamente aunque esa opción no aparezca en el desplegable) — necesario porque la sincronización (crea `anticipo_viaticos` en Enterprise) y `action_registrar_liquidacion()` (crea `tipo='liquidacion'`) deben poder seguir funcionando sin importar esta configuración. Si se necesitara alguna vez una restricción real a nivel de datos, habría que resolver primero cómo distinguir esas dos rutas internas de una creación manual por un usuario (ver el propio docstring de `fields_get()`).
- **`anticipo_id` (en una Liquidación) ahora solo lista Anticipos sin liquidar**: nuevo campo auxiliar `anticipos_disponibles_ids` (Many2many compute, mismo patrón que `available_payment_method_line_ids` — un domain string no puede expresar una subquery "sin Liquidación registrada" directamente), referenciado como `domain="[('id', 'in', anticipos_disponibles_ids)]"`. Incluye siempre el propio `anticipo_id` actual del registro (para que no desaparezca del desplegable si deja de calificar después de haberlo elegido). **`anticipo_id` dejó de ser `readonly="1"` fijo** — ahora es `readonly="state != 'borrador'"`, editable a mano en borrador (sigue llenándose automático vía el botón "Registrar Liquidación", pero ya no es la única forma). **Trampa real al probar esto en `odoo-bin shell` con `.new()`**: Odoo envuelve los ids reales de un x2many en un registro sin guardar como `NewId(origin=<id real>)` — comparar con `in` directo contra el recordset real da un falso negativo aunque el cálculo interno sea correcto (confirmado con un log de traza dentro del propio compute). Hay que comparar por `origin`, no por `in`. Esto es un artefacto exclusivo de `.new()` — el cliente web real nunca ve el wrapper NewId (la respuesta de onchange serializa ids planos), así que no afecta el uso real.
- **Pago Directo: factura obligatoria, monto exacto sin escape** — `action_conciliar()` ahora exige `factura_ids` no vacío para `tipo == 'pago_directo'` (antes de netear nada), y si el neteo no da exactamente cero, **ya no acepta `cuenta_ajuste_id` como escape** (a diferencia de Liquidación, que sigue permitiéndolo sin cambios — la diferencia parcial ES el caso de uso de Liquidación). Refleja la regla de negocio explicada por el usuario en esta misma sesión: Pago Directo = el anticipo/pago cubre el 100% de la factura; si no cubre el 100%, es una Liquidación, no un Pago Directo.
- Verificado end-to-end con un script nuevo (`fields_get()` filtrado en modo Community-like y Enterprise-like + que `create()` interno sigue sin bloquearse; `anticipo_id` excluye uno ya liquidado e incluye uno aplicado sin liquidar; Pago Directo sin factura bloqueado, con factura pero monto distinto bloqueado aunque tenga `cuenta_ajuste_id`, con monto exacto concilia; regresión de Liquidación con diferencia + `cuenta_ajuste_id` sigue funcionando sin cambios) y con `-u` sobre la base de prueba ya instalada (upgrade limpio, sin errores).

### Solicitante vs. Procesador — one field, same module both places

`res.company.payment_order_role` (`solicitante`/`procesador`, **default `procesador`** — an already-installed Enterprise database keeps behaving exactly as before after upgrading this module) is the only thing that distinguishes the two roles, and it only affects **one thing**: whether `action_approve()` on a request actually pushes a copy to another instance (`_sync_to_enterprise()` is a no-op unless `payment_order_role == 'solicitante' and payment_order_sync_enabled`). Everything else — menus, buttons, security groups — is identical in both editions; visibility is controlled by security groups (`group_payment_order_approver`, `account.group_account_invoice`), not by conditionally hiding UI based on the company role field. Don't add role-based `invisible=` conditions to menus/views for this — it was a deliberate simplification (fragile and unnecessary: an instance simply won't have anyone in the accounting groups if it's meant to be Solicitante-only, and "Crear Anticipo" being technically reachable but pointless on a pure-Solicitante instance is harmless).

### Sync mechanism — same JSON-RPC pattern as `construtec_materials_19`/`construtec_materials_sync_19`, but self-contained

`tools/enterprise_sync_api.py` is a **deliberate small copy** (not a shared dependency) of the proven helper in `construtec_materials_19` (Odoo19C): push via Odoo's own built-in `/jsonrpc` (`common.authenticate` + `object.execute_kw(...).create(...)`), `requests` library, never blocks the action that triggers it (`EnterpriseSyncError` caught, `sync_state`/`sync_error` recorded, retry every 30 min via `ir_cron_payment_order_sync_retry` + manual `action_retry_sync()`). **Why a copy and not a shared library**: each integration keeps its own URL/credentials/log, so revoking one API Key can't affect the other; this module also needed to avoid depending on `construtec_materials_19` (a Community-only module in spirit, even though nothing stops it installing elsewhere) just to reuse ~90 lines.

Because **both sides are literally the same model** (`account.payment.order`, same module installed on both instances) — unlike materials' mirror-into-a-different-model design — `_prepare_sync_vals()` still sends **plain values only, no ids** (`origin`/`external_ref`/Char/Date/Float), because `res.company`/`res.users` ids from one database mean nothing in the other even though the schema is identical. The receiving `create()` lands the record with `origin='synced'`, `state='approved'` directly — it does **not** go through this instance's own `action_submit()`/`action_approve()` again (already approved where it came from).

**Provisioning the integration user** (Procesador side): create a dedicated user in **only** `group_payment_order_sync_integration` (create-only on `account.payment.order` — `perm_read=perm_write=perm_unlink=0`, see `security/ir.model.access.csv`) — do **not** also add `base.group_user` or any broader group to it, or it inherits whatever else those imply. Generate its API Key from Ajustes > Mi Perfil > Seguridad de la cuenta, put the URL/db/login/key in Ajustes > Facturación > Solicitudes de Pago on the **Solicitante** instance (that's where `payment_order_role='solicitante'` and the sync fields actually get used).

### Aprobación por monto: Nivel Medio / Nivel Alto (`group_payment_order_approver_medio`/`_alto`)

Pedido explícito del usuario, basado en el formulario en papel adjuntado (`Solicitud de Pago - Auner Calderon.pdf`): ese PDF trae 2 columnas de autorización - "Autorización 1 (montos menores a Q2500.00)" firmada por "Jefe de Área"/"Project Manager", y "Autorización 2 (montos mayores a Q2500.00)" firmada por "Gerente de Área"/"Gerencia Comercial". **No se agregaron estados nuevos al `state` field** (decisión explícita: "igual que ahora, solo cambia QUIEN aprueba") - el flujo `draft → submitted → approved/rejected/cancel` sigue idéntico; lo único nuevo es que `action_approve()` ahora exige un grupo distinto según el monto.

**Por qué NO se portó `construtec_roles_permisos_19`** (el módulo de roles de Odoo19C que el usuario recordaba y preguntó explícitamente si convenía traer a Enterprise): investigado a fondo antes de decidir - ese módulo depende directamente de `construtec_helpdesk_mgmt` (`"depends": ["base", "construtec_helpdesk_mgmt"]`, Community-only) y su `security/construtec_roles_security.xml` referencia 3 grupos de helpdesk (`group_helpdesk_user_own`/`_team`, `group_helpdesk_manager`) dentro de sus propios `implied_ids`. **No instala en Enterprise tal cual** - fallaría por dependencia faltante, y aunque se sorteara eso, tronaría por external ID no resuelto en esas 3 referencias. Como el usuario solo necesita esto para Solicitudes de Pago por ahora, se siguió el mismo criterio ya documentado arriba para `group_payment_order_approver` (self-contained, no depende de nada externo a este módulo) en vez de intentar portar/adaptar ese módulo de Community.

**Jerarquía de grupos** (`security/payment_order_request_security.xml`): `group_payment_order_approver_alto` implica `group_payment_order_approver_medio` implica `group_payment_order_approver` (el grupo genérico ya existente, que a su vez implica `base.group_user`) - así que un usuario Nivel Alto automáticamente tiene todo lo que Nivel Medio y el grupo base ya otorgan (visibilidad vía `account_payment_order_request_approver_rule`, acceso al campo `employee_id` sin bloqueo, etc.), sin tener que listarlo aparte en cada `ir.rule`/vista.

**El umbral es configurable, no fijo** (pedido explícito): `res.company.payment_order_approval_threshold` (`Monetary`, default `2500.0` - el valor del PDF), expuesto en Ajustes > Facturación > "Aprobación por Monto". `_check_is_approver_for_amount()` (llamado por registro dentro de `action_approve()`, ya que el monto varía por Solicitud) compara `self.total_acreditar` contra `self.company_id.payment_order_approval_threshold`:
- `total_acreditar >= threshold` → exige `group_payment_order_approver_alto` (Gerente de Área).
- `total_acreditar < threshold` → exige `group_payment_order_approver_medio` (que Alto también tiene, por la implicación de arriba) - Jefe de Área.

`action_reject()` sigue usando el `_check_is_approver()` genérico (sin distinción por monto) - el usuario no pidió que el rechazo también fuera escalonado por nivel, solo la aprobación.

**Que se vea como una app nativa en Ajustes > Usuarios** (pedido explícito: "quisiera que en la pantalla del usuario estos permisos salieran como las aplicaciones nativas de Odoo... así como Contabilidad, uno le da clic y tiene varios niveles"): en Odoo 19, `res.groups` **ya no tiene `category_id`** (se quitó del modelo) - el mecanismo correcto es `res.groups.privilege`, confirmado leyendo `..\odoo\addons\base\models\res_groups_privilege.py` y el ejemplo real ya existente en este workspace (`construtec_roles_permisos_19/security/construtec_roles_security.xml`, que ya usa exactamente este patrón para su escalera de 4 roles). Sin esto, los grupos se ven como casillas sueltas en "Otros permisos", no como el selector limpio de un renglón por app.

- `ir.module.category` nuevo (`module_construtec_payment_order_category`, "Solicitudes de Pago") - es el renglón que aparece en la grilla de Usuarios, igual que "Contabilidad"/"Ventas".
- `res.groups.privilege` nuevo (`payment_order_approval_privilege`, "Nivel de Aprobación") con `category_id` apuntando a esa categoría - es la "columna" dentro del renglón.
- **Solo** `group_payment_order_approver_medio`/`_alto` tienen `privilege_id` seteado a ese privilegio (por eso se les acortó el `name` a "Nivel Medio (Jefe de Área)"/"Nivel Alto (Gerente de Área)" - el nombre de la categoría ya da el contexto "Solicitudes de Pago", repetirlo en cada nivel sería redundante, igual que "Contabilidad" no dice "Contabilidad: Facturación"). `group_payment_order_approver` (el genérico/base) **deliberadamente no tiene `privilege_id`** - sigue existiendo solo como grupo implícito interno, no aparece como un tercer nivel seleccionable confuso.
- Odoo ordena los niveles dentro del privilegio por profundidad de `implied_ids` (cuántos otros grupos del mismo privilegio implica) - como Alto implica Medio, se renderiza como el nivel más alto automáticamente, sin necesidad de un campo de orden manual.

### Cambio de arquitectura: la aprobación ahora ocurre en Enterprise, no en Community

Decisión explícita del usuario tras probar el flujo real de punta a punta (viendo el botón "Crear Anticipo" aparecer en Community, donde no tiene ningún sentido, y notando que `employee_id` llegaba vacío a Enterprise): **"considero que, una vez que el técnico envíe [la solicitud], las etapas de aprobación estén en Enterprise, porque allá están los usuarios administrativos. Y que en Community solo se vea como enviado."** Esto invierte el diseño original de esta sesión (Community aprobaba localmente y sincronizaba ya aprobada) - ahora:

- **El sync se dispara en `action_submit()`, no en `action_approve()`** - `_prepare_sync_vals()` ahora envía `'state': 'submitted'` (antes `'approved'`). En una instalación Procesadora, `action_submit()` sigue llamando a `_sync_to_enterprise()` pero es un no-op inofensivo (el guard interno ya existente: `company.payment_order_role != 'solicitante'` → `continue`).
- **La Solicitud sincronizada llega a Enterprise en `state='submitted'`**, no `'approved'` - a partir de ahí sigue el flujo NORMAL de Enterprise (sus propios usuarios Nivel Medio/Alto le dan clic a "Aprobar" como si fuera una solicitud creada ahí mismo). No hizo falta ningún código especial para esto - el `create()` genérico solo pone el estado que le llega, y una vez creada en `submitted`, `action_approve()`/`action_reject()` funcionan exactamente igual que para cualquier registro local de Enterprise.
- **Los botones Aprobar/Rechazar/Crear Anticipo ahora se ocultan por completo en una instalación Solicitante** (`es_procesador`, campo compute nuevo que resuelve `company_id.payment_order_role == 'procesador'` - una vista NO puede navegar `company_id.payment_order_role` directo dentro de una expresión `invisible=`, hace falta este auxiliar, mismo patrón que `es_viaticos`). En Community, la Solicitud simplemente se queda visualmente en "Enviada" para siempre desde el punto de vista de esa base - lo que pase después (aprobación, rechazo, Anticipo) ocurre en la copia de Enterprise, y **no hay sincronización de vuelta** (Enterprise → Community) del estado final; no se pidió y queda fuera de alcance de esta pasada. Si se necesita a futuro, sería un mecanismo nuevo simétrico al que ya existe (Community → Enterprise), no algo que ya esté construido.
- El bloque "Aprobación por Monto" en Ajustes también se ocultó para instalaciones Solicitante (`payment_order_role != 'procesador'`) - el umbral solo importa donde realmente se aprueba.

### `employee_enterprise_ref`: resolver el empleado real en Enterprise al sincronizar

Bug real encontrado por el usuario probando el flujo: en la copia de Enterprise de una Solicitud sincronizada, el campo "Empleado Solicitante" y la columna "Empleado" de cada línea llegaban **vacíos** - solo los campos de texto (`puesto`/`departamento`/`tecnico_name`) llegaban bien. Esto era **el comportamiento esperado del diseño original** (`employee_id` es local a cada base, nunca viaja) pero resultó insuficiente en la práctica: el usuario quiere que la Solicitud, ya en Enterprise, quede vinculada al `hr.employee` **real** de allá, no solo a su nombre en texto.

**La solución reutiliza algo que ya existía**: cuando Community sincroniza su directorio de empleados (`res.company._sync_employees_from_enterprise()`), cada `hr.employee` mirror ya guarda `enterprise_employee_ref` = el id **original** de ese empleado en Enterprise. Este es el único id en todo este módulo que es genuinamente válido en ambas bases (viene literalmente de allá) - así que ahora viaja también, tanto en el encabezado como en cada línea:

- `_prepare_sync_vals()` agrega `employee_enterprise_ref: self.employee_id.enterprise_employee_ref` (encabezado) y lo mismo por línea.
- `AccountPaymentOrderRequest._resolve_employee_enterprise_ref()`/la lógica equivalente en `.line.create()` hacen `self.env['hr.employee'].browse(int(ref)).exists()` - una búsqueda directa por id, no por nombre (a diferencia de `justificacion_tipo_name`/`analytic_account`, que sí se resuelven por nombre porque no hay ninguna referencia cruzada previa para esos catálogos). Desde el rediseño "Contacto como fachada" (ver sección siguiente), esto resuelve hacia `employee_partner_id` (`employee.work_contact_id.id`), no directo a `employee_id` - `employee_id` es ahora un campo calculado.
- Si el empleado se resuelve, **también** se usa `employee.company_id` para `company_id` del encabezado - más preciso que cualquier respaldo manual, porque es la compañía real de esa persona.

### Multi-compañía: `payment_order_default_company_id` como respaldo cuando no hay empleado resoluble

Consideración nueva del usuario: Enterprise puede tener varias compañías, con empleados contratados en cada una - si `employee_enterprise_ref` no resuelve (empleado todavía no sincronizado, por ejemplo), la Solicitud no debe caer en cualquier compañía por accidente (rompería reglas multi-compañía en otros lados de Enterprise).

- **Nuevo modelo espejo** `account.payment.order.enterprise.company` (`name`, `enterprise_company_ref`) - mismo patrón que empleados/cuentas analíticas: `tools/enterprise_sync_api.fetch_companies()` (`search_read` sobre `res.company`, solo `name` - nada sensible) + `res.company._sync_enterprise_companies()`, sumado al mismo cron/botón "Sincronizar ahora" que ya jala empleados y cuentas analíticas.
- **`res.company.payment_order_default_company_id`** (Many2one a ese espejo, expuesto en Ajustes > Facturación > Sincronización de Empleados como un desplegable poblado por el propio sync - nunca se escribe a mano el nombre de la compañía, precisamente para evitar errores de tipeo). Pedido explícito: "que me liste qué empresas están" en vez de escribir el nombre a mano.
- `_prepare_sync_vals()` también envía `company_enterprise_ref` (el `enterprise_company_ref` de esta compañía por defecto) - se usa en el receptor **solo si** `employee_enterprise_ref` no resolvió nada (`_resolve_company_enterprise_ref()`, después de `_resolve_employee_enterprise_ref()` en el orden de `create()`). Si ninguno de los dos resuelve, `company_id` cae al default normal de Odoo (`self.env.company`, la compañía del usuario de integración) - sin cambios ahí.

### "Empleado" como Contacto (`employee_partner_id`), no hr.employee directo

Observación del usuario probando el flujo completo (con `employee_enterprise_ref`/multi-compañía ya construidos): **"considero que es mejor que [el campo de empleado] esté relacionado al campo de contactos... esto para no pelear con la regla de multiempresa de empleados, tanto en community como en enterprise."** El problema real: `hr.employee` trae su propia regla de multi-compañía (un usuario normalmente solo ve empleados de las compañías que tiene permitidas) - un picker Many2one directo a `hr.employee` en el formulario de la Solicitud puede quedar vacío/restringido para un usuario que sí debería poder elegir un empleado de otra compañía. `res.partner` (Contactos) no tiene esa restricción.

**Diseño acordado ("Contacto como fachada, empleado por debajo")**: el campo que el usuario ve y elige sigue llamándose "Empleado" en la UI, pero es un Many2one a `res.partner`, no a `hr.employee`. El `hr.employee` real se resuelve por debajo, automáticamente, sin que el usuario tenga que saberlo:

- **`employee_partner_id`** (Many2one `res.partner`, en encabezado y línea) - el campo que el usuario ve/elige. Dominio `[('employee', '=', True)]`, usando el campo **nativo** de Odoo `res.partner.employee` (`Boolean`, `compute` + `store=True`, definido en `..\odoo\addons\hr\models\res_partner.py`) - no hizo falta inventar un campo propio: Odoo ya calcula y guarda si un contacto tiene al menos un `hr.employee` vinculado, y al ser un campo plano guardado en `res.partner`, filtrarlo NO dispara la regla de multi-compañía de `hr.employee` (esa regla solo aplica al leer/buscar `hr.employee` directamente).
- **`employee_id`** (Many2one `hr.employee`, en encabezado y línea) - pasó de ser el campo que el usuario llenaba a ser un campo **calculado** (`compute='_compute_employee_id', store=True, readonly=True`), resuelto por `_resolve_employee_for_partner(partner, company)` (función a nivel de módulo, compartida entre encabezado y línea). Todo lo que ya existía y leía de `employee_id` (banco/teléfono/correo en el onchange y en `create()`, `employee_enterprise_ref` en `_prepare_sync_vals()`, el gate de `action_submit()` que exige empleado en cada línea) **sigue funcionando sin cambios** - solo cambió de dónde sale el valor.
- **Desempate cuando un contacto tiene `hr.employee` en más de una compañía** (contratado en varias empresas - el mismo escenario de multi-compañía ya cubierto por `payment_order_default_company_id`): se usa `partner.sudo().employee_ids` (también nativo, `One2many('hr.employee', 'work_contact_id')`) y se prefiere el que coincide con la compañía de la Solicitud/línea (`company_id` del encabezado, `request_id.company_id` en la línea); si ninguno coincide, cae al primero activo. Decisión explícita del usuario, confirmada antes de implementar.
- **`_resolve_employee_enterprise_ref()`** (recepción sincronizada) ahora resuelve hacia `employee_partner_id = employee.work_contact_id.id` (no hacia `employee_id` directo, que ya no acepta escritura útil por ser calculado) - y como también fija `company_id = employee.company_id.id`, el compute de `employee_id` vuelve a resolver exactamente al mismo `hr.employee` de origen (el desempate por compañía coincide con la compañía real de ese empleado).
- **`write()`**: el candado antisuplantación ahora protege `employee_partner_id` (el campo que el usuario real controla) y, por defensa en profundidad, también `employee_id` directo - ningún usuario sin el grupo aprobador puede cambiar el empleado de una Solicitud ya creada, sea cual sea el campo que intente escribir.
- **Trampa real encontrada verificando esto**: vincular `user_id` a un `hr.employee` dispara el mismo mecanismo núcleo de Odoo ya documentado arriba (`_sync_user()`/`_remove_work_contact_id()`) que **reemplaza `work_contact_id`** por el partner propio del usuario recién vinculado - es decir, el "Contacto" detrás de un empleado puede cambiar de identidad (no solo perder campos) en cuanto se le crea login. Esto no rompe nada porque `employee_ids` (la relación inversa) se recalcula junto con el swap - el contacto nuevo pasa a resolver correctamente hacia ese mismo empleado - pero si se arma una prueba con dos empleados compartiendo un contacto a propósito, hay que vincular `user_id` **antes** de fijar ese contacto compartido, no después (ver `verify_partner_facade.py` - un primer intento de esa prueba falló exactamente por este orden).

### `puesto`/`departamento`: heredados en el Contacto, no resueltos en vivo por Solicitud

Bug reportado por el usuario probando el rediseño "Contacto como fachada" de arriba: al elegir un Contacto en una Solicitud, `puesto`/`departamento` quedaban vacíos. Causa real (confirmada con `debug_puesto_depto.py` antes de tocar nada): la lógica SÍ resolvía bien cuando el `hr.employee` de la compañía de la Solicitud tenía `job_title`/`department_id` cargados - el vacío ocurría cuando el desempate por compañía (`_resolve_employee_for_partner`) no encontraba ningún `hr.employee` en la compañía específica de esa Solicitud (Enterprise real: varias compañías, el mismo contacto empleado en una de ellas nada más).

Decisión del usuario tras plantear la disyuntiva (¿un valor por contacto, o seguir resolviendo en vivo por compañía?): **un solo valor por Contacto** - la mayoría de contactos solo tiene un empleo, y quiere que "se hereden automático cuando se cree el empleado y se vincule el contacto", pensando ya en una relación empresa-a-empresa (varias compañías en Enterprise), no solo Community-Enterprise.

- **`res_partner.py`** (nuevo): `employee_department_id` (Many2one `hr.department`) y `employee_job_title` (Char), ambos `compute` + `store=True` + `compute_sudo=True` en `res.partner`, `@api.depends('employee_ids.department_id', 'employee_ids.job_title', 'employee_ids.company_id')` - se recalculan solos en cuanto se crea/edita/vincula el `hr.employee`, sin ningún cron ni acción manual. Reutilizan `_resolve_employee_for_partner()` (la misma función de `account_payment_order_request.py`) con `self.env.company` como criterio de compañía (no hay una Solicitud de por medio a este nivel) - incluidos ahí porque es lógica de dominio de este módulo, no algo que deba vivir en el core de `hr`.
- **Encabezado y línea** (`_onchange_employee_partner_id`, `_fill_derived_vals_from_employee`, `Line.create()`): `puesto`/`departamento` ahora se leen directo de `employee_partner_id.employee_job_title`/`.employee_department_id.name` - **ya no** dependen de que `_resolve_employee_for_partner` encuentre un `hr.employee` en la compañía exacta de esa Solicitud. El resto (banco/teléfono/correo/`employee_enterprise_ref`/`tecnico_name`) sigue exactamente igual, resuelto en vivo vía `_resolve_employee_for_partner` - esos sí varían legítimamente por compañía (o solo importan para la compañía de esa Solicitud puntual), a diferencia de puesto/departamento.
- **No hace falta ningún script ni sincronización nueva** (pregunta real del usuario después de implementar esto) - confirmado con `verify_partner_job_sync.py`:
  - **Empleados ya existentes en Enterprise antes de esta migración**: Odoo recalcula solo, para TODOS los registros existentes, cualquier campo `compute` + `store=True` recién agregado - es el comportamiento estándar del ORM al correr `-u`, no algo que haya que programar aparte.
  - **La sincronización Community↔Enterprise no necesitó ningún cambio**: `department_id`/`job_title` ya viajaban de Enterprise a Community desde antes, como parte del pull periódico de empleados que ya existía (`_sync_employees_from_enterprise`/`fetch_employees`). El `write()` que ese pull hace sobre el `hr.employee` espejo de Community dispara el `_compute_employee_job_info` de `res_partner.py` **localmente en la base de Community** (mismo código, mismo módulo instalado en ambos lados) - el dato no necesita viajar dos veces, solo se recalcula donde ya llegó.
- **Vista** (`views/res_partner_views.xml`, nuevo): `employee_department_id` se agregó a la ficha del Contacto (`base.view_partner_form`, junto al campo nativo `function`), `readonly="1"` e `invisible="not employee"` - pedido explícito del usuario: "¿Dónde veo el departamento y puesto? En la ficha del contacto que pertenece el empleado."
- **Corrección posterior del usuario - `function` no es un campo nuevo, es el nativo "Job Position"**: la primera versión de esto creó `employee_job_title` (Char) en vez de reusar `res.partner.function` (`base`, ya existente, disponible en Community y Enterprise por igual - lo usa cualquier contacto para su puesto, sea empleado o no). Se corrigió: `function` se **redeclara** en `res_partner.py` con `compute='_compute_employee_job_info', compute_sudo=True, store=True, readonly=False` - mismo patrón exacto que usa el propio Odoo en `crm.lead.function` (`..\odoo\addons\crm\models\crm_lead.py`, `_compute_function()`): `if not partner.function or employee.job_title: partner.function = employee.job_title or partner.function`. Esto es **deliberadamente autoreferencial** (lee y escribe el mismo campo dentro de su propio compute) - no es un error, es el idioma sancionado por Odoo para "compute que cede a un valor manual cuando no tiene nada nuevo que aportar". Como resultado: **nunca pisa el `function` de un contacto que no es empleado** (su `employee_ids` nunca cambia, el compute jamás se dispara para él), y si un contacto luego SÍ se vincula a un `hr.employee` real, `function` pasa a reflejar el puesto de RR.HH. desde ese momento (verificado con `verify_partner_job_info.py`, casos 7 y 8 - un contacto no-empleado con `function='CEO'` puesto a mano conserva su valor; el mismo contacto, tras vincularse a un `hr.employee`, actualiza `function` al puesto real).

### Directorio de Empleados: pull automático desde Enterprise (Solicitante-only)

**Dirección invertida respecto a los demás syncs de este módulo**: aquí Community *jala* (pull) datos de Enterprise, en vez de empujar (push) hacia allá. Motivo explícito del usuario: los empleados **solo se crean en Enterprise** (via `construtec_hr_employee_19`/`construtec_hr_payroll_19`), nunca en Community — este mecanismo únicamente le da a Community una copia de referencia (nombre/departamento/puesto) para poder crear manualmente cuentas `res.users` de esos empleados ahí.

- **`tools/enterprise_sync_api.fetch_employees()`**: `search_read` sobre `hr.employee` en Enterprise pidiendo `name`, `department_id`, `job_title`, `bank_account_ids`, `work_phone`, `private_phone` — nunca el registro completo, aunque las credenciales usadas puedan técnicamente leer más. `department_id`/`job_title` son campos de **`hr.version`** en Odoo 19 (no de `hr.employee` directamente — ver `construtec_hr_employee_19/CLAUDE.md`), pero se leen igual como `employee.department_id`/`employee.job_title` gracias a la delegación de `hr.version` sobre `hr.employee`; verificado leyendo `..\odoo\addons\hr\models\hr_version.py` directamente, no asumido. **Ese mismo `version_id` requiere el grupo "Employees Officer" (`hr.group_hr_user`) para leerse** — un `base.group_user` normal en Community, sin ese grupo, obtiene `AccessError` al leer `job_title`/`department_id` directo; todo el código de este módulo que los lee para un solicitante cualquiera usa `.sudo()` explícitamente (ver `_onchange_employee_id()`/`_fill_derived_vals_from_employee()` en `account_payment_order_request.py`) — confirmado con un test real, no asumido.
- **Decisión explícita del usuario: sin cambios en Enterprise para esto.** Lo correcto en seguridad hubiera sido un modelo/vista de solo-lectura dedicado en Enterprise para no exponer el `hr.employee` completo (salario, banco, DPI, etc.) ante una fuga de credenciales — el usuario reconoció el riesgo y decidió aceptarlo por ahora, reusando las **mismas credenciales de administrador** ya configuradas para el push de Solicitudes de Pago (`payment_order_sync_url/db/login/api_key`). Si esto cambia más adelante, ese modelo de solo-lectura en Enterprise es el primer paso a re-proponer.
- **`hr.employee.enterprise_employee_ref`** (`models/hr_employee.py`, campo nuevo vía `_inherit`): guarda el id del empleado en Enterprise, usado *solo* para no duplicar en cada sincronización — no editable, sin significado fuera de este mecanismo.
- **`res.company._sync_employees_from_enterprise()`**: no-op si `payment_order_role != 'solicitante'` o la sincronización no está habilitada (mismo patrón que el resto). Busca-o-crea `hr.department` por nombre (nunca por id — bases independientes), y hace upsert de `hr.employee` por `enterprise_employee_ref`.
- **Intervalo configurable** (`employee_sync_interval_number`/`_type` en `res.company`, expuesto en Ajustes): al guardar, se escribe directo sobre el único registro `ir.cron` (`ir_cron_employee_sync`) — **el cron es global, no por compañía**; si algún día hay más de una compañía Solicitante con intervalos distintos, la última que se guarde gana. Aceptable hoy porque la instancia Community es de una sola compañía; documentado aquí como limitación conocida, no resuelta.
- **`hr` se agregó a `depends`** — antes este módulo solo dependía de `account`/`mail`. `hr` ya estaba instalado en ambas ediciones antes de este cambio, así que no debería disparar ningún `to_install` en cascada al actualizar.

**Lección de despliegue de esta misma sesión, aplica igual aquí**: cualquier cambio de esquema en este módulo (campos nuevos en `res.company`/`hr.employee`, tablas nuevas) **debe aplicarse en Enterprise vía terminal** (`odoo-bin -u construtec_account_payment_order_19 --stop-after-init`), **nunca dando clic en Actualizar desde Ajustes > Aplicaciones** — ese botón dispara `ir_module.button_install()` internamente, que hace una lectura amplia de `res.company` (`company_countries = self.env['res.company'].search([]).country_id`) *antes* de que corra la migración de esquema del propio módulo, y truena con `UndefinedColumn` de forma 100% reproducible mientras el código ya está desplegado pero el esquema no. Esto causó dos incidentes reales en producción (`construtecasesores.odoo.com`) el 2026-08-18 al agregar `payment_order_role`; se resolvió cada vez revirtiendo el commit (`git revert`, nunca `reset --hard`, ver [[dos_repositorios_odoo19e_enterprise]]) y luego re-desplegando + migrando por terminal.

**Nota sobre despliegue en Docker** (`erp.construtecasesores.com`, VPS propio): `docker exec -it <contenedor> odoo -u <modulo> --stop-after-init -d <db> --no-http` (el ejecutable dentro de la imagen oficial se llama `odoo`, no `odoo-bin`; falta `--no-http` truena con `OSError: Address already in use` porque el proceso principal ya tiene el puerto 8069 ocupado dentro del mismo contenedor). Ese `docker exec` migra la base correctamente, pero es un proceso aparte del que sirve las páginas web — **el proceso principal sigue con el código/registro viejo en memoria hasta que se reinicia** (`docker restart <contenedor>`), o si no vas a ver errores tipo `"res.config.settings"."campo_nuevo" field is undefined` en el navegador aunque la migración ya haya corrido bien.

### Empleado vinculado en la Solicitud (encabezado y cada línea de Viáticos)

`employee_id` (Many2one a `hr.employee`, **local a Community**, nunca se envía como id a Enterprise) tanto en el encabezado (default: el empleado cuyo `user_id` coincide con `self.env.user`, vía el directorio ya sincronizado — ver sección anterior) como en cada `account.payment.order.line` (el empleado destino de ese renglón de viáticos — decisión explícita del usuario: la línea ya no tiene un campo de texto libre "Técnico" en la vista, `employee_id` es la única forma de indicar a quién corresponde el renglón). En ambos casos, un `@api.onchange('employee_id')` **autocompleta** campos de texto plano (`puesto`/`departamento` en el encabezado; `tecnico_name`/`puesto`/`departamento` en la línea) — esos campos de texto, no el id, son lo que viaja en `_prepare_sync_vals()` hacia Enterprise, exactamente igual que el resto de este módulo (ver "Sync mechanism" arriba: nunca ids entre bases independientes). `tecnico_name` sigue existiendo en el modelo de la línea (no required, se llena solo) pero **no está en la vista** - el usuario solo ve/elige `employee_id`; `tecnico_name` es puramente la representación en texto que viaja por RPC.

**`employee_id` de la línea NO es `required=True` a nivel de campo** (solo `required="1"` en la vista, cosmético) - a propósito: una línea sincronizada llega SOLO con `tecnico_name` en texto (Enterprise no tiene forma de mapear un `tecnico_name` de Community a uno de SUS propios `hr.employee`), así que un `required=True` real en el modelo rompería la recepción de toda solicitud sincronizada con líneas. Se exige en cambio en `action_submit()` (`rec.viaticos_line_ids.filtered(lambda l: not l.employee_id)` → `UserError`), que las líneas creadas localmente siempre atraviesan y las sincronizadas (que llegan ya `state='approved'`) nunca pasan.

**Por qué ahora mismo**: motivado por una necesidad futura en Enterprise 19 (definir qué cuentas contables afecta cada viático según departamento/puesto del empleado destino) - explícitamente **no construida todavía**, el alcance de esta pasada es solo capturar y sincronizar departamento/puesto como texto, en encabezado y en cada línea.

### Anti-suplantación: `employee_id` de solo lectura, `cuenta_acreditar`/`banco` autocompletados y bloqueados

Decisión explícita del usuario: una vez creada la Solicitud, **nadie (salvo un Aprobador) puede cambiar `employee_id`** — `write()` lo bloquea (`UserError`) si el nuevo valor difiere del ya guardado, salvo `self.env.user.has_group(APPROVER_GROUP_XMLID)`. El campo también es `readonly=True` a nivel de vista. Motivo: `cuenta_acreditar`/`banco` ahora se autocompletan desde la cuenta bancaria **real** del empleado vinculado — permitir cambiar `employee_id` después de creada la solicitud sería una forma de redirigir el pago a la cuenta de otra persona.

`cuenta_acreditar`/`banco` son `readonly=True` (a nivel de campo, es decir aplica en toda vista de formulario salvo que se sobre-escriba explícitamente) y se llenan solo vía `_onchange_employee_id()` (formulario) o `_fill_derived_vals_from_employee()` (creación por API/script, ya que el onchange no corre fuera del formulario web) desde `employee_id.cuenta_bancaria`/`employee_id.banco_nombre` — nunca editables a mano.

### Cuenta bancaria del empleado: sincronizada en lote, pero self-scoped (`hr_employee.py`)

Decisión explícita del usuario: la cuenta bancaria de **todos** los empleados se trae en el mismo pull periódico que nombre/departamento/puesto (`fetch_employees()` ahora también solicita `bank_account_ids` a `hr.employee` y hace una segunda llamada a `res.partner.bank` para `acc_number`/`bank_id`) - el usuario explícitamente prefirió esto sobre una alternativa más segura (traer en vivo, solo la cuenta propia, nunca guardar la de otros) por simplicidad de mantenimiento.

Para que esto no signifique "cualquier usuario de Community puede leer la cuenta bancaria de cualquier empleado", `hr.employee` gana 4 campos nuevos:
- `cuenta_bancaria_raw`/`banco_nombre_raw`: el dato real, `groups='hr.group_hr_manager'` - invisible a un usuario normal por **cualquier** camino (vista, `read()`/`search_read()` vía RPC), no solo oculto en pantalla.
- `cuenta_bancaria`/`banco_nombre`: campos **compute** (`compute_sudo=True`) sin restricción de grupo, pero que solo resuelven a un valor real cuando `employee.user_id == self.env.user` - para cualquier otro empleado, devuelven `False` sin importar qué permisos tenga quien pregunta. Esta es la comprobación de "self-only" real; `groups=` por sí solo no puede expresar "solo su propio registro", así que se combinan ambos mecanismos (grupo + auto-chequeo en el compute).

**Esto solo funciona de punta a punta porque `account.payment.order.employee_id` siempre es el empleado vinculado al usuario actual** (default automático + bloqueado contra cambios, ver arriba) — nunca se expone un selector que permita a un usuario elegir "ver la cuenta de fulano".

**Bug real encontrado y corregido en esta misma sesión, antes de desplegar**: sin `@api.depends_context('uid')` en el `@api.depends(...)` del compute, el caché de Odoo puede **reutilizar el valor calculado para un usuario cuando OTRO usuario distinto consulta el MISMO registro dentro de la misma transacción** (`self.env.user` no es una ruta de campo, así que `@api.depends()` normal no lo detecta como dependencia — el caché no sabe que debe invalidarse al cambiar de usuario). Se confirmó el fallo con un test real (mismo `hr.employee`, `with_user(A)` seguido de `with_user(B)` en el mismo script) antes de tener el fix, y se confirmó la corrección después - **cualquier compute self-scoped por `self.env.user` en este módulo debe llevar `@api.depends_context('uid')` además de `@api.depends(...)`**, o el mecanismo de privacidad completo queda roto de forma silenciosa (sin error, solo filtrando datos de otro empleado). Ambos computes (`_compute_mi_info_bancaria`, `_compute_mi_telefono_personal`) ya lo tienen.

### Cuentas Analíticas (Proyecto): mismo patrón pull que empleados

`account.analytic.account` gana `enterprise_analytic_ref` (igual patrón que `hr.employee.enterprise_employee_ref`). `res.company._sync_analytic_accounts_from_enterprise()` corre en el mismo cron/intervalo que el sync de empleados (`ir_cron_employee_sync`, cuyo nombre ya no describe del todo su alcance pero se dejó así para no forzar una migración de datos solo por el nombre). `plan_id` es **obligatorio** en `account.analytic.account` (Odoo 19) - se busca-o-crea un `account.analytic.plan` por nombre igual que `hr.department`; si Enterprise no manda `plan_id`, cae en un plan genérico `"Proyectos (sin plan de origen)"` en vez de fallar toda la sincronización.

El encabezado gana `analytic_account_id` (Many2one local, nunca enviado como id) que autocompleta el `proyecto` (Char) ya existente vía `_onchange_analytic_account_id()` - mismo patrón que `employee_id`→`puesto`/`departamento`. `proyecto` sigue siendo lo que viaja a Enterprise en `_prepare_sync_vals()`, sin cambios ahí.

### Teléfono: campos NATIVOS de hr.employee (work_phone -> mobile_phone -> private_phone)

Decisión final y explícita del usuario, tras dos vueltas en esta misma sesión: el teléfono debe viajar por los campos **nativos** de `hr.employee` (`work_phone`, `mobile_phone`, `private_phone`), no por campos propios - "que se traslade de ficha a ficha entre Community y Enterprise usando el modelo estándar". `res.company._sync_employees_from_enterprise()` escribe directo a esos tres campos nativos; `account_payment_order_request` los lee directo (`employee.work_phone or employee.mobile_phone or employee.private_phone`, en ese orden) para autocompletar `telefono` - a diferencia de `cuenta_acreditar`/`banco`, este campo **no** quedó de solo lectura (el usuario no lo pidió), sigue editable a mano.

Enterprise tiene **tres** campos de teléfono, no dos - descubierto cuando el usuario probó esto la primera vez y su propio número no llegó a Community (lo tenía cargado en "Celular de Trabajo" = `mobile_phone`, no en "Teléfono de Trabajo" = `work_phone`).

**Bug real de Odoo core, encontrado y corregido en esta sesión - el motivo de `hr_employee.py`'s `write()` override**: `work_phone`/`mobile_phone` son campos `compute` + `store` + `inverse`, resueltos desde `work_contact_id.phone` (un `res.partner`). En cuanto se asigna `employee.user_id` a un empleado - **exactamente lo que hace el flujo real de este módulo**, cuando el administrador de Community vincula el empleado ya sincronizado a un usuario - el propio núcleo de `hr.employee` (`_sync_user()`/`_remove_work_contact_id()`, `..\odoo\addons\hr\models\hr_employee.py:1314-1334`) **reemplaza `work_contact_id` por el partner del usuario recién vinculado**, que no tiene teléfono, borrando en silencio el dato ya sincronizado. Confirmado reproduciendo el bug exacto (`emp.user_id = u.id` seguido de `emp.work_phone` → `False`) antes del fix.

**El fix**: `hr.employee.write()` (override en este módulo) toma una foto de `work_phone`/`mobile_phone` de los empleados sincronizados (`enterprise_employee_ref` truthy) **antes** de llamar a `super().write(vals)` cuando `'user_id'` está en `vals`, y si después del write del núcleo esos campos quedaron vacíos, los vuelve a escribir. Acotado a empleados sincronizados únicamente (nunca debería haber empleados "nativos" de Community de todas formas, pero por si acaso). `private_phone` es un `Char` simple sin `compute`/`inverse` - no le afecta este problema, se escribe y lee directo sin envoltura especial.

**Trade-off de privacidad asumido conscientemente** (el usuario no lo pidió explícitamente para teléfono, a diferencia de la cuenta bancaria donde sí fue un requisito explícito - ver más abajo): al escribir `private_phone` directo al campo nativo, cualquier usuario de Community con `hr.group_hr_user` ("Employees Officer") puede ver el teléfono personal de **cualquier** empleado - el mismo comportamiento de serie de Odoo, ni más ni menos restrictivo. Un intento anterior en esta sesión había construido un mecanismo self-scoped (solo el propio empleado ve su teléfono personal, ni siquiera un Oficial de RR.HH.) - se descartó a pedido explícito del usuario junto con los campos propios de teléfono. Si esto cambia, ese mecanismo self-scoped (idéntico al de `cuenta_bancaria` de abajo) es el patrón a reusar.

**Importante para el usuario al probar esto**: los datos de un empleado ya sincronizado antes de este cambio (o antes de agregar `mobile_phone`) no se actualizan solos - hay que correr "Sincronizar ahora" (Ajustes > Facturación > Sincronización de Empleados) o esperar al cron, para que el pull vuelva a correr y traiga los campos nuevos.

### Correo: mismo patrón que teléfono (`work_email` -> `private_email`)

Pedido explícito del usuario, calcado 1:1 del diseño de teléfono: `work_email`/`private_email` son los campos nativos equivalentes de correo (`email` en cambio es `related="user_id.email"` - el login de Community, no tiene nada que ver con Enterprise, **no se sincroniza**). `work_email` tiene **exactamente el mismo bug** que `work_phone` (mismo `_compute_work_contact_details`, mismo `work_contact_id`) - por eso `hr_employee.py`'s `write()` override ahora recorre `_WORK_CONTACT_FIELDS = ('work_phone', 'mobile_phone', 'work_email')` como una sola lista, no cada campo por separado. `private_email` es un `Char` simple igual que `private_phone` - mismo trade-off de privacidad (visible a cualquier `hr.group_hr_user`, no self-scoped).

El campo `correo` del encabezado de la Solicitud (antes con `default=lambda self: self.env.user.email`, el login de Community) ahora se autocompleta también vía `_onchange_employee_id()`/`_fill_derived_vals_from_employee()` con `employee.work_email or employee.private_email`, mismo criterio de prioridad que `telefono` - sigue editable a mano, no quedó de solo lectura.

### `justificacion_tipo_id`: catálogo (`account.payment.order.justification.type`), etiquetado "Tipo de Gasto"

Pedido explícito del usuario: "que sea un modelo que se use en encabezado y en detalle". Reemplaza el `Selection` original (`[('viaticos', 'Viáticos')]`) por un modelo nuevo, sencillo (`name`, `sequence`, `active`), seedeado con **un** registro (`data/justification_type_data.xml`, xmlid `justification_type_viaticos`) — el mismo modelo/módulo instalado en ambas ediciones, así que ese xmlid resuelve a un registro real en ambas bases, aunque con ids internos distintos (nunca comparados entre sí). Motivo del cambio: permitir agregar tipos nuevos (la "Materiales" de la Fase 2) **sin tocar código**, vía un menú nuevo (Contabilidad/Facturación > Proveedores > Tipos de Gasto, gateado a `group_payment_order_approver`/`account.group_account_invoice` - un `base.group_user` normal solo puede leer el catálogo, no crearlo/editarlo).

**Nombre técnico vs. etiqueta visible**: el campo Python, el modelo (`account.payment.order.justification.type`), y los nombres de método (`_resolve_justificacion_tipo_name`, `justificacion_tipo_name` en el payload de sync) siguen usando "justificacion_tipo" - solo la **etiqueta visible** (`string=`) para el usuario final es "Tipo de Gasto" (pedido explícito posterior del usuario, "cambiemos el nombre... por tipo de gasto"). Deliberado: renombrar el identificador técnico no aporta nada funcional y sí agrega riesgo/churn - si se retoma esto, buscar `justificacion_tipo` en todo el módulo antes de decidir si vale la pena.

- **Header**: `justificacion_tipo_id` (Many2one, required, default = el registro "Viáticos" vía `env.ref(xmlid)`).
- **Línea**: `justificacion_tipo_id` (Many2one, mismo modelo) - se **sugiere** desde el del encabezado al agregar la línea, pero queda **editable por línea** - pedido explícito: "puede ser cambiado si el jefe de técnico lo necesita cambiar". Reemplaza por completo al viejo campo `rubro` (Char) de la línea, que se eliminó.

**Bug real encontrado y corregido en esta sesión**: el mecanismo original de sugerencia era solo `default_get()` leyendo `self.env.context.get('default_request_id')` - funciona perfecto en un test (`Line.with_context(default_request_id=req.id).default_get(...)`) pero **nunca se disparaba en el formulario real**, porque el escenario normal es crear una Solicitud nueva y agregar líneas ANTES de guardar el encabezado - en ese momento `request_id` es un `NewId` (`odoo.models.NewId`, no un id real de base de datos), y Odoo **no** pasa `default_request_id` en el contexto para líneas agregadas a un one2many dentro de un formulario todavía sin guardar (ese context key solo aparece en flujos explícitos tipo wizard, como `action_crear_anticipo()` de este mismo módulo). Confirmado reproduciendo el escenario exacto con `.new()` en vez de `.create()` para AMBOS el encabezado y la línea. **El fix real es `@api.onchange('request_id')`** (`_onchange_request_id()`) - a diferencia de `default_get()`, el onchange SÍ funciona con el encabezado todavía en memoria/sin guardar, porque Odoo simula la línea nueva usando el estado actual (aunque no persistido) del formulario padre. `default_get()` se dejó como respaldo secundario (por si algún día se crea una línea programáticamente con ese contexto explícito), pero `_onchange_request_id()` es el mecanismo que realmente cubre el uso normal por formulario.
- **Vista**: la pestaña "Viáticos" ya no puede comparar `invisible="justificacion_tipo != 'viaticos'"` (ahora es un id, no un string) - se agregó un campo compute `es_viaticos` (Boolean, compara `justificacion_tipo_id` contra el registro resuelto por xmlid) para esa condición de visibilidad.
- **Sync**: como con `employee_id`/`analytic_account_id`, **nunca viaja el id** - `_prepare_sync_vals()` envía `justificacion_tipo_name` (texto) tanto en el encabezado como en cada línea. A diferencia de empleados/cuentas analíticas (que se resuelven en un **pull** periódico, con tiempo de sobra para buscar-o-crear con calma), esto llega en un **push** síncrono directo a un `create()` genérico vía RPC - por eso `account.payment.order.create()`/`.line.create()` ganan `_resolve_justificacion_tipo_name()`/lógica equivalente: si llega `justificacion_tipo_name` sin `justificacion_tipo_id`, se resuelve ahí mismo con `AccountPaymentOrderJustificationType._find_or_create_by_name()` (`sudo()`, ya que el usuario de integración no tiene permiso de escritura en el catálogo).

### Wizard "Crear Anticipo" (RETIRADO por la fusión - ver arriba): contacto prellenado + diario de banco + aviso de anticipos sin liquidar

Pedidos del usuario probando el flujo en Enterprise:

- **`partner_id` prellenado**: la ayuda del campo decía "no se recibe automáticamente... la instalación donde se originó la Solicitud es una base distinta" - ya no es cierto desde el rediseño "Contacto como fachada"/`employee_enterprise_ref": `employee_partner_id` de la Solicitud YA es un contacto real de la base de Enterprise para cuando llega a este wizard. Se agregó `default=lambda self: ...browse(self.env.context.get('default_request_id')).employee_partner_id` - sigue editable por si hace falta entregarlo a otro contacto.
- **`journal_id` con `domain=[('type', '=', 'bank')]`**: antes no tenía dominio (listaba cualquier diario, incluidos los de venta/compra).
- **Aviso de "Anticipos pendientes de liquidar"** (`account_payment_order.py: _find_anticipos_sin_liquidar()`, llamado desde `action_confirmar()` del wizard): si el contacto que va a recibir el Anticipo nuevo YA tiene otro(s) Anticipo(s) `state='aplicado'` sin una Liquidación registrada todavía (`anticipo_id` en ninguna Liquidación), se muestra un aviso (no bloquea - puede ser intencional, ej. viáticos de dos viajes distintos) y luego redirige igual al Anticipo recién creado, encadenado vía el mecanismo nativo `next` de `display_notification` (`..\odoo\addons\web\static\src\webclient\actions\client_actions.js:23` - `displayNotificationAction` retorna `params.next` como la siguiente acción a ejecutar). Mismo patrón conceptual que `_aviso_posible_pago_directo()`, ya existente.

**`cuenta_anticipo_id` deliberadamente NO se tocó** pese a un pedido posterior del usuario de "filtrar cuentas de gasto" ahí: ese campo alimenta directamente `action_conciliar()` (`CUENTAS_A_NETEAR = ('asset_receivable', 'liability_payable')`), el motor que netea el Anticipo contra las facturas reales del proveedor durante la Liquidación - si apuntara a una cuenta de gasto en vez de por cobrar/por pagar, esa conciliación dejaría de encontrar sus propias líneas y fallaría en silencio, sin ningún error visible. Señalado al usuario explícitamente antes de tocar nada; confirmó dejarlo como está.

### Bug real: `InvalidDomainError` en `payment_method_line_id` con un diario sin métodos de pago

Reportado por el usuario en producción, al elegir un diario de banco en el Wizard "Crear Anticipo": `Invalid domain representation: id,in,`. Causa: tanto el Wizard como `account.payment.order` (`payment_method_line_id`) tenían `domain="[('id', 'in', journal_id.outbound_payment_method_line_ids)]"` - navegar un Many2many **directo por punto dentro de un `domain=` en string** revienta en el cliente en cuanto esa lista queda **vacía** (diario de banco sin métodos de pago outbound configurados) - el propio parser JS de dominios no sabe serializar `id,in,<lista vacía>` correctamente. Preexistente desde antes de esta sesión (`account_payment_order.py`), solo se manifestó ahora porque el nuevo `domain=[('type','=','bank')]` de `journal_id` empezó a permitir seleccionar diarios de banco que, en la práctica, no tenían métodos de pago configurados.

**El fix - mismo patrón que usa el propio Odoo** (`account.payment.available_payment_method_line_ids`, `..\odoo\addons\account\models\account_payment.py`): nunca naveges un Many2many por punto dentro de un domain string - materializa un campo `Many2many` calculado intermedio (`available_payment_method_line_ids`, `@api.depends('journal_id')`) y apunta el domain a ESE campo top-level en su lugar. Aplicado en **ambos** lugares (`account_payment_order.py` y el Wizard) - el campo auxiliar se agregó a ambas vistas con `invisible="1"` (necesario: un domain string solo puede referenciar campos que el formulario efectivamente tiene cargados).

### Bug real: la Cuenta Analítica ("Proyecto") nunca llegaba como relación real a Enterprise, solo como texto

Reportado por el usuario en producción: eligió una Cuenta Analítica al capturar un Anticipo Viáticos en Community, y al Enviar, `analytic_account_id` llegaba **vacío** en Enterprise (aunque el texto "Proyecto" sí se veía bien). Causa: `_prepare_sync_vals()` solo mandaba `proyecto` (el nombre en texto plano) - nunca mandó ninguna referencia resoluble, pese a que `account.analytic.account` YA tiene `enterprise_analytic_ref` (el id original en Enterprise, poblado por `_sync_analytic_accounts_from_enterprise()` al jalar el catálogo) - el mismo mecanismo que `enterprise_employee_ref` usa para empleados. Y `_fill_derived_vals_from_analytic_account()` solo sabe derivar `proyecto` A PARTIR de un `analytic_account_id` ya dado, nunca al revés - así que no había ningún camino para reconstruir la relación del lado de Enterprise.

**El fix - mismo patrón que `_resolve_employee_enterprise_ref()`**: `_prepare_sync_vals()` ahora también manda `analytic_enterprise_ref: self.analytic_account_id.enterprise_analytic_ref`, y un nuevo `_resolve_analytic_enterprise_ref(vals)` en `create()` lo resuelve hacia un `analytic_account_id` real vía `browse(int(ref))` directo (el ref YA es el id real en Enterprise, no hace falta buscar por ningún otro campo). Verificado con un script que simula el mirror en Community (con `enterprise_analytic_ref` apuntando a una cuenta analítica "real") y confirma que la Orden recibida en Enterprise trae `analytic_account_id` como relación real, no solo el texto.

### Intento revertido: `cuenta_contable_id` (Tipo de Gasto) + sync de cuentas/diarios de Enterprise

El usuario pidió, y luego pidió deshacer en el mismo hilo, una función para configurar una cuenta contable de gastos por Tipo de Gasto: primero un campo simple (`account.account` directo), luego - al notar que Community no tiene el plan de cuentas real de Enterprise - un modelo espejo completo (`account.payment.order.enterprise.account`/`...journal`, sync consciente del rol, botón en Ajustes).
