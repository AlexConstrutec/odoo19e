# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

Guatemala payroll compliance reports: 11 XLSX-generating wizards (Planilla de Sueldos, Libro de Sueldos y Salarios, Informe del Empleador, Planilla IGSS, Reporte de Descuentos, Pasivo Laboral × 3, Reporte de Facturación, Reporte Liquidación Empleados, Detalle de Recibos de Nómina) plus QWeb PDF reports (constancia laboral, constancia de ingresos, historial laboral, solicitud IRTRA, salary voucher). Migrated from `gth_reports` + `nomina_report` (`..\Odoo16\`). Depends on both `construtec_hr_payroll_19` and `construtec_hr_employee_19`.

## Architecture

- **`wizard/wizard_mixin.py`** (`construtec.nomina.report.wizard.mixin`, an `AbstractModel`) carries `state`/`name`/`data`/`company_id`, `check_date()`, `got_back()`, `new_workbook()`/`finalize_workbook()` (in-memory `xlsxwriter`, no temp files — the original wrote to `tempfile.gettempdir()`), and `selection_label()`. All 10 wizard classes inherit it — don't re-declare that boilerplate in a new wizard, inherit the mixin.
- **`models/hr_dias_laborados_mes.py`**: replaces a hardcoded year-specific "días laborados por mes" table that was baked into the original `WizardInformeEmpleador` Python code. **This table needs manual review/update every calendar year** (Guatemala's official asuetos change) — it's now editable data (Settings → HR → Configuration → Días Laborados por Mes), not code, but nobody will remind you to update it; if you're touching `Informe del Empleador` around year-end, check this table's current year has rows.
- **`_compute_promedios()`** (`models/hr_employee.py`) is the 3-month rolling average salary calculation used by constancia-de-ingresos-style reports — genuinely intricate (quincena-pairing logic to reconstruct "full months" from biweekly payslips). It was restructured (dict-based buckets instead of ~24 parallel scalar variables) but the *math* was preserved exactly from the Odoo 16 source; if a client disputes a number here, diff against `..\Odoo16\gth_reports\models\hr_employee.py`'s `_compute_promedios` before assuming the port introduced a bug.
- **`send_salary_voucher()`** in `construtec_hr_payroll_19` resolves `construtec_hr_reports_19.email_template_voucher` via `env.ref(raise_if_not_found=False)` — that XML-ID is defined in `data/voucher_email_template.xml` here. If you rename it, the payroll module's voucher emailing silently stops (no error, just never sends).
- **`mail.template.report_template` → `report_template_ids`** (Many2many now) and **`report_name` field is gone** (Odoo 19 mail.template) — if you touch `data/voucher_email_template.xml`, use the current field names, not what the Odoo 16 source used.
- **`hr.version` custom fields carry an `x_` prefix**: `x_bonificacion_fija`, `x_bonificacion_incentivo`, `x_bonificacion_productividad`, `x_horas_extra_valor` (declared in `construtec_hr_payroll_19/models/hr_version.py`). Several wizards here originally referenced them without the prefix (`version.horas_extra_valor`, `version.bonificacion_incentivo`, etc.) or referenced fields that were **commented out and never activated** during the Odoo 16→19 port (`version.estado_contrato`, `version.empresa_facturar`, `employee.ocupacion_puesto_id`, `version.tiempo_contrato` — all still visible, commented, in `hr_version.py`/`hr_employee.py` in `construtec_hr_payroll_19`) — every one of those raises `AttributeError` the moment the report actually runs (production hit this live in `report_planilla_sueldos.py` on 2026-08-17). If you're porting more logic from `..\Odoo16\` into this module, grep the target `hr.version`/`hr.employee` field name in the current model file **before** trusting the Odoo 16 source's name — don't assume it survived unrenamed. `account.payment` also lost its `ref` field at some point (v19 has `memo`/`payment_reference`, not `ref`).
- **A batch of fixes for exactly the class of bug above sat uncommitted in the working tree for an unknown amount of time before finally being committed** (see commit history around 2026-08-17) — `report_planilla_sueldos.py`, `report_facturacion.py`, `report_informe_empleador.py`, `report_libro_sueldos.py`, `report_liquidacion.py`, `report_planilla_igss.py`, `report_prestaciones.py`, and `models/hr_employee.py` were all affected. **Lesson: after fixing a bug in this repo, commit and push it (both `odoo19e` and `odoo19enterprise`, per the standing two-repo rule) before moving to the next task** — a correct fix that never leaves the working directory is indistinguishable from no fix at all, from production's perspective.
- **`wizard/report_detalle_nomina.py` (`wizard.reporte.detalle.nomina`) uses a fixed, curated `CONCEPTS` list — NOT the fully-dynamic per-run column discovery this wizard started with.** Two designs were tried and rejected before landing here, both worth knowing about if you're tempted to "simplify" this again:
  - *Attempt 1*: discover columns at runtime from whatever `code`/`name` appear in `payslip.line_ids`. Correct in principle, but the Visor needs those same columns in a genuine native Odoo list view, and a list view's columns are fixed in its XML `arch` — a per-run dynamic column count can't be expressed there (patching the web client's `ListRenderer` at runtime was already considered and explicitly rejected earlier in this project as too broad/risky — see `[[feedback_cautela_produccion]]`).
  - *Attempt 2*: `fields.Properties`/`fields.PropertiesDefinition` (the same mechanism `hr_payroll` itself uses for `hr.payslip.payslip_properties`) — the web client's `ListRenderer` natively expands a `properties`-typed field into one real column per defined property, no custom JS needed. This worked, **but** Odoo hardcodes every Properties-derived list column to `optional: "hide"` in `getPropertyFieldColumns()` (`web/static/src/views/list/list_renderer.js`) — they always start hidden behind the column-selector (⚙) gear, with no arch/model-level override. The user explicitly wants every column visible with zero clicks, so this was dropped too.
  - **What's actually here**: `CONCEPTS` is an ordered list of `{field, label, codes, kind}` dicts, one entry per salary-rule concept already confirmed across this module's other wizards (`report_planilla_sueldos.py`/`report_libro_sueldos.py`/`report_planilla_igss.py`) plus what the user directly confirmed (`ANT1`=Vales, `ANT2`=Otros Descuentos, `ANT3`=Prestamos — `LO` is also Prestamo, see `construtec_hr_payroll_19/models/hr_payslip.py::_compute_extra_inputs()`, so `prestamos` sums both codes). Any rule code that shows up in a payslip but isn't in `CONCEPTS` (and isn't in `EXCLUDED_CODES`) gets folded into a trailing **"Otros Conceptos"** column instead of silently vanishing. `wizard.reporte.detalle.nomina.line` declares one real `Float` field per `CONCEPTS` entry (plus `otros_conceptos`) — real fields default to visible, so every column shows up with zero clicks, at the cost of needing a code update (`CONCEPTS`) if this client's payroll ever introduces a genuinely new rule concept that should get its own column instead of landing in "Otros Conceptos".
  - Both outputs share `_compute_matrix()` as the single source of truth — one row per payslip, one column per `CONCEPTS` entry (`headers`/`rows`/`totals`/`column_kinds`), plus the underlying `payslips` recordset aligned 1:1 with `rows` so callers can pull real employee/job/department/lote records, not just their printed labels.
  - **"Excel" (`action_excel`)** writes that grid straight into an `xlsxwriter` sheet, writes the binary directly, and returns an `ir.actions.act_url` with `download=true` so the browser downloads it immediately — no intermediate "here's your file" screen. Each concept column is colored light green (`kind='add'`) or light red (`kind='sub'`) per its hardcoded classification in `CONCEPTS`; "Otros Conceptos" is left neutral since it can mix both.
  - **"Visor" (`action_ver`)** builds one `wizard.reporte.detalle.nomina.line` per payslip (throwaway, garbage-collected by the normal `TransientModel` vacuum) and opens them in a real `ir.actions.act_window` (`view_mode: 'list'`) — every `CONCEPTS` field has `optional="show"` in `wizard/report_detalle_nomina_views.xml` (visible by default, still togglable) and `sum="Total"` for a native footer total. No per-concept add/sub coloring here (a `decoration-*` row color doesn't fit — each row is a whole payslip mixing both earnings and deductions).
  - If a 12th wizard needs a fixed, known column layout printed straight to Excel (a legal/compliance report), copy the pattern from `report_planilla_igss.py` instead of either of these two.
- **`_get_payslips()`'s state filter is `state != 'cancel'`, not `state in ('validated', 'paid')`** like `report_libro_sueldos.py`/`report_planilla_igss.py` use — this was a deliberate fix: those two are legal/compliance reports that should only ever reflect closed payroll, but this wizard is a review/export tool, and a user who generates several `hr.payslip.run` lotes but has only validated one of them still expects to see all of them (draft included) for the selected date range. Don't tighten this back to `validated`/`paid` without checking whether that's actually what's wanted this time.
- The `date_start`/`date_end` filter in `_get_payslips()` uses **overlap** semantics (`date_from <= date_end AND date_to >= date_start`), not strict containment, so a payslip whose period only partially falls inside the selected range still shows up — don't "simplify" this back to containment, it was a deliberate fix for lotes being dropped when their period didn't nest exactly inside Del/Al.

## Wizard "Exportar Vouchers (PDF)" - alternativa práctica de corto plazo a WhatsApp

Pedido del usuario (2026-08-31): mientras se resuelve una integración WhatsApp real para el envío de vouchers (considerada "muy compleja" por ahora, ver `construtec_whatsapp_19`), necesitaba una forma práctica de sacar los PDFs de varios empleados/lotes a la vez para poder distribuirlos manualmente.

- **`wizard/export_voucher.py`** (`wizard.export.voucher`, standalone - no hereda `wizard_mixin`, ya que no genera Excel ni necesita `check_date()`): dos campos Many2many, **`payslip_run_ids`** (lotes) y **`employee_ids`** (empleados), **combinables** - si se llenan ambos, el filtro es la intersección (nóminas de esos empleados dentro de esos lotes); si solo se llena uno, filtra solo por ese criterio; si no se llena ninguno, `action_exportar()` bloquea con `UserError` (evita exportar TODAS las nóminas de la base por accidente). `action_exportar()` arma el domain, busca en `hr.payslip` (excluyendo solo `state == 'cancel'`, mismo criterio ya establecido en `_get_payslips()` de `report_detalle_nomina.py` - esto es una herramienta de exportación, no un reporte legal, así que borradores también cuentan).

- **Primer intento (revertido) - un solo PDF combinado, con `t-foreach` agregado al template**: la primera versión de este wizard llamaba `report_action(payslips)` sobre el reporte fijo `construtec_hr_reports_19.report_voucher`, y para que ese reporte soportara varios payslips a la vez se envolvió su plantilla (`voucher_templates.xml`) en un `t-foreach="docs" t-as="doc"`, incluyendo el `<div class="header">` (logo/nombre de compañía) DENTRO del loop. **El usuario probó esto y reportó un PDF "gigante, sin logos"** - causa real: `<div class="header">` es tratado de forma especial por wkhtmltopdf (se extrae una sola vez y se repite en cada página física vía `--header-html`); duplicarlo dentro de un `t-foreach` rompe esa extracción (dejan de ser el header repetido y pasan a ser bloques de contenido normal, apilados una vez por nómina - de ahí el PDF inflado sin logos). El patrón correcto para esto ya existía en el propio módulo (`constancia_laboral`, ver `custom_internal_layout`): ocultar el header estándar y meter el logo como contenido normal DENTRO de cada `.page` - pero como el diseño final (ver abajo) ya no combina PDFs en un solo archivo, esto quedó sin necesidad: **`voucher_templates.xml` se revirtió a su forma original de un solo registro** (`docs.campo`, sin `t-foreach`), sin ningún cambio respecto a antes de esta pasada.

- **Diseño final: un PDF por nómina, empaquetados en un ZIP, reutilizando el reporte de CADA estructura salarial** - pedido explícito del usuario tras probar el primer intento: "cada estructura trae su váucher... necesito que ese váucher se reutilice", más "que todos vengan en un archivo ZIP... cada PDF que sea individual y no un mega archivo". `action_exportar()` ahora:
  1. Llama `payslips._get_pdf_reports()` - el mismo método **core** de `hr_payroll` (`hr_payslip.py`) que Odoo usa internamente al validar una nómina para decidir qué reporte imprimir: si `payslip.struct_id.report_id` está configurado, usa ESE reporte; si no, cae al reporte genérico de stock (`hr_payroll.action_report_payslip`). Reutilizar este método (en vez de forzar `report_voucher` a la fuerza) es lo que garantiza que cada estructura salarial imprima con el voucher que tiene configurado, igual que el PDF que ya se adjunta solo al validar.
  2. Por cada nómina, renderiza un PDF individual (`ir.actions.report.sudo().with_context(lang=...)._render_qweb_pdf(report, slip.id)` - mismo patrón exacto que usa el propio `_generate_pdf()` de core) y lo agrega a un `zipfile.ZipFile` en memoria (`io.BytesIO`, sin archivos temporales - mismo criterio que `new_workbook()` del mixin de Excel).
  3. El ZIP se guarda como `ir.attachment` y se descarga con `ir.actions.act_url`/`download=true` - mismo patrón ya usado por `action_generar_csv_banrural()` en `construtec_hr_employee_19`.
  - **Nombre de cada archivo dentro del ZIP** (`_voucher_filename()`, pedido explícito del usuario, "solo para esta exportación" - no toca el contenido del voucher ni ningún reporte compartido): `<primer_nombre> <primer_apellido> - <lote o período>.pdf`. Si dos nóminas seleccionadas resuelven al mismo nombre (mismo primer_nombre/apellido, ej. dos personas distintas con nombres parecidos, o el mismo empleado en el mismo lote dos veces), se agrega un contador `(2)`, `(3)`... para no sobrescribir un archivo con otro dentro del ZIP - verificado forzando esa colisión a propósito.
- **Este reporte (`report_voucher`) era "huérfano" antes de este wizard**: no tenía ningún botón/menú que lo llamara directamente (no es un `binding_type` sobre `hr.payslip`, y el único código que lo referenciaba - `send_salary_voucher()` en `construtec_hr_payroll_19/models/hr_payslip.py` - está comentado/desactivado). Sigue siendo el reporte que hay que configurar en `report_id` de cada estructura salarial que deba usarlo (Ajustes > Nómina > Estructuras Salariales) - este wizard no asume que TODAS las estructuras lo usan, solo respeta lo que cada una tenga configurado.
- **Menú**: "Exportar Vouchers (PDF)" en el mismo submenú de reportes de nómina (`hr_payroll.menu_hr_payroll_report`), junto a "Detalle de Recibos de Nómina".
- Verificado con un script real (`odoo-bin shell`): bloqueo sin criterios; filtro solo por lote; filtro solo por empleado; combinación lote+empleado; **ZIP con 3 PDFs individuales válidos (no un PDF combinado)**; nombres de archivo con primer_nombre/primer_apellido; colisión de nombre resuelta con contador; confirmado que `_get_pdf_reports()` resuelve al reporte configurado en la estructura salarial (se probó apuntando la estructura por defecto a `report_voucher` y confirmando que el ZIP usa ese reporte, no el genérico de stock).
- **No implementado, fuera de alcance de este pedido**: envío automático (WhatsApp/correo) del PDF resultante - el wizard solo genera/descarga el ZIP, la distribución sigue siendo manual por ahora, tal como pidió el usuario explícitamente ("algo más práctico por el momento a corto plazo").

### Aparte, no relacionado: PDF desactualizado tras Borrador → Validar de nuevo (comportamiento nativo de Odoo, sin cambios de código)

Reportado por el usuario en la misma conversación: al pasar una nómina a Borrador y volver a validarla, el PDF que Odoo adjunta automáticamente al chatter (vía `_generate_pdf()`, core `hr_payroll`) **no se actualiza** - `_generate_pdf()` solo AGREGA un adjunto nuevo cada vez que se valida, nunca borra el anterior, y `action_payslip_draft()` (también core) solo limpia el adjunto de `payment_report`, no estos. **Explícitamente no se tocó código para esto** - el usuario pidió una solución operativa (borrar el adjunto viejo a mano desde el chatter de esa nómina), no un cambio en el repositorio. El wizard "Exportar Vouchers (PDF)" de arriba es, de paso, inmune a este problema: renderiza en vivo cada vez, nunca depende de un adjunto guardado.

## Known gaps (by design)

None currently — all 10 wizards + 6 PDF reports were built and smoke-tested. If a future report is added to this module, follow the existing pattern (inherit the mixin, use `hr.version`/`hr.employee` fields already established in the two dependency modules, don't reintroduce `hr.contract`).
