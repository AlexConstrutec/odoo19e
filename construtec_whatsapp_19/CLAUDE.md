# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

Sends a WhatsApp message (via Meta's WhatsApp Business Cloud API) to a configurable list of contacts whenever an `account.payment.order` (from the sibling module `construtec_account_payment_order_19`, which this module `depends` on) gets Sent (`action_submit()`). Built to replace `construtec_helpdesk_whatsapp` (ticket-focused, being retired per the user's own call - "no me sirve realmente") as this workspace's WhatsApp integration going forward - fully independent module, no shared code, safe to have both installed at once or to remove the old one at any time.

## Why "grupo de destinatarios" is a list of contacts, not a real WhatsApp group

**The official Meta WhatsApp Business Cloud API has no supported way to send to a WhatsApp Group** - only 1:1 messages to individual phone numbers. The user initially asked for "notificar a contactos o grupos de WhatsApp"; after this limitation was explained, explicitly confirmed: contacts only, no real WhatsApp groups. `construtec.whatsapp.recipient.group` is Odoo's own abstraction for "notify several people at once" - a named list of `res.partner` contacts; sending to it just means sending the same template individually to each contact's `phone`. Don't ever try to build actual WhatsApp-group messaging on top of this - it isn't possible through the sanctioned API (only via unofficial WhatsApp Web automation, which violates Meta's ToS and risks a ban - explicitly out of scope, the user wanted to stay compliant).

## Why template messages only, never free text

Meta requires a **pre-approved message template** for any business-initiated message sent outside a 24h customer-service window - which is exactly what "notify on Orden de Pago submit" is (the business is initiating contact, not replying to something the recipient sent first). `tools/whatsapp_api.py`'s `send_whatsapp_template()` only ever builds a `"type": "template"` payload - there is no free-text send path in this module, on purpose, to avoid building something that looks fine in ad-hoc testing (replying within 24h of your own test message) and then silently violates policy / gets the message rejected in real use.

Templates themselves are created and approved **in Meta Business Manager**, not in Odoo - `construtec.whatsapp.template` is just a small catalog recording the exact `meta_template_name`/`meta_template_language` Meta approved, plus a free-text `param_help` reminder of what each `{{1}}`, `{{2}}`... placeholder means. Getting the name/language wrong (even a typo, or wrong language code) makes the Graph API reject the send.

## Architecture

- **Credentials** (`res.company`): `whatsapp_enabled`, `whatsapp_phone_number_id`, `whatsapp_access_token`, `whatsapp_api_version` (default `v21.0`), `whatsapp_business_account_id` (WABA id, reference only - templates are managed in Meta, not here). Exposed in Ajustes > Contabilidad > "WhatsApp (Meta Cloud API)", with a "Probar conexión" button (`action_test_whatsapp_connection()`, calls `check_phone_number()` - reads the phone number's own info, sends no message, safe to click anytime).
- **Payment-order-specific config** (`res.company` too): `payment_order_whatsapp_enabled`, `payment_order_whatsapp_template_id` (which `construtec.whatsapp.template` to use), `payment_order_whatsapp_recipient_group_id` (which `construtec.whatsapp.recipient.group` to notify) - a separate block in the same Settings page, only shown once the general `whatsapp_enabled` is on.
- **`tools/whatsapp_api.py`**: deliberately explicit-scalar-args style (not "pass me a company record"), matching `construtec_account_payment_order_19/tools/enterprise_sync_api.py`'s own convention in the module this one depends on - easy to unit-test by monkeypatching the module-level function, easy to reuse without any ORM coupling. `send_whatsapp_template()` raises `WhatsAppApiError` on ANY failure (missing config, network error, Meta rejecting the request) rather than returning a silent `False` like the sibling helpdesk module does - callers need the real reason to log/show it.
- **`res.company._send_whatsapp_template(template, to_number, params)`**: the actual entry point other code should call. Never raises - catches `WhatsAppApiError`, logs to `construtec.whatsapp.log` either way (success or failure), returns `(ok, message)`. No-ops (returns `(False, ...)`) if `whatsapp_enabled` is off, without even trying the API call.
- **`account.payment.order` (`_inherit`)**: `action_submit()` calls `super()` first (so the actual state transition and Enterprise sync from the sibling module always run first, untouched), then `_send_whatsapp_submit_notification()`. That method is fully config-driven off `res.company` - if `payment_order_whatsapp_enabled` is off, or the template/recipient group aren't set, it's a silent no-op (logged at `info` level only, doesn't block or complain loudly, since not every company needs this). Never raises - a WhatsApp failure must never prevent `action_submit()` from completing, same principle as `_sync_to_enterprise()` in the sibling module.
- **Chatter, always** (explicit user requirement): after attempting all recipients, posts ONE `message_post()` on the Order itself summarizing every attempt with ✅/❌ per contact (and the API's own error message inline for failures) - regardless of the company-level `construtec.whatsapp.log` (kept too, for a cross-order "what's been going wrong with WhatsApp lately" view in Settings). If the resolved recipient group has zero contacts with a `phone` set, posts a distinct chatter note saying so instead of silently doing nothing.
- **`res.partner.phone`**, not `.mobile`: **`res.partner` in this Odoo 19 build has no `mobile` field at all** (confirmed by reading `odoo/addons/base/models/res_partner.py` directly - it's not there) - `phone` is the only number field, used everywhere in this module (`whatsapp.recipient.group._get_phone_numbers()`, the notification code). Don't reintroduce a `mobile` reference by copying an older Odoo pattern from memory/docs.
- **Security**: `group_whatsapp_manager` (new, implied by `account.group_account_invoice`) can create/edit templates and recipient groups and configure the Settings page - deliberately NOT gated behind `base.group_system` (Ajustes técnicos/Administrador), so a normal Accounting admin can configure all of this without needing IT/developer involvement, matching the user's explicit ask ("que la configuración no dependa de codificación sino únicamente de configuración de usuario normal"). `base.group_user` can only read templates/groups (e.g. to see what's configured), not edit them.
- **`res.groups` has no `category_id` field in this Odoo 19 build** (real error hit while building this: `ValueError: Invalid field 'category_id' in 'res.groups'`) - don't set it when defining a new group; this project's own `res.groups.privilege`/`privilege_id` mechanism (used elsewhere for approval-level groups) is the Odoo 19 replacement concept, not needed here since this is a single flat group.

## El link a la Orden de Pago viaja en el CUERPO, no en un botón (corregido 2026-08-09)

El diseño original de este módulo asumía un botón "Sitio web" con URL dinámica en la plantilla de Meta (ver `send_whatsapp_template()`'s `button_param` en `tools/whatsapp_api.py`, que sigue existiendo como mecanismo opcional/reutilizable). **La plantilla real aprobada ("orden_pago_enviada") no usa ese botón** - Meta Business Manager la muestra sin ningún botón configurado; en cambio, tiene **4 variables en el cuerpo**, la última de las cuales es el link completo como texto plano: `"...Link {{4}} Gracias"`.

Mandar solo 3 parámetros de cuerpo (como el diseño original hacía) - o mandar además un componente de botón que la plantilla no tiene - es exactamente lo que producía el error real de Meta: **"Number of parameters does not match the expected number of params"**, visto en el chatter de una Orden real (`OP/0026`, 2026-08-09). `_send_whatsapp_submit_notification()` ahora arma los 4 parámetros de cuerpo (`rec.name`, `rec.partner_id.name`, monto, link completo) y **no** manda `button_param`.

- El link sigue apuntando a **Community, no a Enterprise** (`https://erp.construtecasesores.com/web#id={id}&model=account.payment.order&view_type=form`) - decisión explícita del usuario, aunque la aprobación real ("Aprobar") solo pasa en Enterprise. Quien reciba el WhatsApp puede ver la Orden desde este link, pero para aprobarla necesita entrar a Enterprise por separado.
- **Antes de tocar esto de nuevo**: verificar el contenido EXACTO de la plantilla en Meta Business Manager (Administrador de WhatsApp > Plantillas de mensajes > "orden_pago_enviada" > Editar) - no asumir la estructura desde este archivo ni desde el código; las plantillas se editan del lado de Meta sin que este repo se entere, y un desajuste de cantidad/orden de variables es exactamente este bug.
- El mecanismo de `button_param` en `tools/whatsapp_api.py`/`_send_whatsapp_template()` **no se eliminó** - sigue disponible por si una plantilla futura sí usa un botón de URL dinámica en vez de (o además de) un link en el cuerpo.

## Meta account setup (for whoever configures this, not code)

1. Meta Business Manager (business.facebook.com) - Business Portfolio in the company's name, verified (legal docs).
2. developers.facebook.com - a Business-type App, WhatsApp product added, linked to a WhatsApp Business Account (WABA) under that portfolio.
3. A dedicated phone number (not already active on personal/Business WhatsApp), verified, with an approved Display Name.
4. **Permanent Access Token required for anything automatic** - the 24h temporary token from the API Setup screen is fine for manual testing only; create a System User in Business Manager with `whatsapp_business_messaging` permission for a real permanent token, or every unattended send will start failing whenever it expires with zero warning.
5. At least one Message Template approved for this use case (e.g. body: `"Orden de Pago {{1}} fue enviada. Contacto: {{2}}. Monto: Q{{3}}."`) - record its exact name/language in a `construtec.whatsapp.template` record once approved.
6. Opt-in: every contact in a `construtec.whatsapp.recipient.group` should have actually agreed to receive WhatsApp messages from the company - Meta's messaging tier/quality rating drops if people block/report the number, which can throttle or suspend it regardless of who's technically "internal" (approvers) vs "external" (customers) - there's no such distinction in Meta's policy.

## Cuatro eventos, no solo "Enviado": `construtec.whatsapp.payment.order.notification`

Pedido explícito del usuario, después de probar el flujo completo de Anticipo→Liquidado en `construtec_account_payment_order_19`: "necesito que se comunique... cuando hayan aprobado la solicitud, cuando se haya aplicado el pago, cuando se haya liquidado" - no solo al Enviar. Confirmó de paso la restricción ya asumida por este módulo: "solo existe la vía de las plantillas en WhatsApp" (correcto, sin cambios de fondo aquí).

**El diseño viejo** (un solo par `res.company.payment_order_whatsapp_template_id`/`_recipient_group_id`, cableado únicamente a `action_submit()`) no escalaba a 4 eventos sin agregar 6 campos más y 3 métodos casi idénticos. Se reemplazó por un modelo de mapeo, **`construtec.whatsapp.payment.order.notification`** (`state` → `template_id` → `recipient_group_id` + `notify_interesado`, una fila por evento, editable en **WhatsApp > Notificaciones de Órdenes de Pago** sin tocar código) - agregar un evento nuevo el día de mañana es una fila más en esa lista, no un campo/método nuevo.

- **Triggers**: `account_payment_order.py` ahora sobreescribe `action_submit()`/`action_approve()`/`action_aplicar()`/`action_conciliar()` (los 4 puntos reales de transición del ciclo Anticipo/Anticipo Viáticos/Pago Directo en el módulo del que depende), cada uno llamando a `super()` primero y luego a `_send_whatsapp_payment_order_notification(state)` con el estado correspondiente - nunca se repite la lógica de armar destinatarios/enviar/loggear, todo vive en ese único método genérico.
- **Dos vías de destinatarios, no excluyentes** (decisión explícita del usuario: "al jefe de técnicos/empleado de esa solicitud, además del grupo fijo"): el `recipient_group_id` de esa notificación (igual que antes, un grupo fijo tipo Administración) Y, si `notify_interesado` está activo, el propio contacto de la Orden (`partner_id.name`/`rec.telefono` - el mismo campo que ya usa el flujo de Anticipo Viáticos para el empleado solicitante). **Deduplicados por número** (comparando solo dígitos) antes de enviar - si el interesado ya está en el grupo fijo, no le llega el mensaje dos veces.
- **Mismos 4 parámetros de plantilla para los 4 eventos, a propósito** (`_whatsapp_payment_order_params()`, un solo método compartido): nombre de la Orden, contacto, monto, link - igual que la plantilla "orden_pago_enviada" ya aprobada. Las plantillas de Aprobado/Aplicado/Liquidado **todavía no existen ni están aprobadas en Meta** al momento de escribir esto - se optó por no inventar variables distintas por evento sin saber qué aprobará Meta; si una plantilla futura necesita otra estructura, ese método puede partirse por evento entonces. **Antes de activar cada notificación nueva**: crear y aprobar la plantilla correspondiente en Meta Business Manager y verificar ahí mismo que tenga EXACTAMENTE 4 variables en el cuerpo, mismo criterio ya aprendido con la plantilla de Enviado (ver la sección de arriba sobre el bug real de conteo de parámetros).
- **Ahora instalado también en Odoo19E (Enterprise)** - Aprobado/Aplicado/Liquidado ocurren ahí, no en Community (que solo llega a Enviado localmente). El módulo no necesitó ningún cambio de dependencias (ya dependía solo de `construtec_account_payment_order_19`, instalado en ambas ediciones) - solo copiarlo a la carpeta `odoo19e` e instalarlo ahí, exactamente como ya se hace con el módulo del que depende. Cada instalación (Community/Enterprise) mantiene sus propias credenciales/plantillas/grupos/notificaciones - bases de datos separadas, nada se comparte.
- **Migración de datos** (`migrations/19.0.2.0.0/post-migrate.py`): si ya existía una configuración real para "Enviado" (los campos viejos en `res.company`), se migra automáticamente a una fila `state='enviado'` en el nuevo modelo, con `notify_interesado=False` (para no cambiar el comportamiento ya en producción - antes nunca se notificaba al interesado, solo al grupo fijo). Lee las columnas viejas por SQL directo (`information_schema.columns` primero, por si la instalación es nueva y esas columnas nunca existieron) porque para cuando corre un post-migrate, el ORM ya solo conoce los campos nuevos.
- Verificado con un mock de `send_whatsapp_template()` (sin ningún llamado real a la API de Meta): los 4 eventos disparan correctamente hacia el grupo fijo y el interesado; un número duplicado entre ambos no se manda dos veces; el interruptor general apagado no manda nada; la migración simulando el esquema viejo (columnas agregadas a mano + datos de prueba) crea la fila `enviado` esperada.

## Status as of this writing (2026-08)

- Built and unit-tested (mocked `send_whatsapp_template` - no real Graph API call made from this environment, no real WhatsApp message has been sent by this code yet).
- The user's own personal/dev Meta account is what's configured for now; a proper company-owned Business Manager account is planned for later (`whatsapp_business_account_id` exists specifically so switching accounts later is a Settings change, never a code change).
- Solo la plantilla "Enviado" (`orden_pago_enviada`) existe/está aprobada en Meta - Aprobado/Aplicado/Liquidado necesitan sus propias plantillas creadas y aprobadas ahí antes de poder configurarse en `construtec.whatsapp.payment.order.notification`.
- Instalado en Odoo19C (Community) y, desde este cambio, también en Odoo19E (Enterprise) - cada uno con su propia configuración/credenciales, bases de datos separadas.
