# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

Genérico, no ligado a ningún flujo de negocio de los demás módulos `construtec_*`: una bitácora de auditoría configurable — desde un panel (Ajustes, sin tocar código) el administrador elige **qué modelos** auditar, **qué operaciones** (creación/modificación/eliminación), si guardar **valores de campos** (antes/después) o solo el hecho de que hubo un cambio, y una **retención** (días/meses/años) por modelo para autoeliminar la bitácora vieja vía tarea planificada. `depends: ['base']` únicamente — instala igual de bien en Community y en Enterprise, sin ninguna dependencia de los demás módulos de este workspace.

Motivación del usuario (2026-08-27): con varias sesiones de Claude Code trabajando en la misma carpeta a la vez, y producción real ya corriendo en Enterprise, hacía falta un mecanismo de auditoría visible **dentro de Odoo** — no dependiente de git ni de este asistente — para poder reconstruir quién creó/modificó/eliminó qué, en caso de un cambio inesperado.

## El mecanismo: `_inherit = 'base'`, no un modelo por modelo

El requisito "elegir cualquier modelo desde un panel, sin tocar código" solo se puede lograr interceptando `create`/`write`/`unlink` de forma **centralizada**, para TODOS los modelos del sistema — la alternativa (heredar explícitamente cada modelo a auditar desde código) obligaría a tocar el módulo cada vez que se quiera auditar un modelo nuevo, exactamente lo que el usuario quería evitar. Confirmado explícitamente con el usuario antes de construir esto (ver `feedback_cautela_produccion` en la memoria de este asistente — cualquier mecanismo de efecto global sobre producción se confirma antes de implementar), entendiendo que agrega un chequeo a TODA escritura del sistema, no solo a los modelos auditados.

`models/base_audit.py` define `class Base(models.AbstractModel): _inherit = 'base'` — **`'base'` es un modelo real de la ORM, y cualquier addon puede fusionarse (`_inherit`) con él para agregar comportamiento a absolutamente todos los modelos del registro**, exactamente el mismo mecanismo que usa el propio Odoo en varios módulos núcleo (`odoo/addons/whatsapp/models/models.py`, `odoo/addons/sms/models/models.py`, `odoo/addons/web_studio/models/models.py`, etc. — verificado leyendo esos archivos directamente antes de construir esto, no asumido). Esto es distinto y más seguro que un monkeypatch crudo sobre la clase Python `odoo.models.BaseModel` (que también existe como técnica en otros proyectos, pero fuera del mecanismo de composición normal de la ORM) — aquí el `super()` de `write()`/`create()`/`unlink()` se resuelve por el MRO normal de Odoo, compatible con cualquier otro módulo que también sobrescriba esos métodos en un modelo específico.

**Por qué esto NO es tan costoso como suena**: para cualquier modelo sin regla configurada, el chequeo es un solo lookup en un `dict` cacheado en memoria (`AuditLogRule._get_active_rules_map()`, decorado con `@tools.ormcache()`) que falla y retorna `False` de inmediato — nunca hay una consulta SQL por operación, solo una consulta SQL la primera vez que se llena el caché (o cuando se invalida). Verificado con un script real: crear/modificar/eliminar un registro de un modelo SIN regla (`res.country.state`) no genera ningún log — el overhead es indistinguible de no tener el módulo instalado.

**Activar/desactivar auditoría en caliente, sin reiniciar el servidor**: a diferencia de `_register_hook()` (el mecanismo que usan otros módulos tipo-auditoría, pero que solo se re-ejecuta en un rebuild completo del registry — instalar/actualizar un módulo, no en un simple guardado de un formulario), aquí la regla misma vive en una tabla normal (`construtec.audit.log.rule`) y su `create()`/`write()`/`unlink()` llaman `self.env.registry.clear_all_caches()` — el próximo `create`/`write`/`unlink` de cualquier modelo, en cualquier worker, vuelve a consultar la configuración real. Verificado: desactivar una regla (`active=False`) detiene la auditoría de inmediato, sin reiniciar nada.

## Qué se guarda, y qué nunca se guarda

- **`construtec.audit.log`** (bitácora, un registro por operación): `res_model`/`res_id`/`res_name` (snapshot del `display_name` en ese momento — sigue siendo legible aunque el registro real ya no exista, caso de `unlink`), `method` (create/write/unlink), `user_id`, `create_date` (la propia fecha del log sirve de fecha de la operación, sin duplicar un campo). **Inmutable desde la UI**: `perm_write=0, perm_unlink=0` incluso para el grupo administrador (`security/ir.model.access.csv`) — el único camino de escritura es el hook interno vía `.sudo()` (que ignora ACL por diseño), y el único camino de borrado es la tarea planificada de retención. Nadie puede editar o borrar una entrada de bitácora a mano desde el cliente web, ni con permisos de Administrador.
- **`construtec.audit.log.line`** (una fila por campo que cambió): `field_name`/`field_description`, `old_value`/`new_value` (Text, formateados por `_construtec_audit_format_value()` — Many2one → `display_name`, Many2many/One2many → nombres separados por coma, Selection → la etiqueta legible, no la clave técnica).
  - **`create`**: solo `new_value` (no hay "antes"). **`unlink`**: solo `old_value` (snapshot final, tomado ANTES de `super().unlink()` — después del borrado ya no hay forma de leer el registro). **`write`**: ambos, y **solo para los campos que realmente cambiaron** (comparación antes/después, no todos los campos de `vals`) — verificado que escribir el mismo valor dos veces no genera una segunda entrada de bitácora.
- **Red de seguridad automática, incondicional**: campos de tipo `binary` nunca se guardan (evita blobs gigantes como texto), y cualquier campo cuyo nombre técnico contenga `password`/`token`/`secret`/`api_key`/`apikey` (case-insensitive) nunca se guarda **aunque `capture_field_values` esté activo y el campo no esté en `excluded_field_ids`** — verificado creando un `res.users` con `password` en una regla de auditoría activa: el campo nunca aparece en la bitácora. Esta red de seguridad no es configurable a propósito (no debería serlo: nadie debería poder, ni por error, exponer una contraseña en texto plano en un log).
- **`excluded_field_ids`** (por regla, configurable): campos adicionales que el administrador quiera excluir explícitamente (ruidosos o irrelevantes) — se resta de la lista de campos auditables antes de leer nada, no después.
- **`capture_field_values=False`** (por regla): sigue generando la entrada de bitácora (quién/cuándo/qué operación/sobre qué registro), pero **ninguna línea de campo** — ni siquiera los nombres de los campos que cambiaron. Decisión explícita del usuario vía confirmación previa: por defecto se guardan valores (más útil), pero queda disponible el modo liviano por si algún modelo genera demasiado volumen.

## Retención: por modelo, cron único, "0 = conservar para siempre"

`retention_number`/`retention_unit` (días/meses/años) en la propia regla — `0` (default) significa **conservar indefinidamente**, decisión explícita confirmada con el usuario (más seguro que un default automático que podría borrar evidencia sin que nadie lo haya pedido). `AuditLogRule._cron_cleanup_logs()` (`ir.cron` diario, `data/audit_log_cleanup_cron.xml`) recorre solo las reglas con `retention_number > 0`, calcula el corte con `dateutil.relativedelta` (los nombres de `retention_unit` — `days`/`months`/`years` — son literalmente los nombres de argumento que `relativedelta` acepta, elegidos a propósito para poder pasarlos como `**kwargs` sin traducir nada) y elimina lo que ya superó esa antigüedad. Un solo cron global (no uno por modelo) — mismo criterio ya aceptado en otros cron de este workspace para el volumen real esperado.

**Bug real encontrado y corregido al instalar**: `ir.cron` en este build de Odoo 19 **ya no tiene el campo `numbercall`** (`odoo/addons/base/models/ir_cron.py` — un cron corre indefinidamente mientras `active=True`, sin límite de repeticiones configurable) — el intento inicial de `data/audit_log_cleanup_cron.xml` lo incluía (patrón de versiones anteriores de Odoo) y tronaba con `ValueError: Invalid field 'numbercall' in 'ir.cron'` al instalar. Se quitó el campo del XML.

**Bug real encontrado y corregido en la vista de búsqueda**: `<group expand="0" string="Agrupar por">` (el patrón clásico de "Group By" en un search view de versiones anteriores de Odoo) ya **no es válido** en el esquema RelaxNG de este build (`odoo/addons/base/rng/common.rng` — el elemento `group` dentro de un `search` ya no acepta los atributos `string` ni `expand`, solo `colspan`/`rowspan`/`fill`/`height`/`width`/`name`/`color`/`invisible`) — confirmado leyendo el RNG y comparando contra el patrón real y vigente en `odoo/addons/account/views/account_move_views.xml` (`view_account_move_filter`): un `<group>` sin esos atributos, con un `<separator/>` antes, es la forma correcta hoy. Si se ve `Invalid view ... search definition` en algún search view de este workspace, sospechar primero de este mismo patrón obsoleto antes que de otra cosa.

## Seguridad

Un solo grupo, `group_construtec_audit_log_manager`, implica `base.group_system` (Ajustes Técnicos/Administrador) — deliberadamente restringido a ese nivel, no a un rol más amplio: poder ver "qué cambió en cualquier registro del sistema" (incluyendo, potencialmente, datos de otros módulos que el propio usuario no tendría permiso de ver directamente) es información sensible por definición. Si en el futuro se necesita un "auditor" con acceso de solo lectura a la bitácora pero sin ser Administrador completo, ese sería un grupo nuevo intermedio — no construido ahora porque no se pidió.

## Verificación

Instalado en base desechable (`construtec_test_audit`) y verificado con un script real (`odoo-bin shell`) cubriendo: bloqueo de auditar los propios modelos del módulo; creación registra valores iniciales; modificación registra antes/después solo de lo que cambió; escribir el mismo valor no genera ruido; eliminación guarda un snapshot completo justo antes de borrar; un modelo sin regla nunca genera bitácora (overhead real cero); desactivar una regla detiene la auditoría sin reiniciar nada; `excluded_field_ids` funciona; un campo con nombre sensible (`password`) nunca se guarda aunque no esté excluido explícitamente; el cron de retención elimina solo lo más viejo que la antigüedad configurada; `retention_number=0` conserva todo indefinidamente incluso con datos de años de antigüedad.
