# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

Company-level fiscal/legal fields for Guatemala: `res.company.regimen_iva` (VAT regime before the SAT), `nombre_legal` (legal name), `codigo_establecimiento` (SAT establishment code). Added via `views/res_company_views.xml` (inherits `base.view_company_form`), right before `company_registry`.

## Why this exists instead of installing `l10n_gt_edi`

Stock Odoo already ships a Guatemala electronic-invoicing module (`l10n_gt_edi`) with an equivalent field (`res.company.l10n_gt_edi_vat_affiliation`, same 8 selection values) — but that module is **hardcoded to INFILE, S.A.** as the certifier (see `l10n_gt_edi/models/res_company.py`: field labels literally say "Infile Web Service Provider", "Infile Key (LlaveAPI)", and the invoice report prints "Certificador: INFILE, S.A." as static text). Since the client's actual FEL certifier wasn't confirmed at the time this was built, this module replicates just the 3 non-certifier-specific fields (regime + legal name + establishment code) so reports/payroll can reference them now, without committing to Infile.

## Known gap (by design, not by accident)

**No electronic-invoicing (FEL) integration yet.** `l10n_gt_edi`'s certifier-specific fields (`l10n_gt_edi_service_provider`, `l10n_gt_edi_infile_key`, `l10n_gt_edi_infile_token`, `l10n_gt_edi_ws_prefix`, `l10n_gt_edi_phrase_ids`) were deliberately **not** replicated — "las funciones de certificación las haremos después" (per the user). When that scope is picked up, first confirm which certifier Construtec actually uses before building against it (don't assume Infile).

## SAT document import (n8n → bandeja de revisión → factura)

A second, unrelated scope: an n8n workflow logs into the SAT Agencia Virtual portal (browser automation — no public API for this exists), downloads DTEs (both `recibidas`/compras and `emitidas`/ventas, since Construtec issues its sales invoices **outside** Odoo), and writes them into Odoo via the standard external API (XML-RPC/JSON-RPC) as a **staging record**, not directly as an `account.move`. This is deliberately a different scope from the FEL gap above — it's about *archiving/booking documents already certified by SAT*, not about *certifying/sending* invoices from Odoo.

- **`construtec.sat.document`** (`models/sat_document.py`) — one row per DTE: `direction` (recibida/emitida), `numero_autorizacion` (SAT's UUID, unique via `models.Constraint` so retries can't duplicate a document), `tipo_dte` (Selection: `FACT`/`FCAM`/`FESP`/`FPEQ`/`FCAP`/`NABN`/`NCRE`/`NDEB`/`RECI`/`CIVA`/`FAPE` — each verified against a real DTE XML that actually failed and got fixed (`FAPE` = Factura de Pequeño Contribuyente Especial, per the emisor's real `AfiliacionIVA="PEE"` and Decreto 31-2024's Régimen de Pequeño Contribuyente Especial) — plus `FEXP`/`RDON`/`RSP`/`NENV`/`RECC`/`REPA`/`CRET`, added preemptively from the SAT's public DTE catalog (not yet seen in a real document) to reduce how often this list gets caught short. Selection fields reject anything not in the list with `ValueError: Wrong value for ... tipo_dte`, which has already broken a real import three times (`RECI`, `CIVA`, `FAPE`) — the SAT keeps adding DTE types over time (e.g. Decreto 31-2024), so treat any future occurrence of this exact error as "add the missing code here", not a real bug), `serie`/`numero_documento`, `fecha_certificacion`, raw `nit_emisor`/`nombre_emisor`/`nit_receptor`/`nombre_receptor` from the DTE, a resolved `partner_id` (resolved/created by NIT — mirrors how `l10n_gt_edi` itself identifies parties, no custom NIT field on `res.partner`), `xml_attachment_id`/`pdf_attachment_id` (real `ir.attachment` records, same pattern `l10n_gt_edi_document.py` uses — not `Binary` fields), and `line_ids`. Also carries every other header field the DTE XML/Excel export exposes (see below) — `moneda_codigo`, `nombre_comercial_emisor`, `direccion_emisor`, `codigo_establecimiento`, `nit_certificador`/`nombre_certificador`, plus 11 non-IVA tax amount fields (`monto_petroleo`, `monto_turismo_hospedaje`, etc. — almost always zero, only populated for specific industries) and the Excel-only fields below. The user explicitly asked for "toda la información posible" rather than just the minimum needed for accounting.
- **`create_from_dte(vals)`** (`@api.model` on `construtec.sat.document`) is the single external-API entrypoint — the one method an outside caller (the Python bot, n8n, whatever) invokes via `execute_kw`/JSON-RPC instead of orchestrating `search_read`/`create`/`ir.attachment.create` itself. Takes header fields (same names as the model fields) plus `lines` (list of dicts matching `construtec.sat.document.line` fields) and optional `xml_filename`/`xml_base64`/`pdf_filename`/`pdf_base64`. In one transaction: checks the duplicate + NIT filter (see below), resolves/creates the `res.partner` by NIT (emisor if `direction='recibida'`, receptor if `'emitida'`, via private helpers `_sat_find_or_create_partner`/`_sat_create_attachment`), creates the header + lines + attachments, and writes a `construtec.sat.import.log` row. Idempotent on `numero_autorizacion`: a repeat call returns `{'state': 'skipped_duplicate', 'document_id': <existing>}` without creating anything — verified via `odoo-bin shell` against a real downloaded DTE XML (see the SAT bot doc below), including that a second call with the same `numero_autorizacion` is a no-op. On any exception it logs `state='error'` with the message and re-raises, so the external caller sees the RPC fault.
- **NIT filter** (`_sat_nits_permitidos()`): the real outbox on disk mixes documents from more than one SAT account (the company's own NIT plus the user's personal NIT, downloaded into the same folder structure) — `create_from_dte` rejects anything whose "own side" NIT (`nit_receptor` for `direction='recibida'`, `nit_emisor` for `'emitida'`) doesn't match `res.company.vat` of the active company, returning `state='nit_no_permitido'` (no document created, just a `construtec.sat.import.log` row) instead of a separate config parameter to maintain — deliberately reuses the NIT Odoo already has for the company (Ajustes > Compañías) rather than introducing a second place to keep it in sync. If the company has no NIT configured, nothing is filtered. Verified via `odoo-bin shell`: a document with a matching NIT is created normally, one with a different NIT is rejected with no record created and the correct log entry, and cleanup leaves the DB untouched.
- **`construtec.sat.document.line`** — one row per DTE line item (`numero_linea`, `bien_o_servicio` B/S, `descripcion`, `cantidad`, `precio_unitario`, `monto_iva`, `monto_total`). `product_id`/`account_id`/`tax_ids` are **left blank by n8n on purpose** — the user explicitly chose manual mapping over auto-matching by product code/description ("menos casos raros que depurar"). `monto_descuento`/`otro_descuento` (DTE's `Descuento`/`OtrosDescuento`) are captured but **not** translated into Odoo's percentage-based line `discount` field — informational only. Also `_inherit`s `analytic.mixin` (already a transitive dependency via `account`, no manifest change needed) purely for its `analytic_distribution` Json field + widget, matching the exact widget options `account.move.line` uses (`product_field`/`account_field`/`force_applicability: optional`/`multi_edit: true`) — lets the user assign analytic accounts per line before converting, same manual-mapping philosophy as `account_id`/`tax_ids`. Passed through verbatim into all three conversion targets' lines (`invoice_line_ids`, `purchase.order.line`, `sale.order.line` — all three natively support it too) — verified via `odoo-bin shell` for all three paths.
- **`cuenta_analitica_id`/`cuenta_contable_id`** on the header (`account.analytic.account`/`account.account`) are a bulk shortcut for the exact case where reviewing hundreds of purchase invoices one line at a time is too slow: pick **one** cost account for the whole document (costos directos/indirectos/gastos) instead of touching every line. `cuenta_contable_id` cascades to `line_ids.account_id`, but **the line's own value always wins if already set** — the header only fills lines where `account_id` is still blank (explicit user correction: a line-level `account_id`, whether set manually or by an earlier cascade, is never overwritten by a later header change). This runs in two places: `_onchange_cuenta_contable_id` for instant feedback in the form before saving, and on `write()` so it also fires from an API call or the list view's multi-edit (which onchange alone wouldn't catch) — both filter to `not line.account_id` before applying. `construtec.sat.document.line.create()` separately defaults a **new** line's `account_id` from the header's `cuenta_contable_id` when the line is added without an explicit `account_id` of its own (e.g. splitting a line after the header account is already set) — same "only when blank" rule. Practical implication: to change the cost account across a whole document after lines already got one, clear the lines' `account_id` first (or use the list view's multi-edit to blank them), then set the header again. Verified via `odoo-bin shell`: setting the header fills all-blank pre-existing lines; a line added afterward without `account_id` inherits it; a line added with an explicit `account_id` keeps it; changing the header to a different account afterward does **not** touch that line's already-set value, only still-blank ones.
  - `cuenta_analitica_id` is a single Many2one, deliberately simpler than the line-level `analytic_distribution` Json/widget above — no auto-cascade to lines, it's just a header-level reference field (no propagation logic requested for it).
  - **Not yet built, and deliberately out of scope for now**: reflecting the non-IVA tax amount fields (`monto_petroleo`, `monto_timbre_prensa`, etc.) as `account.tax` records or as separate GL lines. None of Guatemala's specific/selective taxes (IDP combustibles, timbre de prensa, bebidas alcohólicas/no alcohólicas, tabaco, cemento, tasa municipal, bomberos, turismo hospedaje/pasajes, tarifa portuaria) are creditable for a company that isn't the direct taxpayer of that specific tax — they're already embedded in the vendor's price, so forcing them through Odoo's tax engine would create fictitious fiscal credits or rounding mismatches against SAT's own (often fixed-quetzales-per-unit, not percentage) calculation. The header fields already capture the exact amounts for traceability; only **IVA 12%** (`impuestos_plantilla_iva_por_cobrar` in stock `l10n_gt`, if that chart is applied) and the two retention taxes (`tax_vat_withhold` -12%, `tax_isr_withhold` -5%, also in `l10n_gt`) are real `account.tax` candidates — and retentions specifically can never be inferred from the DTE itself (they depend on the vendor's own tax regime, not on anything in the document), so they stay a manual `tax_ids` pick like today.
- **Excel-only header fields** (`estado_sat`, `anulado`, `fecha_anulacion`, `clasificacion_emisor`, `exportacion`, `nombre_establecimiento`): the DTE XML is certified once and never changes, so it can never reflect a *later* cancellation — Agencia Virtual's own Excel export (one row per DTE, downloaded alongside XML/PDF, see the SAT bot section below) is the only source for whether a document was subsequently anulado. `anulado`/`fecha_anulacion` specifically exist because the user asked for this explicitly once told the XML can't carry it. These fields are populated by a **separate pass** (`update_from_excel_row`, see below) that only writes onto a document that already exists — it never creates one on its own.
- **Real bug found and fixed via a real production XML (a fuel invoice)**: `_parse_dte_xml()`'s header total-tax lookup only ever queried `<Totales><TotalImpuestos><TotalImpuesto NombreCorto='IVA'>` and silently discarded every *other* `TotalImpuesto` in that same block — including `NombreCorto='PETROLEO'`, which a real Puma Energy fuel invoice **does** carry there (`TotalMontoImpuesto="1212.94"` in the reported case). Documents imported before this fix have `monto_petroleo` stuck at `0.00` even though the source XML always had the real number. Fixed generically via `_NOMBRE_CORTO_A_CAMPO` (currently `{'IVA': 'monto_iva', 'PETROLEO': 'monto_petroleo'}`) and `_extraer_totales_impuestos()` — add more entries here the moment a real document confirms another `NombreCorto` (e.g. for `monto_timbre_prensa`), same incremental-verification convention as `TIPO_DTE_SELECTION`. A **second, related bug** in the same area: the **line-level** `monto_iva` was summing *every* `<Item><Impuestos><Impuesto>` regardless of `NombreCorto` — a fuel line item carries both an `IVA` and a `PETROLEO` sub-impuesto in the same `<Impuestos>` block, so a line's `monto_iva` was silently inflated by the petroleo amount too (in the reported case, `150.53 + 186.05 = 336.58` stored instead of `150.53`). Fixed by filtering that sum to `NombreCorto == 'IVA'` only — there's no per-line field for the specific taxes (they're document-level totals by design), so a non-IVA per-item impuesto is now correctly discarded at the line level rather than misfiled as IVA.
- **`action_rectificar_desde_xml()`** (form button "Rectificar desde XML", visible when `xml_attachment_id` is set and either `state == 'pendiente'` or `tipo_dte` is `NCRE`/`NDEB`, plus the same bulk-selection `ir.actions.server` binding as the other document actions) is the recovery tool for documents that were imported **before** a parser fix like the one above — it re-decodes the document's own already-stored `xml_attachment_id`, re-runs the current `_parse_dte_xml()`, and rewrites exactly the header fields in `_CAMPOS_RECTIFICABLES_DESDE_XML` (the same set `create_from_dte()` writes at creation time) with whatever the parser produces today. Deliberately does **not** touch `numero_autorizacion` (the search key), `direction`, `partner_id`, `state`, or `line_ids`/their `account_id`/`tax_ids` — those represent decisions already made (partner resolution, manual account/tax review) that a data-rectification pass has no business overriding. After rewriting the header, it re-runs `_sat_apply_to_line()` on every line (in case a previously-zero condition field like `monto_petroleo` now satisfies a categorization rule). Each document's rectification runs in its own `self.env.cr.savepoint()` so one failure (e.g. a genuinely missing/corrupted attachment blob — hit for real during development, from a `filestore` entry that no longer existed for a years-old test record) doesn't poison the rest of a bulk selection. Verified via `odoo-bin shell` against the real Puma Energy XML that surfaced the bug above: a document manually reset to the old-buggy state (`monto_petroleo=0`) was correctly restored to `1212.94` (and `monto_iva` back to `2210.05`) after clicking; a second click is idempotent (no error, same result); a document with a genuinely unreadable attachment correctly reported 1 error without crashing the whole batch; a document with no `xml_attachment_id` at all was correctly skipped as "omitido", not an error.
  - **For an already-converted NCRE/NDEB** (`state != 'pendiente'`), the header-refresh path doesn't apply (rewriting header fields on a document whose `account.move` already exists has no accounting effect) — instead `_sat_verificar_enlace_nota()` runs: if `numero_autorizacion_referencia` is set, the referenced document now has its own `move_id`, and this note's own move is still missing `reversed_entry_id`/`debit_origin_id` (the exact situation the user asked to be checked — the reference wasn't available yet when this note was *originally* converted, per the reference-linking feature above), it links the two moves now. For NCRE specifically, if **both** moves already happen to be posted, it also calls `original_move._reconcile_reversed_moves(note_move, False)` directly — the same reconciliation Odoo normally runs automatically inside `_post()`, called by hand here because that posting already happened in the past, before the link existed. Posts a chatter note on the note's `account.move` (not on `construtec.sat.document` — that model has no `mail.thread`, an actual `AttributeError` hit and fixed during development) documenting the retroactive fix. A second run against an already-linked note is a correct no-op (tallied as "omitido", not "corregido"). The notification message reports 4 buckets: `Encabezados corregidos` (pendiente path) / `Enlaces de nota corregidos` (this path) / `Omitidos` / `Errores`. Verified via `odoo-bin shell`: an NCRE converted before its original existed (unlinked, as expected) → the original gets imported and posted afterward → rectify finds and links it, and posting the NCRE afterward shows the original's `amount_residual` dropped by exactly the NCRE's amount (real reconciliation, not just a cosmetic field) → a second rectify call correctly does nothing.
- **The `soft_reload` UI bug, found from a real screenshot report**: every "utility" action in this module that mutates records and returns only a `display_notification` (`action_convertir_a_factura_masivo`, `action_aplicar_reglas_categorizacion`, `action_rectificar_desde_xml`, `action_fix_mangled_accents`, `action_extraer_codigo`, `action_retry_pending_sync_notify`, `action_retry_sync`) **did update the database correctly**, but when triggered from an **already-open form view** of the affected record, that form kept showing stale field values — a plain `display_notification` action does not make the Odoo web client re-read the record; only a manual page refresh did. Confirmed against a real case: the user clicked "Aplicar Reglas de Categorización" on an open document, the notification presumably fired, but the visible `account_id`/`tax_ids` never appeared to change, read as "nothing happened." Fixed by chaining `'next': {'type': 'ir.actions.client', 'tag': 'soft_reload'}` inside every one of those `params` dicts (`action_retry_sync`, which returned nothing at all, now returns the bare `soft_reload` action) — same pattern stock Odoo itself uses for this exact situation (e.g. `account/models/account_account.py`, `account_online_payment/models/account_online_link.py`). Any *new* notification-returning action added to this module going forward should include this from the start.
- **`state`** is `pendiente` / `convertido_factura` / `convertido_orden_compra` — a document can only go down **one** of those two conversion paths, never both (both action methods raise `UserError` once `state != 'pendiente'`). This was a 2-value field (`pendiente`/`convertido`) before the Orden de Compra path was added; renamed instead of adding a separate boolean, since the two outcomes are mutually exclusive by design.
- **`action_convertir_a_factura()`** on the header builds `invoice_line_ids` from the lines (requires every line to have `account_id` set, raises `UserError` otherwise), picks `move_type` from `direction` + `tipo_dte`, and **re-parents** the two attachments (`ir.attachment.write({'res_model': 'account.move', 'res_id': move.id})`) so they show up in the invoice's own chatter instead of staying attached to the now-historical staging record. Sets `move.sat_document_id` back-reference and `move.message_main_attachment_id` to the PDF. `invoice_date`, `date`, and **`invoice_date_due`** are all set to `fecha_certificacion` — explicitly chosen over letting Odoo compute the due date from the partner's payment term, since the SAT document doesn't carry a real due date at all and defaulting to "today" (Odoo's own fallback when there's nothing better) would silently be wrong for anything imported after the fact (e.g. a backfill of old documents). `invoice_date_due` is technically a stored computed field (`depends('needed_terms')`, so in principle a payment term could re-trigger its own computation and override an explicit value) — verified via `odoo-bin shell` with a vendor that has a real 30-day payment term configured that the explicit value still sticks (`invoice_date_due == fecha_certificacion`, not `+30 días`).
  - `move_type` selection: only `tipo_dte == 'NCRE'` (Nota de Crédito) maps to `in_refund`/`out_refund`. `NDEB` (Nota de Débito) maps to a **normal** `in_invoice`/`out_invoice` — a debit note *increases* what's owed, it is not a refund; this mirrors how Odoo's own "Debit Note" wizard works (creates a new regular invoice/bill, not a credit note). Getting this wrong was an actual bug caught and fixed here — don't re-collapse `NCRE`/`NDEB` into one bucket. See `TIPOS_DTE_NOTA_CREDITO` (only `('NCRE',)`).
  - **NCRE/NDEB reference linking, so the note actually gets the right accounting effect (not just the right `move_type`)**: the DTE carries which original document a note corrects, via a `cno:ReferenciasNota` element — `NumeroAutorizacionDocumentoOrigen` specifically. `_extraer_referencia_nota()` (`sat_document_import.py`) parses this into two header fields, `numero_autorizacion_referencia`/`motivo_ajuste_nota`, threaded through `_parse_dte_xml()` → `create_from_dte()` same as every other field. **Real bug, found from a real XML that this field was silently coming back empty for**: this was first written matching stock Odoo's own `l10n_gt_edi` *emission* template (`server\odoo\addons\l10n_gt_edi\data\templates.xml`, `dte_complemento_referencias`), which wraps `cno:ReferenciasNota` in a parent `<dte:Complemento IDComplemento="Notas">` — but a real DTE actually certified by INFILE for a real credit note used `IDComplemento="ReferenciasNota"` instead, and the parser was filtering strictly on `IDComplemento == 'Notas'`, so it never found the element and both fields stayed `None`/blank on every real note. What Odoo *emits* and what a third-party certifier actually *produces* for the same complement aren't guaranteed to agree on that attribute's exact string. Fixed by finding `cno:ReferenciasNota` directly, by its namespace, anywhere in the tree — not gating on the parent `Complemento`'s `IDComplemento` value at all, since the namespace on the child element is the only part actually guaranteed stable. Also applied `_fix_mangled_accents()` to `motivo_ajuste_nota` (it has the same `?`-for-accented-vowel corruption as everything else from this certifier) and added `ANULACION` to the dictionary, confirmed from a real value ("Anulaci?n, Por error se agregó un ítem...") — the rest of that field is free-form text typed by whoever issued the note, so most of a real sentence stays with unresolved `?`s on purpose (same "don't guess" rule; this field is purely informational and never feeds accounting logic). Verified via `odoo-bin shell` against the real complement fragment reported: `numero_autorizacion_referencia` now correctly extracted, `motivo_ajuste_nota` correctly recovers "Anulación" while leaving the rest of the sentence's unmatched `?`s alone.
  - In `action_convertir_a_factura()`: if `tipo_dte` is `NCRE`/`NDEB` and `numero_autorizacion_referencia` is set, look up a `construtec.sat.document` with that `numero_autorizacion` that already has a `move_id` (i.e., already converted). If found: **NCRE** gets `reversed_entry_id` set to that move (Odoo's own reversal-linking field) — this makes the credit note **auto-reconcile against the original invoice's specific open balance when posted** (`account.move._post()`'s own `_reconcile_reversed_moves` logic, triggered automatically — nothing custom needed here, just setting the field correctly). **NDEB** gets `debit_origin_id` instead (from the `account_debit_note` module, now a manifest dependency) — informational/traceability only, debit notes don't auto-reconcile the way credit notes do, since they're a *new* charge, not a correction being netted against something.
  - **Deliberately does NOT use Odoo's `account.move._reverse_moves()`** (the mechanism the "Credit Note" wizard uses, which fully copies the original invoice's lines and negates them) — that assumes the note reverses the *entire* original invoice, which isn't always true (a SAT Nota de Crédito can be partial — correcting only some lines/quantities). Building the move from the **note's own lines** (as before) stays correct for both full and partial notes; only the *linking* (`reversed_entry_id`) is new. Verified via `odoo-bin shell`: a partial NCRE (30 of an original 100) correctly left the original invoice's residual at exactly `115 - 34.5 = 80.5` (both including the same 15% tax) after posting both moves — a real partial reconciliation, not a full write-off.
  - **Tax default from the referenced invoice**: if the referenced move's product lines all share exactly one `tax_ids` combination, that combination becomes the default for any note line that doesn't already have its own `tax_ids` set (never overrides one already set) — directly addresses "cómo garantizo que la nota tenga los mismos impuestos que la factura original" without needing the user to re-pick them, while still not guessing when the original itself used mixed tax rates per line (same "don't guess" rule as `_fix_mangled_accents`/`action_extraer_codigo`).
  - **Graceful fallback when no reference is found** (original not yet imported, outside the tracked range, or the DTE simply didn't carry the complement): conversion proceeds exactly as before — no link, no tax default — but a chatter message is posted on the resulting move naming the missing reference number, so it's visibly flagged for manual review/reconciliation instead of silently looking "done." Verified via `odoo-bin shell` for all 4 combinations: NCRE found (linked + tax defaulted + partially reconciled on posting), NCRE not found (no link, chatter warning posted, no crash), and NDEB found (`debit_origin_id` set, still a normal `in_invoice`).
  - **Form UI**: the single "Convertir a Factura" button is now 3 mutually-exclusive buttons sharing the same `action_convertir_a_factura()` method, labeled by `tipo_dte` — "Convertir a Factura" (anything else), "Convertir a Nota de Crédito" (`NCRE`), "Convertir a Nota de Débito" (`NDEB`) — directly addresses the confusion of the button always saying "Factura" even when converting a note. The "Detalle SAT" tab shows `numero_autorizacion_referencia`/`motivo_ajuste_nota` only when `tipo_dte` is `NCRE`/`NDEB`.
- **`action_convertir_a_factura_masivo()`** is the bulk counterpart, for selecting many documents at once in the list view (compras, ventas, notas de crédito/débito, any mix) and converting them all from the **Acciones** (⚙) menu — bound via `ir.actions.server` with `binding_model_id`/`binding_view_types = 'list,form'` (Odoo's standard way to add a contextual action to a model's selection menu; the action's own `code` calls `records.action_convertir_a_factura_masivo()`, `records` being the selected recordset — same idiom stock Odoo itself uses, e.g. `account.move`'s own "Share" binding in `account_data.xml`). It's a thin loop around the existing single-document `action_convertir_a_factura()` — no duplicated conversion logic, so a bulk conversion behaves identically per-document to converting one at a time (same `move_type` rules, same NCRE/NDEB reference linking, same IVA auto-tax). Already-converted documents in the selection are silently skipped (tallied separately, not an error) and a document that fails validation (e.g. missing `account_id`) does **not** stop the rest — each attempt runs inside its own `self.env.cr.savepoint()` so a DB-level failure (not just an early `UserError`) can't poison the whole batch's transaction for the remaining documents. Returns a summary notification: `Convertidos: X | Ya convertidos (omitidos): Y | Errores: Z`, with per-document error detail only in the server log (`_logger.exception`), not the notification body. Verified via `odoo-bin shell` with a mixed batch of 5 (recibida FACT, emitida FACT, NCRE, one with a missing `account_id`, one already converted beforehand) — exactly 3 converted, 1 skipped, 1 errored, and the 4 that should have succeeded all did, independent of the one that failed.

## Catálogo de Productos de Proveedor (referencia de precio, no `product.product`)

`construtec.sat.product.catalog` (`models/sat_product_catalog.py`) answers a real gap: `construtec.sat.document.line` accumulates products from many different suppliers (materials, hardware, whatever a `recibida` DTE lists), but creating a real `product.product` per line item is the wrong level of detail for accounting — too many one-off items, no purchasing/inventory value at that granularity. What técnicos *do* want is a quick lookup of "what did we last pay this supplier for this item, and when" without any of that becoming part of the accounting product master. This model is that lookup table — deliberately **not** a `product.product`.

- **Fields**: `name` (from the DTE line's `descripcion`), `codigo` (see extraction rule below), `partner_id` (proveedor — only makes sense for `direction='recibida'`, an `emitida` document has no "proveedor"), `uom_id` (Many2one `uom.uom`, **always blank on auto-creation** — the SAT DTE has no unit-of-measure field at all, so this is filled in by hand by whoever knows the actual unit), `precio_referencia` (unit price from the most recent matching line), `primera_fecha_compra`/`ultima_fecha_compra` (both `Date`, readonly), `sync_state` (`pendiente`/`sincronizado`/`error`) + `sync_error`/`sync_date` for the Community sync below.
- **Dedup key**: `(company_id, partner_id, name_normalized)` unique constraint, where `name_normalized` is `name.strip().upper()` (computed, stored). No fuzzy matching — a supplier that writes the same product two slightly different ways on two invoices gets two catalog rows, on purpose (matches this module's existing "don't guess" philosophy, see `_fix_mangled_accents`).
- **`codigo` extraction** (`_sat_extract_codigo(name)`, module-level function): the SAT DTE has no separate product-code field, so if a supplier includes one it's embedded in `descripcion` in one of three shapes, tried in this order — bracketed (`"[C2X-2] COMBO 2 CAMARAS..."` → `C2X-2`), before a pipe (`"8471.30.00 | LAPTOP DELL..."` → `8471.30.00`), or a leading digit run of 4+ followed by whitespace (`"784512 CABLE UTP CAT6..."` → `784512` — the 4-digit floor is deliberate, so a leading quantity like `"2 CAJAS DE CLAVOS"` isn't misread as a code). No match → `False`, same "leave it blank rather than guess" rule as everywhere else in this module. Computed **once, at catalog-entry creation** (`_sat_register_from_line`) — never recomputed on the update path, since `name` itself never changes after creation (only `precio_referencia`/`ultima_fecha_compra` do). Editable by hand afterward; a manually-set or already-populated `codigo` is never overwritten automatically.
- **`action_extraer_codigo()`** (menu "Documentos SAT" → "Extraer Código de Producto") is the one-time backfill for entries created before this field existed — same "only touch what's empty" rule as `action_fix_mangled_accents`. Verified via `odoo-bin shell`: all 3 extraction shapes plus 2 negative cases (free-text description, and a short leading quantity that must NOT be read as a code) all matched expectations; the backfill action recovered a cleared `codigo` without touching an entry that already had one.
- **Populated automatically from `create_from_dte()`** (see `sat_document.py`, right after `line_ids`/attachments are created): loops `document.line_ids` and calls `ConstructecSatProductCatalog._sat_register_from_line(document, line)` for each — skipped entirely for `direction='emitida'`. Each call is wrapped in its own `try/except` (logged, not re-raised) so a problem here can never prevent the SAT document/factura itself from being saved — that's the actually-important record.
- **Date logic handles backfill, not just chronological imports**: `primera_fecha_compra` only moves *earlier*, `ultima_fecha_compra`/`precio_referencia` only move *later-or-equal* (by the document's `fecha_certificacion`, not import order) — importing an old historical range *after* recent documents were already imported won't stomp `ultima_fecha_compra`/`precio_referencia` with stale data, and re-importing the same range twice is a no-op (no spurious sync). Verified via `odoo-bin shell`: 3 synthetic documents for the same supplier+product created out of chronological order (recent, then an older backfill, then an even-more-recent one) — `primera_fecha_compra` correctly tracked the oldest, `ultima_fecha_compra`/`precio_referencia` correctly tracked the newest at each step, and the catalog never duplicated the row (`search_count` stayed at 1).

### Outbound sync to Odoo19C (Community, module `construtec_materials_19`)

This is the **mirror image** of `construtec_materials_sync_19` (which receives Community → Enterprise for "Solicitud de Materiales"): here, Enterprise is the **caller**, pushing catalog changes to Community over Odoo's standard `/xmlrpc/2/*` endpoints — no custom controller needed on either side, same reasoning as the existing sync module.

- **Trigger**: `_sat_sync_to_community()` fires synchronously, right after `_sat_register_from_line()` actually creates a new catalog row or changes `primera_fecha_compra`/`ultima_fecha_compra`/`precio_referencia` on an existing one — not on every call (an import that changes nothing doesn't re-sync).
- **Connection config**: 4 system parameters (Ajustes > Técnico > Parámetros del Sistema), same convention as `sat_outbox_path`: `construtec_account_19.community_url`, `.community_db`, `.community_login`, `.community_api_key`. **Not yet set on any environment** — until they are, every sync attempt fails cleanly with `sync_state='error'` and a descriptive `sync_error` (verified via `odoo-bin shell`: this is the actual current behavior, not a hypothetical).
- **Resilience, deliberately**: a 10s socket timeout (`_TimeoutTransport`/`_TimeoutSafeTransport`, picked by URL scheme) so an unreachable Community never hangs `create_from_dte` for however long the OS's default TCP timeout is — this method runs inside the same request that n8n's `create_from_dte_xml` call is waiting on. Any failure (auth rejected, connection refused, timeout, missing config) is caught, logged (`_logger.warning`), and recorded on the record (`sync_state='error'`, `sync_error=str(exc)`) — **never** re-raised. Recovery: the "Reintentar Sincronización" button on the form (`action_retry_sync`), the "Reintentar Sincronizaciones Pendientes" bulk menu action (`action_retry_pending_sync_notify`), and an hourly `ir.cron` (`data/ir_cron_sat_product_catalog.xml`, `_cron_retry_pending_sync`) that retries anything not `sincronizado` — the cron is the actual safety net; the button/menu are for a human who wants it to happen *now*.
- **What gets sent** — `models_proxy.execute_kw(db, uid, api_key, 'construtec.materials.catalog.mirror', 'sync_from_enterprise', [vals])` with `vals`:
  ```
  {
      'origin_id': <int, this record's own id in Enterprise - the upsert key Community must key on>,
      'name': <str>,
      'codigo': <str or False, see the codigo extraction rule above>,
      'partner_name': <str, partner_id.display_name - plain text, NOT an id: Community's res.partner ids mean nothing here>,
      'partner_vat': <str or False>,
      'uom_name': <str or False, uom_id.display_name>,
      'currency_name': <str, e.g. 'GTQ'>,
      'precio_referencia': <float>,
      'primera_fecha_compra': <'YYYY-MM-DD' str or False>,
      'ultima_fecha_compra': <'YYYY-MM-DD' str or False>,
  }
  ```
- **What Community (`construtec_materials_19`) needs to implement — not built here, this is the contract Alex is replicating on that side**:
  1. A model (suggested name: `construtec.materials.catalog.mirror`) with plain-text/plain-value fields matching the payload above (no `Many2one` to Enterprise records — same "plain text mirror, not a live business object" reasoning as `helpdesk.material.requisition.mirror`, see that module's own CLAUDE.md).
  2. An `@api.model` method `sync_from_enterprise(vals)` that **upserts** by `vals['origin_id']` (search for an existing mirror row with that `origin_id`, `write()` if found, `create()` if not) — this must be idempotent and support updates, unlike the plain create-only inbox `helpdesk.material.requisition.mirror` uses, because catalog entries change over time (new `ultima_fecha_compra`/`precio_referencia`) and Enterprise re-sends the full row on every change rather than tracking "what already got sent."
  3. A dedicated, minimally-privileged integration user + API Key on **Community**, granted access to *only* that mirror model (mirror the `group_materials_sync_integration` pattern from `construtec_materials_sync_19/security/materials_sync_security.xml` — create-**and**-write here, since updates are required, but still nothing broader).
  4. Whatever user/API Key gets created there must then be entered into Enterprise's 4 system parameters above.

## Constancias de Retención de IVA (modelo separado de construtec.sat.document)

A user request to also archive "Constancias de Retención del IVA e ISR Recibidas" (a
different Agencia Virtual screen: Servicios Tributarios > Constancias de Retenciones y
Exenciones > Constancias de Retención del IVA e ISR Recibidas) — **deliberately a
separate model**, not part of `construtec.sat.document`, per explicit user request ("no
lo podemos trabajar en documento SAT"). A Constancia certifies that a client withheld
part of the IVA when paying Construtec for a sale — since this screen is "Retenciones
**Recibidas**", it always relates to `direction='emitida'` documents (Construtec's own
sales), never `recibida`.

- **`construtec.sat.retention`** (`models/sat_retention.py`) — header: `numero_constancia`
  (unique, the PDF's own "Número de Constancia"), `fecha_emision`, `nit_agente_retenedor`/
  `nombre_agente_retenedor` (the client who withheld), `agente_retenedor_partner_id`
  (resolved by NIT via **search only, no create** — deliberately different from
  `construtec.sat.document._sat_find_or_create_partner`, since this field is informational/
  reporting only, not the source of a real accounting record), `tipo_agente_retencion`
  (e.g. "CONTRIBUYENTES ESPECIALES"), `cantidad_facturas`, `monto_retencion_pdf` (the PDF's
  own "TOTAL" row, kept separate from `monto_retencion_total`/`monto_importe_neto_total`
  — both `compute='...', store=True` sums over `line_ids` — specifically so a
  parsing mismatch between the two is visible instead of silently trusted), `pdf_attachment_id`,
  `requiere_revision_manual` (see multi-invoice caveat below), and `state`
  (`pendiente`/`parcial`/`vinculada`, computed from how many lines have `sat_document_id` set).
- **`construtec.sat.retention.line`** — one row per invoice the constancia covers: `serie`/
  `numero_factura` (from the PDF), `concepto`/`tarifa`/`monto_importe_neto`/`monto_retencion`
  (from the PDF's "DETALLE DE CONSTANCIA" table), and `sat_document_id` (Many2one
  `construtec.sat.document`, domain `direction='emitida'`) — **resolved automatically on
  `create()`** by searching `construtec.sat.document` for a matching `serie` +
  `numero_documento` (confirmed from the real PDF: a Constancia references the original
  invoice via **Serie + Número de Factura**, NOT the DTE's `numero_autorizacion` UUID — those
  are exactly the existing `construtec.sat.document.serie`/`.numero_documento` fields, no new
  matching key needed). `move_id`/`partner_id` are `related` fields off `sat_document_id` for
  quick access. If no matching document exists yet (e.g. the constancia was imported before
  the corresponding sales invoice), the line is created unlinked and the header's
  **"Vincular Facturas"** button (`action_vincular_facturas`, fills-blanks-only, same
  "suggestion, not a silent lock-in" convention as `construtec.sat.categorization.rule`)
  retries the search later.
- **`create_from_pdf(pdf_base64, pdf_filename=None)`** (`@api.model`, `models/sat_retention.py`)
  is the entry point, idempotent on `numero_constancia` (returns `state='skipped_duplicate'`
  on a repeat, same pattern as `construtec.sat.document.create_from_dte`). Parses via
  `_parse_constancia_pdf` (`models/sat_retention_import.py`), creates the header + lines +
  `ir.attachment` in one transaction, and resolves `agente_retenedor_partner_id`. Reachable
  from the UI via **`construtec.sat.retention.import.wizard`** (menu "Documentos SAT" >
  "Importar Constancia (PDF)") — a simple upload-a-PDF-and-click-Importar wizard, since
  there's no automated download path from the bot yet for this screen (see below).
- **PDF parsing** (`_parse_constancia_pdf`, `models/sat_retention_import.py`) uses
  `pdfminer.six` (`extract_text`), **not** `PyPDF2` — both are already available in Odoo's
  bundled Python (no new dependency). `PyPDF2.extract_text()` was tried first and discarded:
  besides the same accent corruption described below, its table-cell reading order is
  unreliable for this form (date and Serie code came out concatenated with no separator,
  DETALLE DE CONSTANCIA columns out of visual order). `pdfminer.six` puts each value on its
  own line, which is reliable enough to anchor on fixed label text with regex (the form is a
  fixed SAT layout, "SAT-2229"). Fields extracted: `numero_constancia`, `nit_contribuyente`/
  `nombre_contribuyente` (should match Construtec's own NIT, since this is "Recibidas"),
  `fecha_emision` (from separate Día/Mes/Año labels), `cantidad_facturas` + a list of
  Serie/Número-de-Factura pairs, the DETALLE DE CONSTANCIA rows (concepto/tarifa/importe/
  retención — matched by regex on the `Q[\d,]+\.\d{2}`/`\d+%` value shapes, not by position,
  since concepto is free text), the PDF's own "TOTAL" retention amount, and
  `nit_agente_retenedor`/`nombre_agente_retenedor`/`tipo_agente_retencion`. Verified against
  the one real PDF available (`1771521747491.pdf`, `construtec_test`): every field extracted
  correctly, and the line's `serie`/`numero_factura` (`0E34E0C2`/`2323663424`) correctly
  auto-matched a REAL `construtec.sat.document` already present in `construtec_test`
  (`direction='emitida'`, same serie/numero, `nombre_receptor` matching the PDF's own agente
  retenedor name) — a genuine end-to-end match against real data, not just a parsing test.
  Also verified: re-importing the same PDF returns `skipped_duplicate`; `action_vincular_facturas`
  is a no-op both when already linked and when no matching document exists yet (correctly
  stays `pendiente`, never guesses a wrong match).
- **A second, DIFFERENT accent-corruption bug from the one `_fix_mangled_accents` was built
  for**: the DTE XML corruption (see below) replaces an accented character with a literal
  `?`; this PDF's corruption (a font-encoding issue inside the PDF itself, from
  `pdfminer.six`'s extraction) replaces it with the Unicode replacement character `�`
  (U+FFFD) instead — confirmed on real fixed form labels ("RETENCIÓN" → "RETENCI�N",
  "AÑO"/"DÍA" → "A�O"/"D�A"). `_fix_pdf_accents()` (`sat_retention_import.py`) reuses the
  *same* `_KNOWN_WORDS_RAW` dictionary from `sat_document_import.py` by replacing `�` with
  `?` before calling `_fix_mangled_accents()` — avoids maintaining two separate word lists
  for what is, once normalized, the same "recover an accented character by dictionary match,
  never guess" problem. Only applied to free-text fields (contact/agent names, `concepto`,
  `tipo_agente_retencion`) — never needed for the numeric/code fields that actually drive the
  invoice-matching logic.
- **Multi-invoice case (`cantidad_facturas > 1`) — CONFIRMED against a real 7-invoice PDF**.
  Turns out the form uses two genuinely different layouts, not just "more rows in the same
  table": for exactly 1 invoice, the Serie/Número pair sits directly on the single page next
  to a 1-row "DETALLE DE CONSTANCIA"; for more than 1, that page carries only an **aggregated**
  total (no per-invoice data at all) and a **second page** appears with a completely different
  table, "DETALLE DE RETENCIONES" — one row per invoice, columns Serie/Factura/Fecha, followed
  by **3 repeated groups** of Tarifa/Importe/Retención (only one of the three is non-zero per
  row in both real examples seen — the other two read `0%`/`Q0.00`, seemingly reserved slots for
  other retention-rate categories that didn't apply to Construtec's own retentions). Parsing:
  detect this second layout by anchoring on the "Serie Factura Fecha Tarifa Importe Retención
  Tarifa Importe Retención Tarifa Importe Retención" header (case-insensitive — this header
  prints as "Retención", title case, unlike "DETALLE DE CONSTANCIA"'s all-caps "RETENCIÓN"
  column, a real formatting difference between the two tables); a per-invoice `tarifa`/
  `monto_importe_neto`/`monto_retencion` is computed by summing the 3 buckets (naturally
  `0 + 0 + X = X`) and taking whichever bucket's tarifa is non-zero. `cantidad_facturas` is
  derived from `len(lines)` in both layouts (**not** from a "Cantidad de Facturas" label
  position — that value's exact position in the extracted text differs between the 1-invoice
  and multi-invoice layouts, confirmed real and not worth chasing positionally once the line
  count itself is authoritative). `construtec.sat.retention.line.fecha_factura` (new field) only
  gets populated in the multi-invoice layout — the per-invoice date the DETALLE DE RETENCIONES
  table happens to expose that the single-invoice layout doesn't repeat. Verified via
  `odoo-bin shell` against the real 7-invoice PDF: all 7 Serie/Número pairs correctly parsed
  and **every one auto-matched a real `construtec.sat.document` already in `construtec_test`**
  (`state` went straight to `vinculada`), and the sum of the 7 lines' `monto_retencion` matched
  the PDF's own page-1 aggregated total exactly (`594.54`) — a real, non-coincidental
  cross-check. `nit_agente_retenedor`/`nit_contribuyente` regexes were also widened to accept a
  trailing `K` (Guatemalan NIT check digit — the 7-invoice PDF's own agent NIT is `543386K`,
  the first NIT seen in this module with that suffix). If a future PDF matches **neither**
  layout, the parser still falls back to `requiere_revision_manual=True` rather than guessing.
- **Bot automation — DRAFT ONLY, not yet run against the real portal**:
  `C:\Users\Alex\Documents\n8n\sat-bot\run_sat_download_retenciones.py` is a new,
  independent script (same `SAT_ENV_FILE`/env-loading pattern as the other 3 wrapper
  scripts). `open_retenciones_iva_menu()` (high confidence — mirrors the *already-confirmed*
  menu pattern in `run_sat_download_only.py::open_dte_menu_cuenta_personal`, which navigates
  the same PrimeFaces root menu via `btnContraerMenu` + hover chains over
  `ui-menuitem-text` spans to reach Servicios Tributarios > Factura Electrónica en Línea
  (FEL); this only changes the 2nd/3rd-level item text to "Constancias de Retenciones y
  Exenciones" > "Constancias de Retención del IVA e ISR Recibidas", same root menu). Past
  that point — the search screen's fields, the results table, and how an individual PDF is
  downloaded per row — is an **unverified guess** built only from screenshots, since there's
  no way to confirm real selectors without live portal access. Rather than shipping
  Selenium code against invented selectors (which would fail silently/confusingly), the
  script instead: (1) navigates to the screen, (2) dumps every visible interactive
  element's tag/id/class/text to `retenciones_page_dump.txt` next to the script, and (3)
  attempts a best-effort search+download using the most common patterns already seen
  elsewhere in this same portal (PrimeFaces `ui-*`/Angular Material `mat-*`), with every
  step wrapped so a wrong guess is logged, never a hard crash. **Next step**: run this once
  against the real portal, and use the resulting page dump to replace the guessed

  entrego la estructura completa... la integro una vez tengas los selectores reales"
  approach already used for the original DTE bot in its early iterations).
  `run_sat_upload_retenciones_to_odoo.py` (calling `construtec.sat.retention.create_from_pdf`
  over XML-RPC, same shape as `run_sat_upload_to_odoo.py`) is **not yet built** — pending the
