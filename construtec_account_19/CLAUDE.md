# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this module is

Company-level fiscal/legal fields for Guatemala: `res.company.regimen_iva` (VAT regime before the SAT), `nombre_legal` (legal name), `codigo_establecimiento` (SAT establishment code). Added via `views/res_company_views.xml` (inherits `base.view_company_form`), right before `company_registry`.

## Why this exists instead of installing `l10n_gt_edi`

Stock Odoo already ships a Guatemala electronic-invoicing module (`l10n_gt_edi`) with an equivalent field (`res.company.l10n_gt_edi_vat_affiliation`, same 8 selection values) — but that module is **hardcoded to INFILE, S.A.** as the certifier (see `l10n_gt_edi/models/res_company.py`: field labels literally say "Infile Web Service Provider", "Infile Key (LlaveAPI)", and the invoice report prints "Certificador: INFILE, S.A." as static text). Since the client's actual FEL certifier wasn't confirmed at the time this was built, this module replicates just the 3 non-certifier-specific fields (regime + legal name + establishment code) so reports/payroll can reference them now, without committing to Infile.

## Known gap (by design, not by accident)

**No electronic-invoicing (FEL) integration yet.** `l10n_gt_edi`'s certifier-specific fields (`l10n_gt_edi_service_provider`, `l10n_gt_edi_infile_key`, `l10n_gt_edi_infile_token`, `l10n_gt_edi_ws_prefix`, `l10n_gt_edi_phrase_ids`) were deliberately **not** replicated — "las funciones de certificación las haremos después" (per the user). When that scope is picked up, first confirm which certifier Construtec actually uses before building against it (don't assume Infile).

## SAT document import (n8n → bandeja de revisión → factura)

A second, unrelated scope: an n8n workflow logs into the SAT Agencia Virtual portal (browser automation — no public API for this exists), downloads DTEs (both `recibidas`/compras and `emitidas`/ventas, since Construtec issues its sales invoices **outside** Odoo), and writes them into Odoo via the standard external API (XML-RPC/JSON-RPC) as a **staging record**, not directly as an `account.move`. This is deliberately a different scope from the FEL gap above — it's about *archiving/booking documents already certified by SAT*, not about *certifying/sending* invoices from Odoo.

- **`construtec.sat.document`** (`models/sat_document.py`) — one row per DTE: `direction` (recibida/emitida), `numero_autorizacion` (SAT's UUID, unique via `models.Constraint` so retries can't duplicate a document), `tipo_dte`, `serie`/`numero_documento`, `fecha_certificacion`, raw `nit_emisor`/`nombre_emisor`/`nit_receptor`/`nombre_receptor` from the DTE, a resolved `partner_id` (resolved/created by NIT — mirrors how `l10n_gt_edi` itself identifies parties, no custom NIT field on `res.partner`), `xml_attachment_id`/`pdf_attachment_id` (real `ir.attachment` records, same pattern `l10n_gt_edi_document.py` uses — not `Binary` fields), and `line_ids`.
- **`create_from_dte(vals)`** (`@api.model` on `construtec.sat.document`) is the single external-API entrypoint — the one method an outside caller (the Python bot, n8n, whatever) invokes via `execute_kw`/JSON-RPC instead of orchestrating `search_read`/`create`/`ir.attachment.create` itself. Takes header fields (same names as the model fields) plus `lines` (list of dicts matching `construtec.sat.document.line` fields) and optional `xml_filename`/`xml_base64`/`pdf_filename`/`pdf_base64`. In one transaction: resolves/creates the `res.partner` by NIT (emisor if `direction='recibida'`, receptor if `'emitida'`, via private helpers `_sat_find_or_create_partner`/`_sat_create_attachment`), creates the header + lines + attachments, and writes a `construtec.sat.import.log` row. Idempotent on `numero_autorizacion`: a repeat call returns `{'state': 'skipped_duplicate', 'document_id': <existing>}` without creating anything — verified via `odoo-bin shell` against a real downloaded DTE XML (see the SAT bot doc below), including that a second call with the same `numero_autorizacion` is a no-op. On any exception it logs `state='error'` with the message and re-raises, so the external caller sees the RPC fault.
- **`construtec.sat.document.line`** — one row per DTE line item (`descripcion`, `cantidad`, `precio_unitario`, `monto_iva`, `monto_total`). `product_id`/`account_id`/`tax_ids` are **left blank by n8n on purpose** — the user explicitly chose manual mapping over auto-matching by product code/description ("menos casos raros que depurar"). `monto_descuento` is captured but **not** translated into Odoo's percentage-based line `discount` field — it's informational only.
- **`state`** is `pendiente` / `convertido_factura` / `convertido_orden_compra` — a document can only go down **one** of those two conversion paths, never both (both action methods raise `UserError` once `state != 'pendiente'`). This was a 2-value field (`pendiente`/`convertido`) before the Orden de Compra path was added; renamed instead of adding a separate boolean, since the two outcomes are mutually exclusive by design.
- **`action_convertir_a_factura()`** on the header builds `invoice_line_ids` from the lines (requires every line to have `account_id` set, raises `UserError` otherwise), picks `move_type` from `direction` + `tipo_dte`, and **re-parents** the two attachments (`ir.attachment.write({'res_model': 'account.move', 'res_id': move.id})`) so they show up in the invoice's own chatter instead of staying attached to the now-historical staging record. Sets `move.sat_document_id` back-reference and `move.message_main_attachment_id` to the PDF.
  - `move_type` selection: only `tipo_dte == 'NCRE'` (Nota de Crédito) maps to `in_refund`/`out_refund`. `NDEB` (Nota de Débito) maps to a **normal** `in_invoice`/`out_invoice` — a debit note *increases* what's owed, it is not a refund; this mirrors how Odoo's own "Debit Note" wizard works (creates a new regular invoice/bill, not a credit note). Getting this wrong was an actual bug caught and fixed here — don't re-collapse `NCRE`/`NDEB` into one bucket. See `TIPOS_DTE_NOTA_CREDITO` (only `('NCRE',)`).
- **`action_convertir_a_orden_compra()`** — the other conversion path, **only available for `direction == 'recibida'`** (purchases; `emitida` are Construtec's own sales, handled outside Odoo, so there's no "sales order" equivalent). Builds `purchase.order.line` records from `line_ids` (needs `product_id` per line, unlike the factura path which only needs `account_id`) and re-parents the attachments the same way. Confirming/receiving/billing from there on is 100% native Odoo (`purchase_stock`) — nothing custom: confirm the PO → a Receipt (`stock.picking`) is auto-created → validate it to actually move stock → "Create Bill" from the PO for the vendor bill. This is why the module depends on `purchase_stock` (not just `purchase` — plain `purchase` has no stock/receipt integration at all, that glue lives specifically in `purchase_stock`).
  - Line `product_id` is optional in `construtec.sat.document.line` (manual mapping, see above), but `purchase.order.line.product_id` is required — `_sat_get_or_create_generic_product()` searches `product.product` by exact name match on the DTE line description, or creates a new **storable** product (`product.template` with `type='consu'`, `is_storable=True` — `is_storable` lives on `product.template`, not `product.product`, so the generic-product path creates a template and takes its `product_variant_id`, it can't `product.product.create()` directly with that field) so it actually counts for inventory control.
- **`account.move.sat_document_id`** (`models/account_move.py`) and **`purchase.order.sat_document_id`** (`models/purchase_order.py`) are the only changes to those two existing models — a readonly back-reference plus an `action_view_sat_document()` smart-button opener on each. Nothing else about invoicing/partida_numero logic changed.
- **`construtec.sat.import.log`** (`models/sat_import_log.py`) is a separate, complementary audit trail written on *every* `create_from_dte` attempt (success/error/`skipped_duplicate`), including ones that never produced a `construtec.sat.document` (e.g. a duplicate `numero_autorizacion`) — the header's own `state` only tracks what happens *after* creation (factura vs. orden de compra vs. still pending), not the import attempt itself.
- Menu: new top-level "Documentos SAT" under Accounting (`account.menu_finance`), listing the bandeja (default-filtered to `pendientes`) and the log.

**Current state of the pieces outside this module**: the portal-login/download side is no longer n8n browser-automation nodes — it turned out Agencia Virtual blocks/rate-limits CDP-controlled browsers, so downloading now happens via an adapted Selenium bot (`C:\Users\Alex\Documents\n8n\sat-bot\run_sat_download_only.py`, isolated from its original source project, stripped of its own API-upload/WhatsApp features) invoked by an n8n **Execute Command** node (installed as an always-on Windows service via NSSM, `NODES_EXCLUDE=[]` to keep that node enabled — it's blocked by default since n8n v2.0). That part downloads real XML/PDF to a local `outbox` folder and is verified working end-to-end. Still true: no line-level auto-mapping (see above).

**`action_import_from_outbox()`** (`@api.model` on `construtec.sat.document`, `models/sat_document_import.py`) closes the loop from that `outbox` folder into this module — deliberately implemented as Odoo-side code that reads the local filesystem directly, **not** an external script calling the API over XML-RPC. Since Odoo and the SAT bot run on the same machine, there's no RPC hop needed: the button calls `create_from_dte()` as a plain in-process ORM call. What it does:
- Reads the outbox root from system parameter `construtec_account_19.sat_outbox_path` (default `C:\Users\Alex\Documents\n8n\sat-bot\data\outbox`), globs `*/section_*/xml/*.xml` under it, and maps `section_1` → `direction='recibida'`, `section_2` → `'emitida'` (confirmed against real downloads: `section_1` is where the DTE's `Receptor` is the account's own NIT, i.e. purchases).
- Parses each DTE (`xml.etree.ElementTree`, namespace `http://www.sat.gob.gt/dte/fel/0.2.0`) into the same shape `create_from_dte` expects — header fields, `lines`, base64 of the XML plus its matching PDF if one exists alongside it (`<section>/pdf/<same-stem>.pdf`). `fecha_certificacion` comes off the XML as a local ISO datetime with a `-06:00`-style offset and gets converted to naive UTC before being handed to the `Datetime` field.
- Calls `self.env['construtec.sat.document'].create_from_dte(vals)` per file and tallies `success`/`skipped_duplicate`/`error`, returning an `ir.actions.client` `display_notification` with the summary. **Verified against the real outbox** (35 downloaded XML, several re-downloaded copies of the same DTE under different filenames): first run correctly created only the 17 truly-unique documents and flagged the other 18 as duplicates (same `numero_autorizacion` inside the XML, different filename); a second run over the same files created zero and flagged all 35 as duplicates. Safe to re-run any time, including from a future scheduled action — nothing here is exposed over XML-RPC/JSON-RPC, it's purely internal.
- Reachable from Accounting → Documentos SAT → **"Importar desde SAT"** (an `ir.actions.server` menu item, not a form button, since it isn't scoped to one record). This is the manual/on-demand path, meant for testing or a human-triggered re-scan of the outbox.

**`create_from_dte_xml(xml_base64, direction)`** (`@api.model`, same file) is the path meant for n8n (or any external orchestrator) to call **directly over XML-RPC/JSON-RPC** — the design settled on n8n owning *when* to upload (it already knows what it just downloaded and doesn't need to re-scan a folder), while Odoo keeps owning *all* the parsing and the anti-duplicate logic (n8n doesn't need to track "what did I already upload" itself — it can resend the same XML any time and Odoo silently no-ops via `numero_autorizacion`, read from the XML content itself, not trusted from the caller). Takes only the XML in base64 plus `direction` — **no PDF, by explicit choice** (`pdf_attachment_id`/`pdf_base64` stay empty on documents created this way). Internally it's a thin wrapper: parse with the same `_parse_dte_xml()` used by `action_import_from_outbox()`, then call `create_from_dte()` — verified against 3 real downloaded XML (created successfully, no `pdf_attachment_id`, and a resend of the same XML correctly returned `skipped_duplicate` without creating a second record).
